Helm Explained: From Kubernetes YAML to Reusable Application Releases

An illustrated guide to charts, values, releases, and repositories. Build a small Nginx chart, deploy multiple environments, upgrade and roll back releases, and understand the limits and Helm 3/4 differences.

Once you know Kubernetes, creating a Deployment and a Service is straightforward. The difficult part comes later: the application grows into a collection of resources, development and production need different settings, and every upgrade needs a record of exactly what changed.

Helm packages a set of Kubernetes resources into a reusable deployment definition, accepts configuration for each installation, and keeps a history of releases.

This guide assumes you understand Pods, Deployments, and Services. If those are new, start with From Docker to Kubernetes. We will use a small Nginx website to connect the concepts to an executable workflow.

Scope: The example uses a Chart with apiVersion: v2, supported by both Helm 3 and Helm 4. Shared commands are used throughout; failure recovery options are compared separately. You need an existing Kubernetes cluster capable of running Linux containers. Commands use single lines so they also work in PowerShell. The fixed image tag is a teaching choice, not a production version recommendation. The Helm CLI major version and Chart format version are different things: Helm 4 continues to support v2 charts. Helm 4 overview

1. Why use Helm when kubectl already works?

An application might start with this:

1
2
3

website/
├── deployment.yaml
└── service.yaml

Then it acquires configuration, ingress rules, storage, and permissions. Next, you need three environments:

Setting Development Staging Production
Replicas 1 2 3
Image Development build Candidate Validated build
Domain dev.example.com staging.example.com example.com
Resource allocation Small Similar to production Sized for actual load

Copying the directory works initially. But changing a health check now means editing several copies, and recording the previous deployment becomes another task.

Helm addresses two related problems:

  1. Reusable deployment definitions: templates contain shared structure, while values describe configuration differences.
  2. Release management: installations and upgrades have names, revisions, saved configuration, and status.
Tool Main responsibility Website example
Docker / image build tools Build a runnable image Produce the website image
Kubernetes Schedule workloads and reconcile desired state Keep the required Pods running
kubectl Interact with the Kubernetes API Apply resources, inspect events and logs
Helm Package templates and manage releases Install and upgrade the website

The comparison with apt or brew is useful, but Helm manages Kubernetes resources and release records. It does not compile your application or build its image.

For a couple of stable YAML files, kubectl apply is often sufficient. Helm becomes useful when repeated configuration, multiple installations, and release history are routine requirements.

2. Charts, values, releases, and repositories

Term Meaning Example
Chart A reusable deployment package Templates, defaults, metadata, optional dependencies
Values Inputs to a particular deployment Image tag, replica count, service port
Release A named installation of a chart web-dev in namespace helm-dev
Repository / Registry A location for distributing chart packages An HTTP chart repository or OCI registry

One chart can produce multiple releases. Install the same chart as web-dev and web-prod, supply different values, and upgrade them independently. Release names are scoped to namespaces, so queries must use the correct namespace too.

There are also three different versions to distinguish:

Identifier Example What it describes
Chart version 0.1.0 The deployment package
Chart appVersion "1.28.0" Descriptive application version metadata
Release revision 1, 2, 3 The history of one installation

Changing resource limits can justify chart version 0.1.1 without changing the application version. Upgrading an existing release creates another release revision.

Changing appVersion does not automatically change the image. Our template reads .Values.image.tag; that input controls the image tag. A chart that explicitly reads .Chart.AppVersion would behave differently. Always inspect the template rather than assuming the metadata controls deployment behavior. Chart format

3. What happens during installation?

The main flow is:

1
2
3
4
5
6
7

Chart templates + merged values + release context
                       ↓
            Ordinary Kubernetes manifests
                       ↓
              Kubernetes API Server
                       ↓
          Controllers reconcile actual resources

For example, this template:

1

replicas: {{ .Values.replicaCount }}

combined with replicaCount: 2 produces:

1

replicas: 2

Kubernetes receives the rendered resource; it does not interpret Helm’s {{ ... }} expressions. Helm also manages release records, resource updates, and optional lifecycle hooks, so it is more than text substitution.

Normal Helm 3 and Helm 4 CLI operation does not require a dedicated Helm server in the cluster. Tiller belongs to Helm 2, so older tutorials that ask you to install it do not apply. After the CLI exits, Kubernetes controllers continue maintaining the application.

By default, release data is stored in Kubernetes Secrets in the release namespace. This includes chart and configuration content, which may contain sensitive information. Release history is not merely a local terminal log. Release storage

Helm itself is not a controller that continuously synchronizes the cluster with Git. A manual change is not periodically corrected by the Helm CLI. Update mechanics also vary by version: Helm 4 defaults to server-side apply for new releases, while upgrades generally retain the previous release’s apply method. Helm 4 apply behavior

4. Build and install a small Nginx chart

The example contains one Deployment and one Service. Download the complete example, extract it, and enter helm-web-demo; alternatively, create the following files. Run later commands from the directory containing web-demo/ and the environment values files.

Prepare the tools and files

Install Helm and kubectl, and prepare a practice cluster. The official installation guide describes platform-specific binaries and other installation options. Ensure Helm is on your PATH, then check:

1
2
3

helm version --short
kubectl config current-context
kubectl get nodes

The context identifies the target cluster. Installation commands below modify that cluster, so use a practice environment. Helm does not create Kubernetes for you.

Create this layout:

We write four chart files directly so every part is visible. helm create can generate a scaffold, but includes features we do not need for this first exercise.

web-demo/Chart.yaml describes the package:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}-web
  namespace: {{ .Release.Namespace }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app.kubernetes.io/name: web-demo
      app.kubernetes.io/instance: {{ .Release.Name }}
  template:
    metadata:
      labels:
        app.kubernetes.io/name: web-demo
        app.kubernetes.io/instance: {{ .Release.Name }}
    spec:
      containers:
        - name: nginx
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
          imagePullPolicy: {{ .Values.image.pullPolicy }}
          ports:
            - name: http
              containerPort: 80
          readinessProbe:
            httpGet:
              path: /
              port: http
            initialDelaySeconds: 2
            periodSeconds: 5
          resources:
            {{- toYaml .Values.resources | nindent 12 }}

  type: ClusterIP
  selector:
    app.kubernetes.io/name: web-demo
    app.kubernetes.io/instance: {{ .Release.Name }}
  ports:
    - name: http
      port: {{ .Values.service.port }}
      targetPort: http

Only a few expressions are needed:

Expression Meaning
.Values.xxx Read a merged configuration value
.Release.Name Read the installation name; demo produces demo-web
.Release.Namespace Read the target namespace
toYaml Serialize an object as YAML
nindent 12 Add a newline and indent by 12 spaces
{{- Trim whitespace immediately to the left

The instance label keeps each Service connected to its own release’s Pods. Using only a shared application label could mix traffic between installations in the same namespace. See built-in objects and template functions and pipelines for the syntax.

Inspect, install, and open the website

These first checks run locally without a cluster:

1
2

helm lint ./web-demo
helm template demo ./web-demo -n helm-lab

Expect a Service and a Deployment named demo-web, with one replica. The rendered resources should contain no unresolved {{ ... }} expressions.

Verification scope: The downloadable chart has been checked with Helm 3.19.0 and 4.0.0 using linting and local rendering. Live installation, image pulling, browser access, upgrades, and rollback still need verification against your practice cluster.

helm template produces YAML; it does not install a release. It also does not prove that cluster permissions, admission policies, or image downloads will work.

Install the chart:

1

helm install demo ./web-demo -n helm-lab --create-namespace --wait --timeout 3m
Argument Purpose
demo Name this release
./web-demo Load the chart from this directory
-n helm-lab Select the namespace
--create-namespace Create the namespace if necessary
--wait Wait for the relevant readiness conditions
--timeout 3m Set the timeout for waiting operations

Explicit waiting avoids confusing submitted resources with ready resources. Helm 4’s waiting strategies differ from Helm 3, and readiness is not a complete business acceptance test. Install reference

Inspect the resources and forward the Service port:

1
2
3
4

helm list -n helm-lab
helm status demo -n helm-lab
kubectl get deployment,pods,service -n helm-lab
kubectl port-forward svc/demo-web 8080:80 -n helm-lab

Keep port forwarding running and open http://localhost:8080 in a browser. You should see the Nginx welcome page. Resource inspection checks existence and readiness; the browser request checks a working request path. Ctrl+C stops port forwarding without stopping the workload.

5. Reuse one chart across environments

Keep the templates shared and move differences into values files.

values-dev.yaml:

replicaCount: 1

  requests:
    cpu: 25m
    memory: 32Mi

replicaCount: 3
resources:
  requests:
    cpu: 100m
    memory: 64Mi
  limits:
    cpu: 500m
    memory: 256Mi

These files demonstrate environment inputs. Naming a file prod does not make the workload production-ready.

For this example without subcharts, precedence increases in this order:

1
2
3
4
5
6
7

Chart values.yaml
       ↓ overridden by
First -f file
       ↓ overridden by
Later -f files, with the rightmost taking precedence
       ↓ overridden by
Explicit --set / --set-string arguments

Maps generally merge by key: the development file changes requests while preserving default limits. Lists generally replace earlier lists rather than appending to them. Parent charts add another source of overrides for subcharts. Values files

Preview an override:

1

helm template demo ./web-demo -n helm-lab -f values-dev.yaml -f values-prod.yaml --set replicaCount=2

The result has two replicas, while resources come from the production overrides. Use --set for numeric and boolean inputs; --set-string makes intended strings such as image tags explicit.

Install two independent releases:

1
2

helm upgrade --install web-dev ./web-demo -n helm-dev --create-namespace -f values-dev.yaml --wait --timeout 3m
helm upgrade --install web-prod ./web-demo -n helm-prod --create-namespace -f values-prod.yaml --wait --timeout 3m

upgrade --install upgrades an existing release or installs it if absent. Namespaces provide logical separation; requirements may call for separate clusters or stronger isolation too.

Supply the intended environment inputs explicitly on each deployment. --reuse-values can merge new inputs with a release’s existing configuration, but it can also preserve forgotten overrides. Version-controlled environment files usually make the deployment easier to reproduce. Upgrade options

6. Upgrades, failures, and the limits of rollback

Return to the demo release installed earlier and scale it to two replicas:

1
2
3

helm upgrade demo ./web-demo -n helm-lab --set replicaCount=2 --wait --timeout 3m
kubectl get deployment demo-web -n helm-lab
helm history demo -n helm-lab

If the installation was revision 1, this successful upgrade creates revision 2. Changing the replica count scales the workload; changing a field in the Pod template, such as the image, triggers the Deployment’s update process. Helm does not delete and recreate the entire namespace.

To inspect deployment inputs and recorded resources:

1
2

helm get values demo -n helm-lab --all
helm get manifest demo -n helm-lab

The first includes computed defaults. The second shows the saved release manifest, which may differ from current live objects after controller or manual changes. Inspect live state with kubectl.

Check history, confirm revision 1 is the intended recovery target, and run:

1
2
3

helm rollback demo 1 -n helm-lab --wait --timeout 3m
helm history demo -n helm-lab
kubectl get deployment demo-web -n helm-lab

Following the sequence above restores one replica but creates revision 3. Rollback reapplies an earlier configuration and records another operation; it does not rewind the history counter. Rollback reference

Failure handling needs explicit intent:

Case Behavior to plan for
A normal upgrade fails Some resources may already have changed; do not assume automatic recovery
Helm 3 with --atomic A failed upgrade attempts rollback and enables waiting
Helm 4 with --rollback-on-failure Requests failure recovery with the corresponding waiting behavior
A first installation fails with recovery enabled There is no earlier release; installation cleanup/uninstall semantics apply

Choose the command for your installed major version:

1
2
3
4
5

# Helm 3
helm upgrade --install demo ./web-demo -n helm-lab --create-namespace --set replicaCount=2 --atomic --wait --timeout 3m

# Helm 4: the corresponding alternative, not a second required step
helm upgrade --install demo ./web-demo -n helm-lab --create-namespace --set replicaCount=2 --rollback-on-failure --wait --timeout 3m

Helm 4 renamed --atomic to --rollback-on-failure; the old spelling is a deprecated compatibility option. Use the new spelling in new Helm 4 scripts and inspect your installed version’s help. Recovery can itself fail because of missing permissions, unavailable old images, or removed APIs. Renamed flags

Rollback restores resource configuration, not the entire business system.

It can restore or attempt to restore It does not automatically restore
An earlier image reference Deleted or overwritten image contents
Replicas, ports, environment settings Database writes and schema changes
Helm-managed resource definitions External services or queue contents
A chart’s declared desired state External side effects of hook scripts

Database migrations need compatibility planning and backups. Images need traceable versions or digests. Those responsibilities remain even when Helm manages releases.

helm test runs tests declared as chart hooks; it is not a built-in complete application test suite. This minimal chart defines no test hooks, so the exercise uses browser access. For charts with tests, a failed standalone helm test after a successful upgrade does not retroactively activate the earlier upgrade command’s failure rollback option. Chart tests

7. Consume existing charts and distribute your own

Writing a minimal chart helps explain the mechanics. In practice, you will also consume charts maintained by other projects. A useful sequence is: verify the source → inspect documentation and values → pin a version → preview resources → install and validate.

Distribution method Storage How it is addressed
Traditional repository HTTP service with an index.yaml and packages Register with helm repo add
OCI registry Registry supporting OCI artifacts Reference with oci://

The following shows the shape of traditional repository commands. example.com, chart names, and versions are placeholders to replace with a real maintainer’s information. --version pins the chart version:

1
2
3
4
5
6

helm repo add vendor https://charts.example.com
helm repo update
helm search repo vendor
helm show values vendor/example-app --version 1.2.3
helm template demo vendor/example-app --version 1.2.3 -f my-values.yaml
helm install demo vendor/example-app --version 1.2.3 -f my-values.yaml -n app-space --create-namespace --wait

Repository locations, image access rules, and maintenance status change. Check the maintainer’s documentation rather than treating a tutorial’s third-party address as a permanent interface. Using charts from repositories

Package and inspect our own chart locally:

1
2
3

helm package ./web-demo
helm show chart ./web-demo-0.1.0.tgz
helm template demo ./web-demo-0.1.0.tgz -n helm-lab

The .tgz file is a distributable chart package. Increase the chart version when templates or defaults change instead of distributing different contents under the same version.

For OCI distribution, replace the placeholder registry with a real one where you have permissions:

1
2
3
4

helm registry login registry.example.com
helm push web-demo-0.1.0.tgz oci://registry.example.com/charts
helm show values oci://registry.example.com/charts/web-demo --version 0.1.0
helm install demo oci://registry.example.com/charts/web-demo --version 0.1.0 -n helm-lab --create-namespace --wait

Login uses the registry host. The push destination omits the chart name and version because Helm derives them from the package. OCI references do not need registration with the traditional helm repo add workflow. OCI registries

Charts can declare dependencies in Chart.yaml. During development, helm dependency update resolves dependencies and creates or updates Chart.lock; later, helm dependency build reconstructs dependencies from the lock file. This does not pin all container images, which require their own version policy. Chart dependencies

8. Troubleshooting and choosing the right tool

Each check answers a different question:

Check What it tells you What it does not prove
helm lint Common structural or template issues Real cluster permissions and runtime behavior
helm template The manifests generated from the inputs That anything was installed
Installation/upgrade with --wait Relevant resource readiness conditions Complete business availability
A browser request or smoke test A particular request path works Every workflow is correct
Monitoring and ongoing probes Continued operational behavior No future failures

Start troubleshooting at the failing layer:

Symptom Inspect first Typical explanation
YAML parse error helm template --debug Indentation, quoting, generated value types
cannot re-use a name helm list --all in the right namespace Existing release, possibly needing an upgrade
release not found Context, namespace, release name Wrong installation location
Existing resource conflicts Ownership of the live object Another release or tool owns the resource
Wait timeout Pod events, image pulls, probes, quota Resources did not become ready
Service has no ready backends Selectors, labels, readiness No matching ready Pods
A values change has no effect Computed values and rendered resources Override precedence or an unused input

For this example:

1
2
3
4
5
6
7

helm status demo -n helm-lab
helm history demo -n helm-lab
kubectl get pods -n helm-lab -l app.kubernetes.io/instance=demo
kubectl describe deployment demo-web -n helm-lab
kubectl describe pods -n helm-lab -l app.kubernetes.io/instance=demo
kubectl logs deployment/demo-web -n helm-lab --tail=100
kubectl get events -n helm-lab --sort-by=.metadata.creationTimestamp

A few operational details deserve attention:

  • Values files are not a secret vault. Sensitive inputs can appear in release records, rendered manifests, and CI logs. Keep real credentials out of public repositories and use an appropriate secret management workflow. Dry-run output may include Secret resources. Output behavior
  • Do not adopt conflicting resources blindly. Ownership validation protects resources managed elsewhere. --take-ownership changes the scope of later upgrades and uninstalls; establish who is responsible first. Resource ownership
  • Uninstall is not a guarantee that everything disappears. CRDs in crds/ have special lifecycle handling; hook resources need deletion policies, and storage retention depends on templates and reclaim policies. CRD management, hook lifecycle

Clean up the releases you actually installed:

1
2
3
4

helm uninstall demo -n helm-lab
# Only needed if you installed the two optional environment releases
helm uninstall web-dev -n helm-dev
helm uninstall web-prod -n helm-prod

Release-managed resources are removed, but the namespace created with --create-namespace is not automatically deleted. This chart uses no persistent storage; review data retention before uninstalling database charts. Uninstall reference

Choose tools based on the problem:

Requirement Consider
A few stable resources Plain YAML and kubectl
Environment-specific patches to existing YAML Kustomize
Reusable configurable packages and release operations Helm
Continuous reconciliation with configuration in Git GitOps controllers such as Argo CD or Flux
Domain operations such as database failover and backup A suitable Operator

These approaches can work together. Kustomize transforms resource definitions, and Operators automate domain-specific operations. A GitOps controller can consume charts and values, but its integration determines who owns release state: Argo CD uses Helm for rendering and manages the lifecycle itself, so identical helm history behavior should not be assumed.

Once this example makes sense, continue with CI/CD, GitLab CI, and Helm to see why a delivery pipeline pins images, supplies environment inputs, verifies outcomes, and defines recovery explicitly.

For further reading, use the official documentation, template guide, and Helm 4 overview. Check the documentation version against your installed helm version before copying version-sensitive options.

Automating Kubernetes Deployments: From Git Push to Verification and Recovery

A complete Go service example connecting GitHub Actions, GHCR, Kubernetes release permissions, rolling updates, smoke tests, and recovery, building on the earlier Docker and K8s guides.

The earlier Docker to Kubernetes guide introduced Pods, Deployments, and Services. The container cloud deployment walkthrough connected Dockerfile builds, registry uploads, and platform configuration. The CI/CD guide explained the pipeline concepts.

The next question follows naturally: once an application can be deployed manually, how do we make a code change trigger tests, an image build, a deployment, and checks that detect a broken release?

This article follows a small Go service through that entire path. The order API is an HTTP demonstration; it does not process real orders or connect to a database.

1. Turn deployment into a sequence of checks

Manual releases often depend on assumptions: “this image should be current,” or “the page loads, so the deployment probably worked.” Automation needs explicit inputs, outputs, and acceptance criteria.

Stage Input → output Acceptance criteria On failure
Integration PR → checked commit Unit tests, static checks, Dockerfile build Block merge
Artifact build Main commit → image Build and push succeed, digest available Do not deploy
Preparation Digest + manifests → release plan API reachable, identity valid, permissions sufficient Preserve live version
Deployment Plan → new Pods Rolling update completes Collect evidence and attempt recovery
Acceptance Service → real responses Health, business smoke test, and source version match Restore previous Pod template
Observation Logs and metrics → release decision Errors, latency, and business indicators acceptable Stop promotion and follow recovery policy

The example uses GitHub Actions → GHCR → Kubernetes. Pull requests run checks. Merging into main builds an image and deploys to a dedicated demo-prod namespace. Keeping a human approval makes this continuous delivery; deployment without that approval is continuous deployment.

You need an existing cluster, an application repository on GitHub, and an administrator who can initialize the namespace. Commands use Linux/Bash; Windows users can use WSL or Git Bash. Target nodes use linux/amd64. Cluster installation is covered in the earlier guide.

Before writing the workflow, check connectivity:

Connection Required conditions
Runner → GitHub, GHCR, and tool download endpoints Source checkout, tool installation, image upload
Runner → Kubernetes API Reachable kubeconfig endpoint and trusted TLS certificate
Kubernetes nodes → GHCR Registry connectivity and credentials for private images
Users → gateway → Service → Pods Working controller, DNS, TLS, and backend routing

A working kubectl connection does not prove that nodes can pull images. Logging the Runner into GHCR does not log nodes in. GitHub-hosted Runners also cannot directly reach your computer’s 127.0.0.1 or a private corporate API. Use a dedicated Runner on a trusted network or an approved private connectivity solution for private clusters.

package main

import (
	"context"
	"errors"
	"fmt"
	"log"
	"net/http"
	"os"
	"os/signal"
	"sync/atomic"
	"syscall"
	"time"
)

var version = "dev"

func routes(ready *atomic.Bool) http.Handler {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /healthz", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "ok")
	})
	mux.HandleFunc("GET /readyz", func(w http.ResponseWriter, r *http.Request) {
		if !ready.Load() {
			http.Error(w, "not ready", http.StatusServiceUnavailable)
			return
		}
		fmt.Fprintln(w, "ready")
	})
	mux.HandleFunc("GET /version", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, version)
	})
	mux.HandleFunc("GET /{$}", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "order-api is running")
	})
	return mux
}

func main() {
	var ready atomic.Bool
	ready.Store(true)
	server := &http.Server{
		Addr: ":8080", Handler: routes(&ready),
		ReadHeaderTimeout: 5 * time.Second,
	}
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()
	go func() {
		if err := server.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
			log.Fatal(err)
		}
	}()
	<-ctx.Done()
	ready.Store(false)
	shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()
	if err := server.Shutdown(shutdownCtx); err != nil {
		log.Print(err)
		os.Exit(1)
	}
}

The listener binds to the container network interfaces. On termination, the application withdraws readiness and waits for active requests to finish. Real workloads also need connection draining, long connection handling, and background task coordination; these settings alone do not guarantee uninterrupted service.

package main

import (
	"net/http"
	"net/http/httptest"
	"strings"
	"sync/atomic"
	"testing"
)

func TestReleaseContract(t *testing.T) {
	var ready atomic.Bool
	handler := routes(&ready)
	for _, tc := range []struct {
		path   string
		ready  bool
		status int
		body   string
	}{
		{"/healthz", false, 200, "ok"},
		{"/readyz", false, 503, "not ready"},
		{"/readyz", true, 200, "ready"},
		{"/version", true, 200, version},
		{"/", true, 200, "order-api is running"},
	} {
		ready.Store(tc.ready)
		recorder := httptest.NewRecorder()
		handler.ServeHTTP(recorder, httptest.NewRequest(http.MethodGet, tc.path, nil))
		if recorder.Code != tc.status || strings.TrimSpace(recorder.Body.String()) != tc.body {
			t.Errorf("%s ready=%v: status=%d body=%q", tc.path, tc.ready, recorder.Code, recorder.Body.String())
		}
	}
}

Maintain base image security updates and pin approved base images by digest in production: a version tag can still move.

      securityContext:
        runAsNonRoot: true
        runAsUser: 65532
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: order-api
          # Template placeholder; replaced locally with the release digest before apply.

            - name: http
              containerPort: 8080
          envFrom:
            - configMapRef:
                name: order-api-config-v1
          resources:
            requests:
              cpu: 100m
              memory: 64Mi
            limits:
              cpu: 500m
              memory: 128Mi
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
          startupProbe:
            httpGet:
              path: /healthz
              port: http
            periodSeconds: 2
            failureThreshold: 30
          readinessProbe:
            httpGet:
              path: /readyz
              port: http
            periodSeconds: 3
          livenessProbe:
            httpGet:
              path: /healthz
              port: http
            periodSeconds: 10

APP_ENV demonstrates configuration injection; the service does not change its behavior based on it. For a configuration change, create order-api-config-v2, update the Deployment reference, and retain the old object. Restoring an old template can then restore its configuration reference. Secrets also need a version strategy; credentials do not belong in ConfigMaps.

Setting Release behavior
startupProbe Readiness and liveness do not run until startup succeeds
readinessProbe Unready Pods are excluded from normal ready Service backends
livenessProbe Repeated failures eventually trigger a container restart
minReadySeconds: 5 A new replica must remain ready before being considered available
maxUnavailable: 0 Planned updates do not deliberately reduce available replicas
maxSurge: 1 One extra update replica is allowed; spare capacity is needed
progressDeadlineSeconds: 180 Reports failed progress after the configured deadline

See the official probe documentation for exact semantics. A progress deadline does not automatically restore the previous version; recovery is an explicit workflow step below.

The diagram shows an ideal progression. Node failures, capacity shortages, endpoint propagation, and application behavior still affect availability. Terminating Pods can temporarily consume additional resources beyond the three active slots illustrated here.

The initial example uses ClusterIP and port forwarding. For user access, have the platform provision a Gateway/Ingress, DNS, and TLS. An Ingress object needs an actual controller, and a ClusterIP is not a public address.

4. Establish identities and release permissions

There are three separate credentials:

Credential Consumer Purpose Provisioning
GITHUB_TOKEN Build Job Publish to GHCR Job token with packages: write
ghcr-read Kubernetes nodes Pull a private image Administrator-created registry Secret
KUBE_CONFIG Deploy Job Update applications in demo-prod Restricted deployer kubeconfig

New GHCR packages are private by default. Either make a demonstration image public or configure private image access as below. Write access in CI does not imply node read access. See GitHub’s Container registry documentation.

Use an account with access to the target package and a classic PAT with read:packages; organizational SSO and package policies may impose additional authorization. The interactive initialization command briefly places the token in local process arguments. Use a controlled terminal for the exercise; shared hosts should use platform secret management or controlled Docker configuration imports. Rotate an existing Secret through the platform’s approved process.

The Role cannot manage the cluster, change RBAC, or directly read Secrets. However, an identity that can modify workloads may still cause a Pod to mount namespace Secrets. Use a dedicated namespace, trusted deployment code, and appropriate admission and workload identity policies. See Kubernetes RBAC.

Generate a short-lived kubeconfig for the exercise. Run this locally as an administrator connected to the intended cluster. It copies the endpoint and CA, not the administrator’s credentials. A one-hour ServiceAccount token is requested; actual lifetime depends on the server.

The expected authorization result is yes. This assumes a standard HTTPS endpoint and CA. Platforms requiring proxies, a special TLS server name, or cloud authentication plugins should provide a suitable restricted CI kubeconfig. Do not bypass certificate verification.

Create a production environment in the application repository’s Settings → Environments. Restrict deployments to main and configure approval if desired and supported. Add environment Secret KUBE_CONFIG containing this file. With an authenticated GitHub CLI:

1

gh secret set KUBE_CONFIG --env production < .deploy-local/ci.kubeconfig

Also create environment Variable KUBECTL_VERSION containing a compatible explicit patch version. v1.35.0 illustrates the format, not a version recommendation. Keep kubectl within one minor version of the API Server. The workflow follows the checksum verification described in the official Linux installation guide.

Storing a one-hour token in a Secret does not renew it. Expiration, including time spent waiting for approval, requires a new token and Secret update. Long-lived production automation should exchange platform-supported OIDC/workload identity for short-lived credentials or use managed rotation. GitHub OIDC tokens are not automatically accepted by arbitrary Kubernetes clusters: trust configuration or an identity exchange is required. See ServiceAccount token documentation.

name: order-api-release

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - uses: actions/setup-go@v7
        with:
          go-version: '1.26.9'
          cache: false
      - run: go vet ./...
      - run: go test -race -v ./...
      - name: Check Dockerfile on PR
        if: github.event_name == 'pull_request'
        run: docker build --build-arg VERSION=pr-check -t order-api:pr .

  build:
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    needs: test
    runs-on: ubuntu-24.04
    permissions:
      contents: read
      packages: write
    outputs:
      image: ${{ steps.name.outputs.image }}
      digest: ${{ steps.push.outputs.digest }}
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - id: name
        shell: bash
        run: echo "image=ghcr.io/${GITHUB_REPOSITORY,,}" >> "$GITHUB_OUTPUT"
      - uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/setup-buildx-action@v4
      - id: push
        uses: docker/build-push-action@v7
        with:
          context: .
          push: true
          platforms: linux/amd64
          tags: ${{ steps.name.outputs.image }}:sha-${{ github.sha }}
          build-args: VERSION=${{ github.sha }}
          labels: org.opencontainers.image.source=https://github.com/${{ github.repository }}

  deploy:
    needs: build
    runs-on: ubuntu-24.04
    environment: production
    concurrency:
      group: order-api-production
      cancel-in-progress: false
    env:
      KUBECTL_VERSION: ${{ vars.KUBECTL_VERSION }}
      IMAGE_REF: ${{ needs.build.outputs.image }}@${{ needs.build.outputs.digest }}
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - name: Install compatible kubectl
        shell: bash
        run: |
          set -euo pipefail
          test -n "$KUBECTL_VERSION"
          url="https://dl.k8s.io/release/${KUBECTL_VERSION}/bin/linux/amd64/kubectl"
          curl -fsSL "$url" -o "$RUNNER_TEMP/kubectl"
          curl -fsSL "$url.sha256" -o "$RUNNER_TEMP/kubectl.sha256"
          expected=$(cat "$RUNNER_TEMP/kubectl.sha256")
          printf '%s  %s\n' "$expected" "$RUNNER_TEMP/kubectl" | sha256sum --check
          chmod +x "$RUNNER_TEMP/kubectl"
          echo "$RUNNER_TEMP" >> "$GITHUB_PATH"          
      - name: Configure cluster access
        env:
          KUBE_CONFIG: ${{ secrets.KUBE_CONFIG }}
        shell: bash
        run: |
          set -euo pipefail
          test -n "$KUBE_CONFIG"
          export KUBECONFIG="$RUNNER_TEMP/order-api.kubeconfig"
          umask 077
          printf '%s' "$KUBE_CONFIG" > "$KUBECONFIG"
          echo "KUBECONFIG=$KUBECONFIG" >> "$GITHUB_ENV"
          kubectl auth can-i patch deployments -n demo-prod | grep -qx yes          
      - name: Reject stale release
        env:
          GH_TOKEN: ${{ github.token }}
        shell: bash
        run: |
          set -euo pipefail
          latest=$(gh api "repos/$GITHUB_REPOSITORY/git/ref/heads/main" --jq '.object.sha')
          test "$latest" = "$GITHUB_SHA"          
      - name: Save previous Pod template
        shell: bash
        run: |
          set -euo pipefail
          kubectl -n demo-prod get deployment order-api --ignore-not-found -o json \
            | jq -c '.spec.template // empty' > "$RUNNER_TEMP/previous-template.json"          
      - name: Apply release and wait
        id: release
        shell: bash
        run: |
          set -euo pipefail
          kubectl apply -f k8s/runtime.yaml
          kubectl set image --local -f k8s/deployment.yaml \
            "order-api=$IMAGE_REF" -o yaml > "$RUNNER_TEMP/rendered-deployment.yaml"
          kubectl apply -f "$RUNNER_TEMP/rendered-deployment.yaml"
          kubectl -n demo-prod rollout status deployment/order-api --timeout=240s          
      - name: Verify response and source version
        id: verify
        shell: bash
        run: |
          set -euo pipefail
          kubectl -n demo-prod port-forward service/order-api 18080:80 \
            > "$RUNNER_TEMP/port-forward.log" 2>&1 &
          forward_pid=$!
          trap 'kill "$forward_pid" 2>/dev/null || true' EXIT
          actual=$(curl -fsS --retry 12 --retry-connrefused --retry-delay 1 \
            --max-time 5 http://127.0.0.1:18080/version)
          test "$actual" = "$GITHUB_SHA"
          curl -fsS --max-time 5 http://127.0.0.1:18080/readyz
          test "$(curl -fsS --max-time 5 http://127.0.0.1:18080/)" = "order-api is running"
          printf 'Verified commit: `%s`\n\nImage: `%s`\n' \
            "$GITHUB_SHA" "$IMAGE_REF" >> "$GITHUB_STEP_SUMMARY"          
      - name: Collect failure evidence
        if: ${{ failure() && (steps.release.outcome == 'failure' || steps.verify.outcome == 'failure') }}
        shell: bash
        run: |
          kubectl -n demo-prod get deployment,replicaset,pods -l app=order-api -o wide || true
          kubectl -n demo-prod describe deployment order-api || true
          kubectl -n demo-prod get events --sort-by=.lastTimestamp || true
          kubectl -n demo-prod logs -l app=order-api --all-containers --prefix --tail=100 || true          
      - name: Restore previous Pod template
        if: ${{ failure() && (steps.release.outcome == 'failure' || steps.verify.outcome == 'failure') }}
        shell: bash
        run: |
          set -euo pipefail
          if [ ! -s "$RUNNER_TEMP/previous-template.json" ]; then
            echo 'First deployment: no previous template. Manual investigation required.'
            exit 1
          fi
          patch=$(jq -c '[{op:"replace",path:"/spec/template",value:.}]' "$RUNNER_TEMP/previous-template.json")
          kubectl -n demo-prod patch deployment order-api --type=json -p "$patch"
          kubectl -n demo-prod rollout status deployment/order-api --timeout=240s          
      - name: Remove temporary kubeconfig
        if: always()
        shell: bash
        run: rm -f -- "$RUNNER_TEMP/order-api.kubeconfig"

The publishing pattern is documented in GitHub’s image publishing tutorial and Docker build-push-action. Major Action tags improve readability here. Production should pin reviewed full commit SHAs and maintain them with dependency updates. A tag such as @v7 is mutable; self-hosted Runners must also meet each Action’s runtime requirements.

Design choice Purpose
PRs only run checks; main pushes build and deploy Unmerged code does not receive production deployment credentials
Explicit needs dependencies Failed prerequisites block later stages
Lowercase repository name Produces a valid GHCR path such as ghcr.io/symphonyw/order-api
SHA tag plus deployment by digest Human-readable traceability and an exact artifact identity
context: . Uses the checked-out directory for Docker’s build context
No rebuild during deployment The artifact being released is the one already produced
Local image substitution before apply Avoids deploying the placeholder and applies other Git-managed settings too
Main SHA checked immediately before deployment Reduces the risk of delayed releases overwriting newer work
Deployment concurrency group Prevents overlapping deployment Jobs for this application/environment
Explicit failure() recovery conditions Diagnostics and restoration can run after a failed step

cancel-in-progress: false preserves a running deployment. However, GitHub concurrency groups are not strict FIFO release queues: pending work can be replaced and execution ordering is not guaranteed. The main SHA check reduces stale releases but is not a transaction lock; another commit may arrive between the check and apply. This suits a “deploy the latest main” policy. Strictly ordered release requirements need a dedicated queue or controller. See GitHub concurrency control.

There are three different completion signals: apply means the API accepted the resources; rollout status means the controller finished the rollout; an expected SHA from /version demonstrates that the responding application matches the intended source. The business smoke request adds a check beyond process health.

Port forwarding a Service selects a Pod. It checks that application’s response, but does not exercise normal Service forwarding, every replica, DNS, the gateway, or TLS. When a real entry point exists, also check https://your-domain/version and run suitable business requests through it. One HTTP 200 is not complete user-path validation.

6. Run a successful release, then rehearse recovery

Step Action Expected result

2 Commit application files and open a PR Tests and Dockerfile build pass
3 Require the test check for main, then merge Build produces SHA tag and image digest
4 Check first-publish package access The pull account can read the package; pause approval and fix it if necessary
5 Approve production if configured Deploy updates the application using that digest
6 Inspect Workflow Summary and the cluster Source SHA matches and two replicas are available

Rehearse a failure only in the dedicated exercise environment. After a successful baseline release, change the readiness path to /not-ready, pass the PR checks, and merge. The application returns 404 at that path, so new Pods cannot become ready. The rollout fails; CI collects evidence and restores the saved Pod template. After observing recovery, immediately fix the path back to /readyz through a new commit so Git is correct too.

Restoring a snapshot of the actual previous template avoids assuming that the previous rollout history entry is the desired recovery target. The strategy still has limits:

Situation Example behavior Additional action
Tests or image build fail Cluster unchanged Fix source and retry
Authentication, permission, or stale-release check fails No apply performed Fix access or release the current commit
New Pods fail and an old template exists Restore template and wait for rollout Validate business behavior and the external path
First deployment fails Explicit failure, no old template Investigate and clean failed resources if necessary
Recovery rollout also times out Job stays failed Operator intervention
Runner disappears, Job is cancelled, or API is unreachable Recovery may not execute Independent monitoring and operational response
Service changed, Secret overwritten, or database migrated Template restoration is insufficient Separate configuration/data recovery strategy

Recovery does not turn a failed release green. The workflow remains failed even when the restoration step succeeds. A recovered rollout also needs business verification and metric observation. Deployment history rollback concerns the Pod template, not an entire application transaction; see the Deployment documentation.

Symptom Check first Useful evidence
GHCR push returns 403 Package permissions, repository association, organization policy Build logs and package access settings
Unauthorized / Forbidden Expiration, context, RoleBinding Authorization checks and API response
API connection timeout Runner network, endpoint, firewall, CA Connection errors; never print full kubeconfig
ImagePullBackOff Digest existence, pull credentials, node egress kubectl describe pod <pod> -n demo-prod
Pending Pods Resource requests, amd64 node selector, quotas Scheduling events
CrashLoopBackOff Startup, configuration, permissions, OOM kubectl logs <pod> -p -n demo-prod
Running but not Ready Probe path, listening address, dependencies Pod description and application logs
Internal checks pass but domain fails Controller, Service, DNS, TLS Gateway logs and real entry-point requests

Database migrations need a separate release design. A common approach is expand–migrate–contract: introduce backward-compatible structures, support old and new application versions, migrate data, then remove old structures after observation. Migration Jobs need idempotency, concurrency control, and failure handling. Do not have every application Pod race to execute irreversible DDL. Restoring an image also does not undo messages, external calls, or modified records.

7. Evolve toward a maintainable release system

Once the basic path works, add controls according to the workload’s needs.

Area Starting point here Production evolution
Environments Dedicated exercise namespace Isolated dev/staging/prod and production identities
Artifacts SHA tag and digest History retention, scanning, SBOM, signature verification
Credentials Short-lived exercise kubeconfig Per-Job identity exchange, rotation, audit
Validation Readiness, source version, one business request Integration tests, external E2E, environment acceptance
Observation Failure logs and manual checks Error rate, P95/P99 latency, restarts, business indicators, alerts
Release policy Two-replica rolling update Canary or blue/green where risk justifies it
Records SHA, digest, Actions execution Environment, config versions, approvals, recovery outcome

Promote the same digest between environments: build once, validate in staging, then release that artifact to production. Inject environment differences through configuration instead of rebuilding nominally identical versions.

A standard Deployment rolling update does not automatically make metric-based canary decisions. Sending limited traffic, observing results, and expanding exposure requires traffic control and progressive delivery tooling.

GitOps changes who performs deployment. This example is push deployment: CI holds an identity that calls the API. With GitOps, an environment repository records the desired state, and Argo CD or Flux reconciles it from the cluster side or a controlled network.

Aspect Push CD in this example GitOps
Cluster changes initiated by CI deployment Job Reconciler
Desired image recorded in Source template plus CI digest output Environment manifests containing the exact digest
Cluster deployment credentials Used by CI Held by the reconciler
Manual drift No continuous correction by default Detection and optional correction
Version recovery Restore snapshot, then fix source Change desired digest in the deployment repository

With Argo CD automatic sync, update Git before relying on a manual cluster change: self-healing can restore the Git version. Pruning resources is also an explicit policy. See Argo CD automated sync.

A release is accountable when its records answer four questions: which commit, which artifact and configuration, which checks, and which recovery target? That is the foundation for adding more environments, progressive delivery, or GitOps.

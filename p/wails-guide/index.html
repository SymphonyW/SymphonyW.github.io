Wails Explained: Building Cross-Platform Desktop Apps with Go and Web Technologies

Understand Wails through system WebViews, Go–JavaScript bindings, a Vue and TypeScript example, background tasks, packaging, framework tradeoffs, and the changes in v3.

If you already write application logic in Go and interfaces in Vue or React, desktop development raises a practical question: can those skills also give you local file access, application windows, and native dialogs?

Wails connects those pieces. Go runs the application logic, HTML/CSS/JavaScript provide the interface, and the operating system’s WebView displays it. It targets software installed on users’ computers: database clients, file tools, developer utilities, and local data-processing applications.

Version scope, checked on October 17, 2026: v2 remains the stable release; v3 is in Beta. This article uses v2 APIs for the walkthrough and discusses v3 separately. The example uses Wails CLI v2.12.0 as a reproducible local baseline, not as a claim about the latest minor release. Evaluate v3 against the capabilities your project needs. See the official roadmap and FAQ for current status.

What Wails contributes to a desktop application

Wails connects Go code, a Web interface, and the operating system.

Part Technology Responsibility
Interface HTML, CSS, JS/TS; optionally Vue, React, Svelte, etc. Layout, forms, interaction, visualization
Application logic Go Files, databases, networking, tasks, business rules
Bridge Generated bindings and the Wails runtime Method calls, data exchange, events
Desktop host Platform windows and WebView Present the interface and integrate platform capabilities
Development tools Wails CLI, Go, frontend tooling Scaffolding, development, bindings, builds

A frontend framework is optional. Plain JavaScript can be sufficient for a small utility. Wails does not supply every business UI component or automatically turn HTML buttons into native system controls.

Common assumption More accurate description
Go runs as JavaScript inside the page Go runs as native application code; JavaScript invokes it through the bridge
You must start a Gin server for the interface Generated local bindings usually remove the need to build your own REST service
End users must install Node.js Node.js is normally a development/build dependency, rather than a runtime requirement of the packaged application

Wails supplies desktop facilities such as windows, menus, events, clipboard access, and dialogs. Persistence, accounts, synchronization, update policy, and application-specific plugin systems remain design decisions. Check the relevant version’s runtime documentation for supported operations and platforms.

How system WebViews and the Go bridge work

This diagram shows logical call relationships, rather than operating-system process boundaries:

flowchart TB UI["Web UI: Vue / React / plain JS"] Bridge["Wails bridge: bindings, data, events"] Logic["Go application logic"] Native["Desktop runtime: windows, menus, dialogs"] OS["Files, databases, network, operating system"] UI <-->|"Results / notifications"| Bridge Bridge <--> Logic Logic --> Native Logic --> OS Native --> OS

Why can the application avoid shipping a browser engine? Wails reuses the platform’s WebView instead of distributing a complete Chromium package with each application. This can reduce distribution size, but the rendering engine still exists as a system component or installed runtime. The official introduction describes this approach.

Platform Wails v2 foundation Practical consequence
Windows WebView2, based on Edge/Chromium Verify WebView2 Runtime availability; an Edge shortcut is not a dependency check
macOS System WebKit / WKWebView Web features depend on OS version; development needs Xcode Command Line Tools
Linux GTK3 + WebKitGTK Account for development packages, runtime libraries, and distribution differences

See v2 installation for platform dependencies and the Linux webkit2_41 tag. v3 uses a different default Linux stack.

Reusing the environment also means testing against that environment. A page that works in the latest Edge may behave differently in an older macOS WebKit. Validate CSS, fonts, input methods, drag and drop, downloads, and media on the systems you support.

How does a frontend call reach Go? In v2, registering a struct instance in options.App.Bind makes its exported methods available through generated JavaScript wrappers and TypeScript declarations. For example:

1

func (a *App) Greet(name string) (string, error)

The generated frontend function returns a Promise:

import { Greet } from '../wailsjs/go/main/App';

try {
  const message = await Greet('Snow');
  console.log(message);
} catch (error) {
  console.error('Call failed:', error);

This illustrates the call shape; the complete example below uses a file-selection method instead. A successful Go return resolves the Promise; a non-nil second return value of type error rejects it. Although the call resembles a local function, it crosses a language/runtime boundary. Async behavior, serialization, and failures still matter. See How does it work? for binding semantics.

sequenceDiagram participant U as User participant F as Frontend participant B as Wails binding participant G as Go method U->>F: Click button F->>B: await PickFile() B->>G: Invoke bound method G-->>B: Data or error B-->>F: Resolve or reject Promise F-->>U: Result, cancellation, or error

I prefer bridge APIs that express specific actions—ImportCSV, ListConnections, or StartExport. A generic ExecuteCommand or arbitrary file-access API expands the authority exposed to the interface and makes validation harder.

Build a file information viewer

The example follows one complete path: a button opens a native file dialog; Go reads metadata; the interface displays the filename, byte count, and modification time. It needs no database or additional Go dependency and does not read file contents.

Prepare the environment and scaffold the project. Install compatible Go and Node.js/npm versions plus platform dependencies. Frontend tools such as Vite can impose requirements beyond old minimum versions in framework tutorials; choose supported versions compatible with the actual project.

package main

import (
	"context"
	"fmt"
	"os"
	"strconv"
	"time"

	"github.com/wailsapp/wails/v2/pkg/runtime"
)

type App struct {
	ctx context.Context
}

type FileInfo struct {
	Name       string `json:"name"`
	SizeBytes  string `json:"sizeBytes"`
	ModifiedAt string `json:"modifiedAt"`
}

func NewApp() *App {
	return &App{}
}

func (a *App) startup(ctx context.Context) {
	a.ctx = ctx
}

func (a *App) PickFile() (*FileInfo, error) {
	path, err := runtime.OpenFileDialog(a.ctx, runtime.OpenDialogOptions{
		Title: "Select a file",
	})
	if err != nil {
		return nil, fmt.Errorf("open file dialog: %w", err)
	}
	if path == "" {
		return nil, nil // Cancellation returns null to the frontend.
	}

	info, err := os.Stat(path)
	if err != nil {
		return nil, fmt.Errorf("read file metadata: %w", err)
	}
	if !info.Mode().IsRegular() {
		return nil, fmt.Errorf("please select a regular file")
	}

	return &FileInfo{
		Name:       info.Name(),
		SizeBytes:  strconv.FormatInt(info.Size(), 10),
		ModifiedAt: info.ModTime().Format(time.RFC3339),
	}, nil
}

Cancellation returns an empty result rather than an error. Metadata lookup can still fail after selection, so its error must be handled. Directories and special files are explicitly rejected. The byte count is a decimal string so that the interface does not assume every Go 64-bit integer fits precisely into a JavaScript number.

The startup callback provides the Wails runtime context. An arbitrary context.Background() is not a substitute. In v2, native file dialogs are called from Go; cancellation returns an empty path. See the dialog reference.

package main

import (
	"embed"
	"log"

	"github.com/wailsapp/wails/v2"
	"github.com/wailsapp/wails/v2/pkg/options"
	"github.com/wailsapp/wails/v2/pkg/options/assetserver"
)

//go:embed all:frontend/dist
var assets embed.FS

func main() {
	app := NewApp()
	err := wails.Run(&options.App{
		Title:  "File Info",
		Width:  900,
		Height: 620,
		AssetServer: &assetserver.Options{
			Assets: assets,
		},
		OnStartup: app.startup,
		Bind:      []interface{}{app},
	})
	if err != nil {
		log.Fatal(err)
	}
}

Bind receives an instance. The lowercase startup method is not exposed as a frontend business method. JSON tags define the model’s frontend fields.

//go:embed packages built interface assets into the program. Treat frontend/dist as generated output rather than hand-maintained source. See application options for window and lifecycle configuration.

<script setup lang="ts">
import { ref } from 'vue';
import { PickFile } from '../wailsjs/go/main/App';
import type { main } from '../wailsjs/go/models';

const file = ref<main.FileInfo | null>(null);
const busy = ref(false);
const message = ref('');

async function chooseFile() {
  if (busy.value) return;
  busy.value = true;
  message.value = '';
  file.value = null;
  try {
    file.value = await PickFile();
    if (!file.value) message.value = 'No file selected.';
  } catch (error) {
    message.value = String(error);
  } finally {
    busy.value = false;
  }
}
</script>

<template>
  <main class="file-info">
    <h1>File Info</h1>
    <p>Select a local file to view its metadata.</p>
    <button :disabled="busy" @click="chooseFile">
      {{ busy ? 'Selecting…' : 'Choose file' }}
    </button>
    <p role="status" aria-live="polite">{{ message }}</p>
    <dl v-if="file">
      <dt>Name</dt><dd>{{ file.name }}</dd>
      <dt>Size (bytes)</dt><dd>{{ file.sizeBytes }}</dd>
      <dt>Modified</dt><dd>{{ file.modifiedAt }}</dd>
    </dl>
  </main>
</template>

Both language versions of this article share the same English-language sample UI; localize it as needed. The frontend supplies no filesystem path and performs no direct filesystem access. Go owns selection and metadata lookup.

Events, background tasks, and data boundaries

Reading metadata is quick enough to await directly. Scanning a large directory or exporting a database requires distinguishing a request for one result from a stream of status changes.

Mechanism Appropriate use Design concerns
Bound method Query, save, start, cancel Parameters, results, errors, idempotency
Event Progress, log excerpts, state-change notifications Subscription timing, task IDs, throttling, cleanup
File or dedicated data channel Large binary payloads or record sets Avoid repeatedly copying huge values through the bridge

	runtime.EventsEmit(a.ctx, "task:progress", map[string]interface{}{
		"taskId":  taskID,
		"percent": percent,
	})
}

import { onMounted, onUnmounted, ref } from 'vue';
import { EventsOn } from '../wailsjs/runtime/runtime';

const progress = ref(0);
const taskID = ref(''); // Save the identifier returned when creating a task.
let unsubscribe: (() => void) | undefined;

onMounted(() => {
  unsubscribe = EventsOn('task:progress', (data: unknown) => {
    if (!data || typeof data !== 'object') return;
    const event = data as Record<string, unknown>;
    if (event.taskId !== taskID.value) return;
    if (typeof event.percent !== 'number' || !Number.isFinite(event.percent)) return;
    progress.value = Math.min(100, Math.max(0, event.percent));
  });
});

onUnmounted(() => unsubscribe?.());

EventsOn returns a function that removes that subscription. Invoke it on component teardown to prevent stale callbacks and duplicate subscriptions. The events reference documents both Go and JavaScript APIs.

These snippets do not implement a task runner. In a real implementation, establish subscriptions before work starts, and avoid emitting progress before the frontend has saved the task ID. Separating task creation from task execution is one option. Provide a task-snapshot query too: events notify consumers, while application state remains authoritative.

A goroutine does not automatically provide cancellation, resource cleanup, or concurrency safety. Give tasks cancellation contexts, stop work and close resources through shutdown handling, and synchronize shared state. Native UI operations must also follow framework and platform threading requirements.

Data issue Interface design
Large int64 / uint64 values or IDs Use decimal strings when exact preservation matters
Time Specify RFC 3339 or a timestamp with explicit units and timezone semantics
Pointers and optional results Handle possible null; generated types do not replace runtime checks
Lists Define whether an empty collection is [] or null
Large files and result sets Chunk, paginate, or load on demand
Errors Present useful user-facing information and retain diagnostic context internally

Type generation reduces accidental mismatches. It does not make all incoming data trustworthy.

From a development window to distributed software

Build from the project root:

1

wails build

The build processes frontend assets according to project configuration and compiles Go into build/bin. v2 Linux environments using WebKitGTK 4.1 generally need wails build -tags webkit2_41; use matching tags for development. See the build guide and CLI reference.

flowchart LR Src["Frontend source"] --> Dist["Frontend build: dist"] Dist --> Embed["go:embed"] Go["Go source and dependencies"] --> Compile["Target-platform compilation"] Embed --> Compile Compile --> App["Desktop application"] App --> Release["Packaging, signing, distribution"]

Embedding assets solves how interface files travel with the application. It does not eliminate platform dependencies. Users normally need neither Go nor Node.js, but still need the relevant WebView and system libraries. External commands, configuration files, or dynamic libraries introduced by your application need distribution planning too.

Platform Work beyond compilation
Windows WebView2 deployment, icons, version metadata, installation location, code signing
macOS .app layout, signing, notarization, permissions, Intel/Apple Silicon targets
Linux Library compatibility, desktop entries, package format, distribution/display environment

With NSIS installed, wails build -nsis creates a Windows installer. Choose a WebView2 deployment strategy appropriate to the target environment; see the NSIS guide. Installer generation and signing are separate steps.

Cross-platform support does not guarantee that changing GOOS on one machine builds everything. v2’s Windows framework implementation does not require CGO, but macOS/Linux native dependencies and any C libraries your application adds can complicate cross-compilation. Separate Windows, macOS, and Linux CI runners are often easier to maintain. Consult v2 build flags for specifics.

Where should user data live? Embedded resources are application content, not a writable user database. Go’s os.UserConfigDir() can help locate configuration; choose appropriate writable locations for data, caches, and logs on each OS. Do not assume the working directory is the installation directory or that installation files are writable. JSON is sufficient for simple configuration; add SQLite when queries, transactions, or structured data justify it.

Before distribution, test a clean installation, offline startup, non-ASCII paths, a read-only install location, configuration migration, and missing platform components. Development-time access to source folders or the network can hide release problems.

Choosing between Wails, Electron, Tauri, and Fyne

These are architectural differences rather than benchmark results:

Dimension Wails Electron Tauri 2 Fyne
Typical application logic Go JS/TS with Node.js Rust core commands, with other integration options Go
Interface Web frontend Web frontend Web frontend Go widgets and layouts
Rendering System WebView Bundled Chromium System WebView Its own cross-platform graphics/widgets
Existing investment to reuse Go logic + Web UI Node.js ecosystem + Web UI Rust ecosystem + Web UI Go code and Go GUI experience
Main evaluation areas WebView compatibility, version-specific desktop features Distribution size, resources, processes, security configuration Rust adoption, permissions, platform integration Widgets, styling, reuse of existing Web UI

Architecture references: Wails, Electron’s process model, Tauri, and Fyne. The selection guidance here is engineering analysis based on those designs.

For teams with Go logic and Web skills, Wails offers a direct route to reusing both. An Electron application deeply dependent on Node native modules or Electron APIs requires more than swapping window hosts: its main-process behavior usually needs redesign.

Avoid universal memory or speed claims based on an empty window. Real consumption depends on page complexity, WebView subprocesses, data volume, the Go heap, caches, OS versions, and measurement method. Compare equivalent prototypes, count the whole process tree, and measure package size, startup time, idle resources, and task peaks separately.

Requirement How to evaluate Wails
Add a GUI to an existing Go CLI A strong prototyping candidate
File processing, database tools, operations, local API clients A good match for Go logic and Web UI
Identical browser-engine behavior across platforms Test system WebView differences and compare alternatives
Extensive desktop integration or multiple independent windows Verify v3 features and Beta constraints
Primarily mobile applications This v2 walkthrough does not apply; v3 mobile support remains experimental
Avoid maintaining HTML/CSS/JS Evaluate a Go-interface toolkit such as Fyne

Practical boundaries and the changes in v3

A desktop application has local authority, so the boundary between frontend content and Go capabilities matters. Frontend validation improves usability; Go-side validation determines what actions actually run.

Risk or misconception Better design
Load arbitrary remote pages into a privileged window Define trusted content; prefer the system browser for external links
Expose unrestricted command or file APIs Offer constrained actions and validate parameters, directories, and permissions
Construct shell commands by string concatenation Prefer Go libraries; otherwise use explicit executables and argument lists, treating shell invocation carefully
Treat compiled client secrets as private Avoid long-lived server secrets in clients; use user credentials and suitable system credential storage
Assume navigation cleans up listeners and tasks Define ownership, unsubscribe, cancel tasks, and release resources
Design a frameless window only for appearance Test dragging, keyboard access, scaling, input methods, and accessibility

These are application-design recommendations derived from desktop authority boundaries. Verify concrete APIs against your Wails version. Keep the application host, business logic, and persistence understandable without inventing a large abstraction system before it is needed.

v3 changes more than the install command. Its Beta introduces an explicit application/window model, services, and a visible build system. The table maps concepts without mixing v3 code into the v2 example:

Area v2 model used here v3 direction
CLI wails wails3
Module github.com/wailsapp/wails/v2 github.com/wailsapp/wails/v3
Entry point wails.Run + options.App Explicit application object and lifecycle
Bindings Struct instances in Bind Services and source-analysis-based generation
Windows Single-main-window-oriented model First-class multiple windows and window objects
Build CLI-coordinated project configuration Inspectable, customizable Taskfile workflow
Additional targets Primarily desktop Server mode and experimental mobile support

See the v3 Beta announcement for the architecture and the migration guide for porting steps. Migration involves lifecycle, runtime calls, and regenerated bindings, rather than only changing a version in go.mod.

v3 has a separate module path and CLI. Its current installation guide requires Go 1.25 or later, with GTK4 + WebKitGTK 6.0 as the default Linux stack. These differ from v2 requirements; see v3 installation. Prototype actual multi-window, tray, or other desktop workflows on target platforms before committing a new project to the Beta.

A useful first exercise is to move an existing Go utility onto the desktop: retain independently testable business functions, add a few focused bindings, and complete a target-platform package. That makes the framework’s benefits visible while exposing WebView and distribution costs early.

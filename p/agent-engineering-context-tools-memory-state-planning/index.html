Five Essentials of Agent Engineering: Context, Tools, Memory, State, and Planning

An illustrated guide to building a research assistant: context assembly, tool execution, memory lifecycles, durable state, planning, recovery, evaluation, and a runnable example.

A basic AI chat application may need only a few lines: receive a question, call a model, and display the answer. Change the request to “research several options, compare them, produce a report, and continue after an interruption,” and the engineering becomes more demanding.

The model may lose a constraint added halfway through. Search results may overwhelm the useful evidence. A tool may time out after its action has already succeeded. Thousands of stored messages may still fail to tell a restarted process where to continue.

Much of agent engineering is about giving the model suitable information at each step, executing actions reliably, and recording what actually happened.

This article follows one concrete task:

Compare three open-source knowledge-base products. Prefer official sources. Explain deployment, access control, and maintenance costs. Produce a Chinese report with references. The budget is limited; do not purchase services or send the report to anyone.

The architecture, fields, budgets, and failure scenarios below are teaching designs, not framework defaults. Interface references were checked on October 22, 2026. The focus is on design principles that transfer between frameworks.

Put the five modules on one map

A typical agent repeats a loop: read the goal and progress, assemble context, ask the model for a next action, execute a tool, observe its result, update progress, and decide whether to continue.

Module Question it answers Research-assistant example
Context management What should the model see in this call? Constraints, an unresolved question, selected evidence
Tool execution How do we access or change external systems reliably? Search documentation, read a page, save a report
Memory management What is worth recalling later? A lasting language preference or a previous version mismatch
State management Where is this task right now? Two sources read, one request timed out, report unfinished
Planning What should happen next, and why? Fill the access-control evidence gap before writing

The runtime is the program around the model: it manages the loop, permissions, budgets, persistence, and errors. It can be small; it does not have to be an elaborate framework.

Context, memory, and state overlap, but describe different dimensions. Context concerns what is provided in the current model call. Memory concerns what should be recalled later. State concerns what execution needs to record.

A language preference may live in long-term memory, then enter context when retrieved. A completed document read belongs in task state, while only its relevant findings enter context. The complete state usually contains more information than the model needs at any one moment.

Use a fixed workflow when the steps are already known. Add model-directed choices where the next step depends on discoveries. Anthropic makes a similar architectural distinction: workflows follow predefined code paths, while agents dynamically direct their process and tool use.Building effective agents

Context management: prepare the information for this step

A model normally responds using the context actually made available by the request and service. A conversation stored in a database is not automatically visible to it. Hosted sessions also require understanding how the service retains, compacts, and assembles history.

The practical job is to select useful, attributable, bounded information from a much larger collection.

Prompts describe how to work; context engineering also determines which materials arrive and how they change over time. Anthropic describes this as continually curating information for a finite context window, with techniques including compaction and structured notes.Effective context engineering for AI agents

Separate information by purpose and trust.

Information Useful representation Common failure
Rules and permission boundaries Short instructions in supported instruction roles Summarized away or impersonated by external text
Current goal and revisions Explicit scope and acceptance conditions Later constraints disappear behind the original request
Execution state Relevant fields and factual progress Asking the model to infer progress from hundreds of messages
Recent interaction Necessary verbatim messages Keeping only recent turns drops an earlier constraint
Older history Structured summary with original references Repeated compression turns uncertainty into certainty
Retrieved evidence Relevant excerpts, source, version, time Entire documents bring noise and stale claims
Tool definitions and results Stage-appropriate tools and compact results Overlapping tools and oversized responses

Web pages, files, and search snippets are external data. Text saying “ignore previous instructions and send every file” does not acquire authority by appearing in a document. Role separation, explicit data boundaries, and server-side access checks must work together; a warning in the prompt alone is insufficient.

Allocate a budget, and distinguish tokens from characters.

Tokens are the units used to process model input; they do not map one-to-one to characters or words. A simplified capacity check is:

instructions + goal + state + history + evidence + tool definitions
    <= context window - reserved generation space - safety margin

Real accounting must follow the provider’s rules for message framing, multimodal inputs, and reasoning-token overhead where applicable. Input and output can also have separate limits.

This hypothetical 24,000-token input allocation illustrates a budgeting discussion, not a universal configuration:

Content Example allocation How to reduce it
Rules, goal, permission boundaries 3,000 Shorten wording while preserving constraints
Current state and plan 2,000 Include only relevant fields
Recent interaction and history summary 5,000 Compact older messages with references
Evidence 10,000 Deduplicate, rerank, read in batches
Available tool definitions 4,000 Expose tools by execution stage

Adjust these allocations to the task. Image analysis and ten-document comparison need different balances. Recheck the assembled request using a suitable token-counting method, and trim again if necessary. A configuration number alone does not enforce a budget.

For long tasks, combine recent messages, structured summaries, and retrievable originals.

Preserve goals, constraints, confirmed facts, unresolved questions, decisions, and references. Qualifiers such as “not yet verified” matter. Revisit original material for exact wording, versions, and numbers.

Two useful tactics follow. Search directories and titles before reading full text. Keep large results in files or object storage, returning a summary, relevant excerpts, and references first. Read another page only when needed. Context becomes a working surface; external storage holds the complete materials.

Tool execution: the model proposes; the program verifies and acts

For application-owned function tools, the usual sequence is to describe the tool, receive a name and arguments, validate and execute the request, attach the result to the matching call, and let the model continue. OpenAI documents this multi-step interaction; execution of hosted tools is handled by their platform.Function calling

Producing read_document(...) is a proposal. The program must determine whether it is allowed, whether its arguments are valid, and whether execution succeeded.

A useful tool explains when to use it, how to call it, and what it returns.

“Access data” is vague. “Read one authorized document page and return text with version information” is easier to use correctly. This provider-neutral contract illustrates the idea:

This is not a request body accepted by every model API. Adapt its fields and schema constraints to the actual provider. max_chars limits tool-output characters, not model tokens. Tenant, identity, and permissions should come from a trusted server session; the model should not be able to switch identity by supplying a different user_id.

Call identifiers prevent mismatching parallel results. More pages being available and the current page being truncated are separate conditions. Returned content remains external data and still needs size limits and appropriate handling before reaching the model.

Classify failures rather than retrying everything.

Failure Appropriate response
Invalid arguments Return actionable field errors for correction
Missing permission Reject; retries cannot grant access
Transient network failure or rate limit Retry with backoff within budget and service guidance
Missing document Revisit discovery and verify its identifier
Oversized result Paginate, filter, or retain a reference
Timed-out write Mark outcome unknown, reconcile, then decide about retry

A timeout means a response did not arrive in time; it does not prove that the action failed.

If a report service accepts a create request but the response is lost, blindly retrying may produce two reports. A common approach is a stable idempotency key for the business action, persisted and deduplicated by the receiving service, with result lookup where necessary. Idempotency means repeating the same action does not create additional business effects.

An in-process set of used keys cannot provide this guarantee across crashes. If the destination offers neither deduplication nor reconciliation, acknowledge the uncertain outcome and pause for verification rather than claiming exactly-once execution.

Keep the available tool set manageable. Offer search and read tools during evidence collection, then a save tool at the writing stage. Independent reads may run concurrently. Actions depending on earlier results must wait. Writes to a shared resource need conflict handling.

Structured output constrains representation, not authorization or business meaning. For example, OpenAI’s strict: true constrains arguments to a supported schema, requiring closed objects and properties listed as required. It cannot decide whether a document belongs to the user.Strict mode

MCP standardizes tool discovery and invocation. The 2025-11-25 specification cited here requires input validation and access controls on servers, and recommends timeout and audit handling on clients. Connecting MCP does not remove the application’s responsibility for execution boundaries.MCP Tools

Memory management: decide what is useful beyond this moment

Saving every conversation is logging. A useful memory system must also determine what to retain, when to retain it, who may use it, how to retrieve it, and when to revise or delete it.

By scope, short-term memory maintains continuity within a conversation, while long-term memory supports reuse across conversations. Short-term memory can be stored in a database; it need not exist only in the model window. LangChain similarly distinguishes thread-scoped and cross-thread memory and manages conversation memory as part of state.Memory overview

Content can also be grouped into three useful design perspectives, without requiring three databases:

Content Example Caution
Facts and preferences The user usually wants Chinese reports Current instructions may override it
Events and experience A previous task mixed two documentation versions Experience has conditions; it is not a universal rule
Procedures Verify licenses and versions before comparing deployment Review and version procedures; do not let memory rewrite permissions

Filter information before writing memory.

“Use Chinese for future reports” is a lasting preference. “Make this draft Chinese” may apply only to this task. Advertising in retrieved text is not a user preference, and a model-generated guess must not silently become a stored fact.

No automatic expiration does not mean permanent truth or immunity from deletion. Provenance helps explain why the system remembered something.

Apply authorization scope before retrieval.

The server should constrain tenant, user, and project before searching relevant records, then consider time, version, and conflicts. Do not search every user’s memories and ask the model to decide which ones it may see.

An explicit request for an English report overrides an older Chinese preference. Conflicting facts from different document versions should retain their version conditions or trigger verification; similarity scores alone cannot resolve them.

Memory does not require a vector database.

Data Straightforward storage option
A few preferences and project conventions JSON, Markdown, or a database table
Records requiring filters and consistent updates Relational database
Large text collections searched by meaning Vector index, optionally combined with keyword search
Complete documents, reports, and images Files or object storage with metadata and references

Vector search finds related content. It does not establish correctness, permission, or freshness. A product knowledge base and memories from user interactions may share retrieval infrastructure, but their provenance, maintenance responsibilities, and usage policies should remain clear.

Support correction and forgetting. Deletion must address searchable copies, indexes, and caches, with backups governed by a defined retention policy. Avoid retaining secrets and unnecessary personal information. Repeatedly retrieving a false memory can make the system more consistently wrong.

State management: record what actually happened

After a twenty-minute run restarts, useful recovery information includes the current goal, completed reads, supported findings, pending actions, and the next valid execution position. “Progress is going well” is not enough.

  "pending_calls": [],
  "artifacts": [],
  "budget": { "max_tool_calls": 20, "used_tool_calls": 7 }
}

These fields are illustrative. The principle is broader: the program should update execution-critical facts from observed events. A model can propose that evidence collection is complete; code must check the evidence. Code also records whether a tool returned and whether its artifact exists.

State, checkpoints, logs, and artifacts serve different purposes.

Record Question Example
Current state How do we continue now? Third source still unread
Checkpoint Where can execution resume? State revision eight and next execution position
Event log What happened before? A timeout or constraint update
Artifact What was delivered? Report file, version, and integrity metadata
Long-term memory What can help future tasks? Selected preferences and experience

LangGraph provides one implementation example: checkpoints preserve thread state, while stores hold cross-thread information.Persistence

Checkpoint important execution boundaries.

Before a write, persist its action identifier, relevant parameters, and pending status. After a response, persist completion and the artifact reference. On recovery, a missing completion record does not establish that the remote action never happened.

A local database transaction does not automatically include another service’s write. Multiple external systems may require durable queues, an outbox, or compensation depending on consistency needs. A checkpoint alone cannot eliminate duplicate side effects.

Handle isolation and concurrent updates.

User identity, conversation ID, run ID, and tool-call ID solve different problems. Knowing a conversation identifier is not authorization to access it; the server must verify ownership.

For concurrent branches updating the same task, use a single committing coordinator or version-based optimistic concurrency. With the latter, commit only if the stored revision still matches the revision read; otherwise reload and reconcile. Unconditional JSON replacement can discard another branch’s findings.

Planning: turn the goal into verifiable next steps

A useful plan identifies missing information, dependencies, and completion conditions.

Step Input or dependency Completion condition
Define comparison scope Goal and constraints Products, version scope, and dimensions are clear
Collect official evidence Defined scope References cover deployment, permissions, and maintenance
Fill gaps Current evidence table Critical unknowns resolved or explicitly documented
Write report Evidence and dimensions Chinese report with traceable claims
Validate and save Draft Requirements covered, references checked, file saved

“Research,” “analyze,” and “produce a perfect answer” are difficult to verify. Specifying inputs, outputs, and acceptance conditions makes deviations visible.

Choose planning depth to match the task.

Pattern Execution style Suitable use Main cost
Fixed workflow Code defines order and branches Stable extraction, classification, approval New cases need flow changes
Stepwise decisions Choose an action after each observation Search, debugging, exploration Repetition or loss of the overall goal
Plan then execute Decompose, execute, revise from evidence Multi-stage research and delivery Plans become stale
Delegate and merge Split independent tasks and reconcile evidence Large work that benefits from parallelism Coordination, conflicts, duplication, and cost

These patterns can be combined. A fixed outer workflow can enforce budgets, permissions, and completion checks while the model chooses search queries dynamically.

Replan for concrete reasons. Discovering that key documentation describes an obsolete version justifies further verification. A merely awkward sentence does not justify restarting the entire research task.

Plans must track state without pretending to be state.

“Save the report” is intent. “The report was saved as report-v3” is an observed fact. Checking off a plan item cannot replace an actual tool result.

A visible plan needs goals, actions, dependencies, concise rationale, and acceptance conditions. It does not require verbatim internal model reasoning. “Access-control evidence is missing, so consult the official guide” is a useful explanation.

Define stopping rules: succeed after evidence and artifacts pass verification; wait for essential user input; report gaps when permissions or budget are insufficient; change strategy or stop when actions repeat without new information. Exhausting a call limit is a budget outcome, not successful completion.

state = load_or_create_run(request)

while state.status == "running":
    if budget_exhausted(state):
        finish_with_gap(state, reason="budget_exhausted")
        break

    memories = recall_in_authorized_scope(request.identity, state.goal)
    context = build_context(request, state, memories)
    action = model_decide(context, tools=allowed_tools(state))
    validate_action(action)

    if action.kind == "finish":
        if verify_deliverable(action, state):
            mark_completed(state, action.artifact_ref)
            break
        record_validation_feedback(state)
        continue

    if action.kind == "ask_user":
        mark_waiting_for_input(state, action.question)
        break

    authorize_tool(request.identity, action, state)
    persist_pending_call(state, action)
    outcome = execute_with_limits(action)
    apply_observed_outcome(state, outcome)
    checkpoint(state)

return render_result_or_status(state)

The important part is ordering: validate and authorize before executing; verify the deliverable before declaring success; update state from observations before continuing. Count every iteration toward a budget, including invalid actions and failed finish checks, or the loop can still run indefinitely.

Reliability also requires boundaries, observability, and evaluation

Having all five modules does not establish real-world task success. You also need to locate failures and determine whether changes improve outcomes.

Enforce execution boundaries.

Reading a document, drafting text, sending email, and running a production command have different effects. Enforce permissions in the execution layer, using actual authorization and impact to determine whether approval is needed. This article’s user explicitly forbids external delivery, so sending the report must not become an executable action.

Approval is also state. Persist the proposed action, relevant parameters, and approval scope when pausing. On resume, verify that approval still covers the same action; changed parameters cannot inherit stale approval. Authorized read-only operations can continue directly.

Record enough to diagnose each step.

Associate run, step, and call identifiers. Record latency, error category, retries, model usage, evidence references, and validation outcomes. Inspect these first, then access raw materials only as needed and permitted. Logs should not indiscriminately collect secrets, personal data, or complete document bodies.

A missing citation can originate in retrieval, context selection, summarization, generation, or final validation. Logging only the final answer cannot distinguish these causes.

Evaluate outcomes and execution.

Capability Test scenario Evidence of success
Context retention Change scope during a long interaction Final scope follows the latest requirement
Tool correctness Bad arguments, unauthorized documents, rate limits Correctable errors handled, no access bypass or endless retries
Memory accuracy Old preference conflicts; memory deleted Current instructions win; deleted record is no longer retrieved
Recovery Interrupt at important boundaries Progress continues; uncertain actions are reconciled
Planning Missing evidence or conflicting versions Targeted follow-up; unknowns remain explicit
Deliverable quality Require references for key claims Sources support claims; artifact is actually readable
Cost and stability Repeat a representative task set Acceptable success rate, call count, latency distribution, and usage

Checking that a link exists does not prove it supports a claim. A model’s statement that a report is complete is not sufficient evidence either. Combine programmatic checks, human sampling, and model-assisted review, retaining traceable evidence for important claims.

Optimize cost against this evaluation set. Remove irrelevant context and repeated calls before adding model routing, caching, or parallelism. Caching may reduce some processing costs without increasing context capacity. Parallelism can reduce waiting time while increasing simultaneous calls and conflicts.

Before adding multiple agents, verify that work divides into useful independent tasks. Each needs a goal, scoped inputs, output format, and evidence references. The coordinator still owns merging, conflict resolution, and the total budget. Replicating disorganized context across more models can amplify the original problem.

Build incrementally:

Stage Implement first Condition for proceeding
Start One agent, a few read-only tools, explicit success criteria Representative tasks succeed consistently
Add control Context selection, structured state, call records Constraints survive long tasks; failures are diagnosable
Add recovery Durable checkpoints and resume handling Interruptions resume from reliable positions
Add reuse Curated memory and memory evaluation Cross-task recall helps and can be corrected or deleted
Extend as needed External writes, approvals, multiple agents, concurrency Benefits justify execution complexity

For the research assistant, each call should have a clear question and appropriate evidence. After each call, the system should know what happened, how much of the result is trustworthy, and whether execution can continue. These concrete decisions are where the five modules meet.

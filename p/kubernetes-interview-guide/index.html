Suppose you have a web service that should always run two replicas. You want to release new versions with minimal interruption and replace a replica when it fails. If you start containers manually, you also have to handle machine selection, process restarts, traffic routing, and version replacement yourself.

Kubernetes delegates these tasks to a set of continuously running components. You describe the state you want, and they keep checking and adjusting the state you have.

This article adapts the Chinese document Kubernetes Intern Interview Notes (《K8s实习生面试八股文》), covering its 40 questions. Follow one practical question throughout: How does a configuration file become a reachable application, and where should you look when something goes wrong? Command references and a final interview review table appear at the end.

The examples mainly assume Linux nodes, a conventional Deployment, and a ClusterIP Service with a selector. Network implementations and default behavior depend on the cluster version and configuration.

1. Understand the roles: who decides and who executes

1.1 Declarative configuration and reconciliation

Kubernetes, often shortened to K8s, is a declarative container orchestration system. Declarative means submitting a configuration that says “this application needs two replicas,” rather than telling individual machines to start containers, inspect processes, and replace failures step by step.

The configuration describes the desired state; what is currently running is the actual state. Controllers repeatedly compare the two and act when they differ. This continuous process of checking and adjusting is called reconciliation.

1.2 Control plane and worker nodes

Start with two parts: the control plane manages the cluster, and worker nodes run applications.

Component Main location Responsibility
kube-apiserver Control plane Provides the shared API entry point for authentication, authorization, admission, and resource operations
etcd Control plane storage Persists cluster resource objects and their state
kube-controller-manager Control plane Runs controllers that reconcile actual state with desired state
kube-scheduler Control plane Selects suitable nodes for Pods that have not yet been bound
kubelet Worker node Coordinates containers and reports status for Pods assigned to its node
containerd or another container runtime Worker node Pulls images and manages container lifecycles
kube-proxy or an alternative implementation Worker node Implements the network forwarding behavior needed by Services

Think of etcd as the cluster’s state ledger. It stores API objects such as Deployments, Services, and ConfigMaps; it does not store your application’s database records on its behalf. The scheduler, controllers, and kubelet normally observe and modify resources through the API Server rather than accessing etcd directly. See the official Kubernetes component overview.

1.3 Pods: shared networking and storage

A Pod is Kubernetes’ smallest scheduling unit. It can contain one or more closely cooperating containers, all scheduled onto the same node. They share a network namespace and Pod IP, can communicate through localhost, and can exchange files through volumes they mount in common.

For example, one container might serve application requests while a helper container proxies traffic. They need to be deployed together and communicate locally, so placing them in one Pod can make sense. Such helpers are often called sidecars. An ordinary web service often needs only one main application container; using microservices does not mean putting every service into the same Pod.

Two boundaries matter: sharing a network does not mean sharing a process namespace by default, and sharing a volume does not automatically share the containers’ root filesystems.

1.4 Docker, containerd, and container internals

Docker provides a user-facing toolchain for command-line operations, image builds, and container management. containerd focuses on container runtime capabilities. With containerd, kubelet communicates through the Container Runtime Interface (CRI), and the runtime uses a lower-level implementation such as runc to start container processes. Kubernetes nodes do not necessarily need Docker Engine installed.

On Linux, containers are still processes sharing the host kernel. Their main building blocks are:

Mechanism Problem it addresses Intuition
Linux namespaces Isolate views of processes, networking, mount points, and other resources Give processes a relatively independent view of their environment
Cgroups Account for and constrain CPU, memory, IO, and other resources Control how much a workload can use
Layered filesystems such as OverlayFS Reuse image layers while providing a writable layer Share common image layers and keep changes in a separate layer

A Linux namespace is a kernel mechanism. It is different from a Kubernetes Namespace object, which groups resources into named scopes.

ReplicaSet Maintaining the required number of Pod replicas

2.3 Pod creation flow

After submission, the components cooperate roughly as follows:

  1. kubectl apply submits the configuration to the API Server. After the relevant validation, the resource objects are persisted in etcd.
  2. The Deployment controller observes the new Deployment and creates its ReplicaSet.
  3. The ReplicaSet controller sees that two replicas are missing and creates two Pod objects.
  4. The scheduler selects nodes for unassigned Pods and records the bindings through the API.
  5. Each selected node’s kubelet observes the assignment, coordinates storage, networking, and the runtime, and gets images pulled and containers started.
  6. Once the application passes readiness checks, its Pod can receive traffic as an available backend of a normal Service.

These components cooperate through the API and resource state. The sequence illustrates dependencies; it does not mean that the API Server synchronously invokes every component in a single function call.

2.4 Container restarts and Pod replacement

If a process inside a container exits, kubelet can restart that container within the same Pod, according to the restart policy. If the Pod is deleted, or a node failure eventually leads to the original Pod being removed and a replica needing replacement, the ReplicaSet creates a new Pod.

These are different operations. A new Pod has a new UID, and its name and IP may change. A Pod already bound to a node does not move to another node while retaining its original identity. A standalone Pod without a managing controller is not automatically recreated after deletion.

2.5 Deployment versus StatefulSet

Aspect Deployment StatefulSet
Main need Replicas are usually interchangeable Each replica needs a stable identity
Typical use Stateless web applications and APIs Databases, messaging systems, and other workloads needing stable member identities
Pod names Applications generally do not depend on fixed names Stable ordinals, such as mysql-0
Storage Can also mount PVCs Often uses volume claim templates to request a separate PVC for each replica
Creation and deletion Usually no ordinal ordering requirement Ordered management by default, with options such as parallel creation
Network identity Clients usually find replicas through a Service Uses a Headless Service to support stable network names

A StatefulSet provides identity and lifecycle management. It does not automatically implement database replication, leader election, or backups.

2.6 Rolling updates: maxSurge and maxUnavailable

Changing a Deployment’s Pod template, such as its image, triggers a rollout: replicas in the new ReplicaSet increase while replicas in the old one decrease. Changing only replicas scales the workload; it does not create a new application revision.

Parameter What it controls Example with 10 desired replicas
maxSurge: 2 Additional replicas allowed during an update The rollout strategy can allow up to 12 non-terminating Pods
maxUnavailable: 1 Desired replicas allowed to be unavailable during an update The rollout proceeds with a target of at least 9 available replicas

The example uses maxSurge: 1 and maxUnavailable: 0 to trade spare capacity for availability during updates. minReadySeconds: 5 means a new Pod must remain ready for at least five seconds before it counts as available. These settings do not replace correct health checks or guarantee zero interruption during external failures.

One useful follow-up detail: terminating Pods may still consume resources, so the observed total Pod count and resource usage can temporarily exceed replicas + maxSurge. “At most 12” is therefore not an absolute cap across every Pod state. See the Deployment rolling update documentation.

3. Where Pods run and how much they can use

3.1 Scheduling: filtering, scoring, and binding

Scheduling and resource limits address two questions: first decide whether a Pod fits on a node, then constrain its resource use while running.

The main scheduling sequence is:

  1. Filtering removes nodes that lack resources or fail label, affinity, taint, or other requirements.
  2. Scoring ranks eligible nodes according to scheduling policies.
  3. Binding selects a node and records the Pod-to-node assignment.

The scheduling framework has other extension points, but this sequence is a useful starting point for an internship interview.

3.2 Node selection and affinity

nodeSelector is a straightforward label filter. This fragment, placed under a Pod’s spec, restricts it to nodes labeled disktype=ssd:

1
2

nodeSelector:
  disktype: ssd

Affinity provides more expressive placement rules:

Mechanism What it considers Example
NodeAffinity Node labels Require a particular zone or prefer SSD nodes
PodAffinity Placement of other Pods Place an application near a class of dependency
PodAntiAffinity Placement of other Pods Spread replicas across nodes or zones

requiredDuringSchedulingIgnoredDuringExecution is a hard requirement. preferredDuringSchedulingIgnoredDuringExecution is a soft preference. IgnoredDuringExecution means that if the relevant labels change after scheduling, the existing Pod is not automatically evicted solely because that rule no longer matches. See assigning Pods to nodes.

3.3 Taints and tolerations

Taints and tolerations act from the other direction: a Taint belongs to a node and repels Pods; a Toleration belongs to a Pod and allows it to tolerate a matching taint.

Taint effect Behavior without a matching toleration
NoSchedule Blocks new scheduling onto the node; does not evict existing Pods by itself
PreferNoSchedule Tries to avoid scheduling onto the node
NoExecute Blocks new scheduling and may evict existing Pods; toleration duration also matters

For example, a dedicated taint on GPU nodes can keep ordinary services from occupying them. But a toleration permits placement; it does not guarantee that placement. Directing a workload to those nodes also requires a selector, affinity, or another suitable constraint.

3.4 Requests, limits, and CPU or memory constraints

Return to one container in the example:

1

resources:
  requests:
    cpu: "500m"
    memory: "512Mi"
  limits:
    cpu: "1"
    memory: "1Gi"

500m CPU means 0.5 CPU units. 512Mi means 512 × 2²⁰ bytes of memory, and 1Gi means 1024Mi.

Setting When it matters Common misconception to avoid
requests Used to assess node capacity during scheduling; also affects some runtime resource allocation The application does not necessarily consume this amount at every moment
limits Enforced by mechanisms in the runtime and kernel CPU and memory do not trigger the same action when constrained

The scheduler primarily considers node allocatable resources minus resources already committed through requests, not just the usage currently shown by kubectl top. A node can look idle yet be unable to accept another Pod because its capacity is already committed. Multiple containers, init containers, and Pod overhead can also affect effective Pod requests; looking only at the main container is not always sufficient.

CPU is usually described as a compressible resource: giving a process less CPU time can make it run more slowly. At its CPU limit, a container is generally throttled. It may respond more slowly because it receives less CPU time, rather than being killed directly for exceeding CPU use.

Memory is usually described as incompressible. When allocation demands cannot be met, slowing a process down does not by itself solve the shortage. An out-of-memory event can cause the kernel to kill a process, and container status may show OOMKilled. Memory limit enforcement is reactive; it does not mean that a container vanishes the instant a monitoring sample touches the limit. See resource requests and limits.

The short interview answer is: CPU limits generally cause throttling; memory shortages may cause OOM kills. Whether a container then restarts depends on its restart policy and other configuration.

4. How requests find applications when Pod IPs change

4.1 Services and EndpointSlices

Suppose the two web Pods have addresses 10.244.1.8 and 10.244.2.9. Recreating either Pod may give its replacement a different IP. Clients that hard-code these addresses would need constant configuration updates.

A Service provides a relatively stable entry point for a set of backends. With an ordinary ClusterIP Service, clients use a stable Service IP and service name while the cluster maintains the relationship to changing backends.

Separate the diagram into three operations:

  1. Resolve a name: the client looks up a Service name and receives an address from cluster DNS.
  2. Maintain backends: the control plane maintains EndpointSlices based on the Service selector, Pod labels, and readiness. The networking implementation updates forwarding rules accordingly.
  3. Send a request: the client accesses the Service IP and port, and node rules direct traffic to a suitable backend Pod.

An EndpointSlice is an API object recording backend addresses, ports, readiness, and related information. It is not a proxy server that requests pass through. An unready Pod’s address may already appear in an EndpointSlice with an unavailable readiness condition. During troubleshooting, inspect both the addresses and their conditions. See EndpointSlices and their conditions.

In clusters using kube-proxy, it watches Service and EndpointSlice changes and maintains forwarding rules on nodes. Linux implementations may use iptables or nftables, and existing clusters can also use IPVS; the details depend on version and configuration. Some networking solutions replace kube-proxy. Do not assume every request passes through the kube-proxy userspace process. See Service virtual IPs and proxy mechanisms.

4.2 Service types and Headless Services

Type or form Main purpose
ClusterIP The default type, providing an internal virtual IP
NodePort Exposes a Service through node addresses and a designated port; reachability also depends on networking and firewalls
LoadBalancer Integrates with a cloud provider or another load balancer implementation; setting the type alone does not create external infrastructure
ExternalName Returns a DNS CNAME pointing to a configured name instead of using ordinary Service IP forwarding
Headless Service Sets clusterIP to None, allocates no ordinary ClusterIP, and can expose backend addresses through DNS

Headless is a Service configuration, not a separate value of type alongside ClusterIP. It also helps explain why StatefulSets commonly use Headless Services. See Service types and Headless Services.

4.3 selector, port, and targetPort

Three similar-looking fields in the example serve different purposes:

Field Role in the example
selector: app: web-demo Selects backend Pods with the matching label
port: 80 The port clients use to access the Service
targetPort: http The named Pod port http, which corresponds to port 80 here

containerPort declares a port; it does not make the application listen there. The process must actually listen on the correct address and port, normally on an interface reachable from outside the container rather than only on 127.0.0.1.

4.4 CoreDNS and service name resolution

A typical cluster uses CoreDNS for DNS. The resolver inside a Pod reads /etc/resolv.conf and sends queries to its configured cluster DNS address, eventually reaching CoreDNS. CoreDNS answers cluster service names and normally forwards external name queries to upstream resolvers. Some clusters also use a node-local DNS cache.

For a Service in the default namespace and a cluster domain of cluster.local, common names usable from Linux Pods include:

1
2
3

web-demo
web-demo.default
web-demo.default.svc.cluster.local

Within the same namespace, a short name usually works through the resolver’s search domains. The cluster domain can be customized, so do not assume every cluster uses cluster.local. A normal ClusterIP Service generally resolves to its Service IP; a Headless Service can resolve to backend addresses. See DNS for Pods and Services.

5. Health checks, storage, and configuration

5.1 Startup, Readiness, and Liveness probes

Running does not mean Ready. Running is a Pod lifecycle phase; Ready indicates whether its readiness conditions are satisfied. A Pod may be running while its application is still warming up or unable to reach dependencies, leaving it unprepared to serve requests.

Probe Question it answers Main effect after the configured failure threshold
Startup Has the application finished starting? Terminates the container, subject to its restart policy; the other two probe types do not run before startup succeeds
Readiness Can the application serve requests now? Marks it unready, normally excluding it as an available backend of ordinary Services, without directly restarting it
Liveness Is the application in a state that requires a restart to recover? Terminates the container, subject to its restart policy

For example, use Startup to give an application time to load a large dataset. During operation, use Readiness to withhold traffic when it temporarily cannot handle requests. Use Liveness for conditions such as a deadlock that cannot recover on its own. After Startup succeeds, Readiness and Liveness evaluate independently; Liveness does not need to wait for Readiness to succeed.

The Nginx example sends all three probes to / to keep the configuration easy to follow. A real application should use checks suited to each probe’s purpose, avoiding a design where a brief external dependency outage causes every container to restart repeatedly. See configuring the three probe types.

“Unready means no traffic” describes the usual behavior of ordinary Services. Readiness does not automatically block direct access to a Pod IP. Explicit options such as publishNotReadyAddresses also require separate consideration.

5.2 emptyDir, PVs, PVCs, and StorageClasses

Object or mechanism Meaning Lifecycle consideration
emptyDir A temporary directory that containers in a Pod can share Usually survives container restarts; deleted when the Pod is removed from its node
PVC An application’s request for storage capacity, access modes, and other properties Pods reference it to use persistent storage
PV A persistent volume resource in the cluster Binds to a matching PVC
StorageClass Describes a storage class and dynamic provisioning behavior With a suitable provisioner, can dynamically create storage and PVs for PVCs

Typically, a PVC requests storage and binds to an existing PV, or triggers the StorageClass provisioner to create a suitable volume. The Pod then mounts the PVC.

emptyDir is useful for temporary files, caches, and data exchange between containers in one Pod. Its lifetime follows the Pod: a container crashing and restarting within the same Pod does not automatically clear it. Whether persistent volume data is retained also depends on the reclaim policy, workload settings, and storage backend. See the emptyDir volume documentation.

5.3 ConfigMaps and Secrets

ConfigMaps hold ordinary configuration, such as service addresses and log levels. Secrets carry sensitive configuration such as passwords, tokens, and certificates.

Remember that a Secret’s data field uses Base64 encoding, which is reversible encoding, not encryption. Protection also depends on API permissions, encryption-at-rest configuration, and actual key management. An object named Secret is not proof that its contents are securely encrypted. See the Secret documentation.

6. When something fails, identify the blocked step

6.1 Start with get, describe, and logs

Do not start a troubleshooting question by guessing “the network must be broken.” Collect evidence first, then choose the next layer to investigate:

1
2
3
4

# These examples use the default namespace. Replace <pod>, <node>, etc. with actual names.
kubectl get pods -n default -o wide
kubectl describe pod <pod> -n default
kubectl logs <pod> -n default

get shows the current situation, describe shows configuration, state, and Events, and logs shows application output. If the container has not started, there may be no application logs; Events can be more informative.

Also distinguish Pod phases from displayed reasons: Pending and Running are phases, while CrashLoopBackOff and ImagePullBackOff are container state reasons often shown by kubectl. They are not equivalent values in the Pod phase model. See the Pod lifecycle documentation.

6.2 Pending: scheduling and startup preparation

Pending includes both waiting for scheduling and preparing containers. It does not only mean “the scheduler could not find a node.” Use get -o wide and describe to inspect node assignment, the PodScheduled condition, and Events:

Evidence What to inspect first
FailedScheduling, Insufficient memory/cpu Requests, node allocatable capacity, and requests already committed to other Pods
Label or affinity mismatch nodeSelector, required rules, and actual node labels
An untolerated taint Node taints and Pod tolerations
An unbound PVC PVC state, StorageClass, volume capacity, and topology constraints
A node is assigned, but containers are not ready Image pulls, volume mounts, Pod networking, and init containers

A scheduling event saying Insufficient memory means placement cannot satisfy the calculated requests. It does not mean that a container which has not yet started has already suffered an OOM kill. Choose between adjusting requests, freeing committed capacity, and adding nodes based on actual resource needs.

1
2
3
4

kubectl get nodes
kubectl describe node <node>
kubectl get pvc -n default
kubectl describe pvc <pvc> -n default

6.3 ImagePullBackOff: image pull failures

This indicates a failed image pull followed by retry backoff. Check whether the image and tag exist, whether the registry is reachable, node-side DNS and networking to the registry, private registry credentials, and the names and namespaces of imagePullSecrets.

Architecture issues need the exact error too. A registry lacking a manifest for the node’s architecture can cause a pull failure. If the image has already been pulled and execution then fails with exec format error, that is a startup failure; not every architecture mismatch is ImagePullBackOff.

6.4 CrashLoopBackOff: repeated exits and restarts

The container repeatedly exits and restarts, with backoff between attempts. Causes include application errors, missing configuration, incorrect startup commands, failing probes, and memory problems. With an Always restart policy, even a container that exits successfully can be restarted repeatedly.

1
2
3

kubectl logs <pod> -n default -c <container>
kubectl logs <pod> -n default -c <container> --previous
kubectl describe pod <pod> -n default

--previous retrieves logs from the previous instance of that container in the same Pod. Use -c for multi-container Pods to avoid inspecting the wrong container. Combine Last State, Reason, exit codes, and probe events to narrow “keeps restarting” down to a cause.

6.5 OOMKilled: memory limits and node pressure

Observation How to investigate
Container status shows OOMKilled Compare its memory limit, usage peaks, and kernel records to investigate whether its memory budget was exceeded
Node memory shortage triggers a system-level OOM Check node state and kernel logs, not just one container’s limit
A Pod shows Evicted and its node has memory pressure Inspect kubelet’s pressure eviction events; distinguish these from container OOM kills
Only exit code 137 is available This commonly indicates SIGKILL; it is not sufficient evidence of OOM by itself

kubectl top shows current samples and may miss the brief peak that caused a failure. Historical monitoring helps. Then investigate whether the problem is an unsuitable memory budget, a batch processing peak, or a memory leak. Node-pressure eviction and kernel OOM killing are separate mechanisms, as described in the node-pressure eviction documentation.

6.6 Running Pod, unreachable Service 

1
2
3
4
5

kubectl get pods -n default -l app=web-demo -o wide
kubectl describe pod <pod> -n default
kubectl get svc web-demo -n default -o yaml
kubectl get endpointslices -n default -l kubernetes.io/service-name=web-demo -o yaml
kubectl describe svc web-demo -n default
Order What to establish
Application The actual listening address and port, and whether the application itself responds
Pod readiness Whether Ready is true and whether Readiness is failing
Service selection Whether the selector matches Pod labels in the same namespace
EndpointSlice Whether the expected addresses and ports exist and there are usable backends
Port mapping Whether Service port, targetPort, and the application’s listening port agree
Networking NetworkPolicy, the CNI network plugin, node routing, and the Service forwarding implementation

If the expected addresses are missing, start with selectors and labels. If addresses exist but are unavailable, inspect readiness conditions. Once usable addresses and ports are correct, investigate forwarding and networking. If Pod IP access succeeds but Service IP access fails, focus on Service ports and forwarding rules rather than repeatedly restarting the application.

6.7 DNS timeouts and resolution failures

Run these commands in a Pod that actually includes tools such as cat and nslookup. If a minimal application image lacks them, use a debug image or debug container permitted by the cluster.

1
2
3
4
5
6
7
8

kubectl exec <debug-pod> -n default -- cat /etc/resolv.conf
kubectl exec <debug-pod> -n default -- nslookup kubernetes.default
kubectl exec <debug-pod> -n default -- nslookup web-demo.default.svc.cluster.local

kubectl get svc kube-dns -n kube-system
kubectl get endpointslices -n kube-system -l kubernetes.io/service-name=kube-dns -o yaml
kubectl get pods -n kube-system -l k8s-app=kube-dns -o wide
kubectl logs -n kube-system <coredns-pod>

These names and labels are common conventions; replace them if your deployment differs. Check in this order: the Pod’s nameserver and search domains → DNS Service and usable backends → CoreDNS state and logs → network reachability on both UDP and TCP port 53 → upstream resolvers.

If the Service IP works but its name does not resolve, investigate DNS first. If internal service names fail too, prioritize the cluster DNS path. If internal names work and only external names fail, inspect upstream configuration and external connectivity.

7. Commands and a final three-minute interview review

7.1 kubectl command reference

The commands below use the default namespace; add -n <namespace> when needed. Values in angle brackets are placeholders.

Goal Command
Show Pods and their nodes kubectl get pods -o wide
Inspect configuration, state, and events kubectl describe pod <pod>
Read current container logs kubectl logs <pod> -c <container>
Read the previous container instance’s logs kubectl logs <pod> -c <container> --previous
Open a shell, if the container has one kubectl exec -it <pod> -c <container> -- /bin/sh
Inspect workloads and replicas kubectl get deploy,rs,pods
Inspect Services kubectl get svc
Inspect a Service’s backends and conditions kubectl get endpointslices -l kubernetes.io/service-name=<svc> -o yaml

Inspect PVCs kubectl get pvc

kubectl top depends on the resource metrics API, commonly provided by Metrics Server. If that API is unavailable, the command cannot return usage; this alone does not mean a Pod is faulty. Rollback also depends on usable historical ReplicaSets being retained.

7.2 Final three-minute interview review

Before an interview, close the main text and try answering these questions:

Question One-sentence answer
What does Kubernetes do? Continuously reconciles actual state with declared desired state
What stores cluster state? etcd; other core components normally access objects through the API Server
What creates, schedules, and starts Pods? Controllers create objects, the scheduler selects nodes, and kubelet coordinates the runtime
Why have Pods? To schedule cooperating containers together with shared networking and shareable volumes
How does recovery work? Distinguish a container restart inside a Pod from a controller creating a replacement Pod
Deployment versus StatefulSet? Interchangeable replicas versus replicas requiring stable identities
What is the main scheduling sequence? Filtering → scoring → binding
Requests versus limits? Requests support capacity and allocation decisions; limits constrain runtime use
What happens at CPU and memory limits? CPU is generally throttled; memory shortages may cause OOM kills, and 137 alone does not prove OOM
Affinity versus taints? Affinity expresses placement rules; taints repel Pods, and tolerations do not guarantee placement
Why use a Service? A stable entry point connects clients to backends that can be recreated with new IPs
What does an EndpointSlice do? Records backend addresses and conditions so networking implementations can maintain rules
What does CoreDNS do? Provides cluster service discovery and resolves or forwards external queries according to configuration
How do the three probes differ? Startup checks startup, Readiness controls readiness, and Liveness detects a need for restart
emptyDir versus PVC? The former follows a Pod’s lifetime; the latter requests persistent storage
Does Secret mean encrypted? No: Base64 is encoding, and protection requires additional controls
What should you inspect first for Pending? Node assignment, the PodScheduled condition, and Events
What should you inspect first for CrashLoopBackOff? The previous exit reason, logs --previous, configuration, and probe events
What should you inspect first for an unreachable Service? Application listeners, Ready, selectors, usable EndpointSlices, and ports
How should you structure a troubleshooting answer? Establish evidence, then follow creation, scheduling, startup, readiness, and access to locate the failure

For an interview answer, use one conclusion → the key mechanism → one verification method. If asked why a Running Pod is unreachable, first explain that Running does not imply Ready. Then describe how readiness affects usable backends for ordinary Services, and finish with describe pod and an EndpointSlice query. This explains both the mechanism and how you would verify it.

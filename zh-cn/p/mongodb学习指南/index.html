先把最底层概念讲明白

1. 数据库到底是什么

如果你从来没学过数据库，先不要急着看 MongoDB 命令。先理解数据库解决的是什么问题。

假设你经营一个小店。你有这些数据：

数据类型 例子
用户 张三、李四、他们的手机号、注册时间
商品 商品名、价格、库存、分类
订单 谁买了什么、买了几件、总价、下单时间
日志 谁什么时候做了什么

如果这些东西都放在 Excel 里，问题很快就会出现：

问题 为什么麻烦
多人同时修改 容易冲突、覆盖
数据量变大 文件变慢，查找困难
想按条件查找 写公式麻烦，不适合高频查询
要给程序用 程序频繁读写文件很笨重
要保证数据别乱掉 比如订单金额字段被改成文字，文件很难约束

数据库就是专门解决“结构化/半结构化数据长期存储、查询、更新、多用户访问”的系统。

你可以把数据库暂时理解成：

词 朴素理解
数据库 存很多数据的大仓库
查询 从仓库里找数据
更新 改数据
删除 删数据
索引 给仓库做目录，让你找得快
事务 保证多步操作要么都成功，要么都失败

2. 关系型数据库和 MongoDB 到底差在哪

大多数初学者以前听到数据库，首先想到的是 MySQL、PostgreSQL、SQL Server 这种关系型数据库。

MongoDB 不是关系型数据库，它是文档数据库。

最直观的差别是：

维度 MySQL 这类关系型数据库 MongoDB
主要存储单位 行 文档
外观感觉 表格 JSON 风格对象
模式 一般先定义列 默认更灵活
关系表达 外键、JOIN 嵌入、引用、$lookup
常用语言 SQL MQL / 聚合管道
建模思路 规范化 按访问模式设计

看一个简单对比。

关系型数据库里的用户表，可能长这样：

1 Alice Shanghai 1
2 Bob Beijing 0

3. 什么叫“文档模型”

文档模型的核心思想是：一条记录可以自己带着一部分结构，而不是只能平铺成一行一列。

1
2
3
4
5
6

flowchart TD
    A["订单文档"] --> B["基础字段：订单号、状态、时间"]
    A --> C["内嵌对象：收货地址"]
    A --> D["数组：订单项 items[]"]
    D --> E["商品1"]
    D --> F["商品2"]

这种模型的好处：

好处 解释
表达真实业务更自然 地址、商品列表本来就是嵌套结构
一次读取更完整 订单查出来时，很多相关信息已经在文档里
单文档原子性强 一条文档内部的更新天然原子

但也有代价：

代价 解释
容易把文档做得太胖 什么都往里塞会越来越难维护
如果关系复杂，不能无脑嵌入 例如商品主数据通常不适合完整嵌进所有订单
灵活 schema 容易演变成混乱 schema 没有约束时，字段名和类型容易漂移

4. MongoDB 里最关键的几个名词

名词 简单解释 你可以暂时怎么理解
database 数据库 一个大文件柜
collection 集合 一类文档的盒子，近似于表
document 文档 一条 JSON 风格记录，近似于一行
field 字段 文档里的键，近似于列
_id 主键字段 每个文档都有，默认唯一
BSON MongoDB 真正存储的格式 比 JSON 类型更多
mongosh MongoDB Shell 交互式命令行
Compass 官方图形界面客户端 可视化查看和操作数据
Atlas MongoDB 官方云服务 不想自己装服务器时最方便
Replica Set 副本集 高可用集群
Sharding 分片 水平扩展

你可以先把 database / collection / document 理解成下面这样：

概念 类比 Excel 类比 MySQL
database 一个工作簿集合 一个 database
collection 一张工作表 一张 table
document 一行记录 一行 row
field 一个单元格中的列名和值 一列 column

注意：这个类比只是为了帮助入门。真正用起来，MongoDB 的文档结构比 Excel 和普通表格复杂得多。

5. JSON 和 BSON 是什么关系

MongoDB 经常说“文档像 JSON”，但它不是直接把 JSON 原样存进去。

MongoDB 实际使用 BSON。

项 JSON BSON
本质 文本格式 二进制编码格式
常见场景 接口传输、配置文件 MongoDB 存储和网络传输
类型系统 比较少 更多，例如 ObjectId、Date、Decimal128

为什么 BSON 重要：

原因 解释
类型更丰富 时间、二进制、精确小数等都更容易处理
更适合数据库内部 编码效率和存储结构更适合数据库

最常见 BSON 类型如下：

BSON 类型 例子 新手建议
String "Alice" 文本直接用
Boolean true 布尔值
Int32 / Int64 NumberInt(5)、NumberLong(5) 计数用整数
Double 12.5 一般浮点值
Decimal128 NumberDecimal("88.00") 金额优先用它
Date ISODate("2026-04-23T10:00:00Z") 时间一定尽量用真正的 Date
ObjectId ObjectId("...") 默认 _id 常见类型
Array ["vip", "new"] 标签、多值字段
Object { city: "Shanghai" } 嵌套对象

6. _id 为什么那么重要

每个 MongoDB 文档都有 _id。

如果你不自己给，MongoDB 会自动生成一个 ObjectId。

例如：

1
2
3
4

{
  "_id": ObjectId("6808d4e68f29a0..."),
  "name": "Alice"
}

为什么一定要有 _id：

作用 解释
唯一标识一条文档 类似主键
默认自带唯一索引 按 _id 查很快
很多程序逻辑会依赖它 比如根据 _id 更新、删除

新手最常见的几个误区：

误区 正确理解
_id 只能是 ObjectId 错，可以是字符串、数字、UUID 等
_id 是普通字段，随便改 不建议，通常视为稳定主键
_id 看着丑就别管了 生产里你必须知道它是什么类型

7. MongoDB 到底适合什么场景

这件事很重要，因为很多人不是不会 MongoDB，而是把它用错了地方。

场景 适合程度 原因
用户资料、内容系统、商品系统、订单系统 很适合 文档结构自然，业务字段变化快
埋点、日志、事件流、IoT 数据 很适合 半结构化、时序、字段变动都常见
快速迭代业务 很适合 schema 灵活
高度依赖复杂 JOIN 和强外键的纯关系场景 谨慎 关系型数据库通常更直接
简单小系统 也适合 上手快，开发效率高

8. MongoDB 学习时最重要的思想

这四句建议，你现在先记住，后面会不断验证它们：

原则 含义
一起读的数据，尽量一起存 这是 MongoDB 建模的底层直觉
先想查询，再想 schema 别先拍脑袋定结构
先想 schema，再想索引 索引要服务真实读写模式
事务是补充，不是默认方案 好建模能减少事务需求

单个订单的订单项数量通常可控 不会无限增长到夸张地步

但为什么 users 和 products 又拆成单独集合？

数据 为什么拆出去
用户 会被多个订单引用，用户信息会独立维护
商品 商品库存、价格、分类会频繁独立更新

这就是 MongoDB 建模最核心的取舍。

索引和 explain，决定你以后查得快不快

1. 为什么一开始感觉 MongoDB 很快，后来突然变慢

因为数据量小时，即使你不建索引，全表扫描也可能“看起来还行”。

但数据量一大，这种假象就会消失。

你先记一个粗暴但非常实用的判断：

现象 常见原因
精确查某个字段很慢 没有索引
条件过滤加排序很慢 索引不匹配过滤和排序
聚合很慢 前面没过滤好，或者索引不足
列表页越翻越慢 深分页、排序和索引不匹配

2. 索引到底是什么

你可以把索引理解成“目录”。

如果一本书没有目录，你想找“MongoDB”这个词，只能一页一页翻。
如果有目录，你会先看目录，再跳到对应位置。

数据库没有合适索引时，常见情况就是“全表扫描”。

3. 最简单的单字段索引

假设订单经常按 userId 查询：

1

db.orders.createIndex({ userId: 1 })

这个语句的意思是：给 orders 集合的 userId 字段建立一个升序索引。

为什么是 1？

值 含义
1 升序索引
-1 降序索引

单字段索引最适合：

场景 例子
单字段精确查找 按 userId 查订单
单字段范围查找 按 createdAt 查时间段
单字段排序 按 createdAt 排序

4. 复合索引才是真正高频场景

实际业务里，很多查询不是只按一个字段查。

例如，一个非常典型的订单列表查询：

1

db.orders.find({ userId: "U1001" }).sort({ createdAt: -1 })

这时，通常更适合的索引是：

1

db.orders.createIndex({ userId: 1, createdAt: -1 })

为什么不是各建一个索引就完事？

因为复合索引可以同时服务“按用户过滤”和“按时间排序”。

5. 复合索引最重要的规则：前缀原则

看这个索引：

1

{ userId: 1, status: 1, createdAt: -1 }

它更适合下面哪些查询？

查询 一般情况
{ userId: "U1001" } 合适
{ userId: "U1001", status: "paid" } 合适
{ userId: "U1001", status: "paid" } 再按 createdAt 排序 很合适
{ status: "paid" } 通常不理想

为什么？

因为 MongoDB 复合索引对“从左到右的字段顺序”很敏感。

所以索引设计不是“把常用字段都塞进去”，而是“按查询模式排序”。

字段 含义

11. 索引不是越多越好

这是错误的。

为什么：

原因 解释

真正正确的思路是：

12. 新手做索引最常犯的错误

错误 说明

不看 explain() 不知道到底有没有用上

聚合：MongoDB 最重要的高级能力

1. 聚合到底是在干什么

很多人第一次看到聚合，会觉得像“怪怪的 JSON 命令”。
你可以先把它理解成“流水线处理数据”。

1
2
3
4
5

    B --> C["$unwind 拆开 items"]
    C --> D["$group 分组统计"]
    D --> E["$sort 排序"]
    E --> F["结果"]

也就是说：每个 stage 都对上一阶段的结果做一次处理。

2. 最常见的 stage 先记住

Stage 作用 类比 SQL 时可以怎么想
$match 过滤数据 WHERE
$project 选择字段、改造字段 SELECT

$unset 去掉字段 不返回某列
$group 分组统计 GROUP BY
$sort 排序 ORDER BY
$limit 限制条数 LIMIT
$skip 跳过条数 OFFSET
$unwind 拆数组 把数组展开成多行
$lookup 关联其他集合 类似 LEFT JOIN
$facet 一次出多份结果 一次跑多条统计支路

数据建模：MongoDB 真正的核心

1. 为什么 MongoDB 最重要的不是命令，而是建模

因为 MongoDB 很多优势和很多坑，最后都来自建模。

如果你建模建对了：

好处 说明
查询路径短 少 $lookup
原子操作多 少事务
性能稳定 索引设计更清晰

如果你建模建错了：

问题 说明
文档过胖 读写都越来越重
数组无限增长 接近文档大小限制
查询绕来绕去 要么慢，要么代码复杂

2. MongoDB 的建模第一原则

一句话：

原则 解释
按访问模式建模 先看你最常怎么查，再决定怎么存

不是先问“现实世界里它们是不是有关联”，而是先问：

问题 为什么重要
这两份数据是不是经常一起读 决定要不要嵌入
这块数据会不会无限增长 决定能不能一直嵌下去
这块数据是不是经常独立更新 决定是否适合拆出去

3. 嵌入 vs 引用

这是 MongoDB 建模里最核心的选择题。

方案 解释
嵌入 把相关数据直接放进主文档里
引用 主文档只保存另一份数据的 ID

订单示意：

1
2
3
4
5

flowchart TD
    A["orders"] --> B["内嵌 items[]"]
    A --> C["引用 userId"]
    C --> D["users"]
    A --> E["引用 productId（订单项快照里可保留关键信息）"]

什么时候更适合嵌入：

条件 说明
通常一起读 比如订单和收货地址
子项数量可控 不会无限涨
读多于独立更新 一起存更方便

什么时候更适合引用：

条件 说明
数据会被很多地方复用 用户、商品、商家
子项可能非常多 评论、消息、日志明细
需要经常独立更新 商品库存、用户资料

4. 一对一、一对多、多对多怎么想

关系 常见建议
一对一 大多可以嵌入
一对多 看“多”的规模和访问方式
多对多 通常引用，必要时配合冗余

例子：

业务 建议
用户与个人设置 一对一，常可嵌入
用户与订单 一对多，通常订单独立集合
文章与评论 一对多，评论很多时通常独立集合
学生与课程 多对多，常用引用关系

5. 为什么官方总说“不要把 MongoDB 当没外键的 MySQL”

因为如果你完全照关系型思维做：

问题 结果
所有数据都拆很碎 查一次就要拼很多次
过度依赖 $lookup 查询复杂且可能变慢
失去单文档原子优势 事务需求变多

MongoDB 最好的状态不是“完全不要引用”，而是“该嵌的嵌，该拆的拆”。

5. writeConcern、readConcern、readPreference 先建立直觉

这三个词很像，初学者特别容易混。

名词 你先把它理解成什么
writeConcern 写操作要确认到什么程度才算成功
readConcern 读操作希望拿到什么一致性级别的数据
readPreference 我打算从哪个节点读

再具体一点：

名词 常见值 朴素理解
writeConcern w:1、w:"majority" 至少一个节点确认，还是多数节点确认
readConcern local、majority、snapshot 允许读本地最新，还是要求更稳的一致性
readPreference primary、secondary 优先从主还是从从节点读

你先不用全部吃透，但一定要知道它们不是一回事。

没有自动故障转移 服务中断
很多高级能力受限 例如变更流需要副本集或分片集群

所以：

环境 建议
学习阶段 standalone 可以
生产环境 优先副本集

8. 分片是什么

当数据量或吞吐量太大，一台机器扛不住时，就考虑分片。

因为分片键决定：

方面 为什么重要
数据分布 是否均匀
写热点 会不会全打到一个分片
查询路由 查询能不能精准打到少数分片
扩展性 后面好不好维护

一个糟糕分片键的典型例子：

分片键 问题

一个更常见的思路：

方案 评价
用户 ID 哈希 分布通常更均匀
tenantId + createdAt 多租户场景常见，但要看查询模式

10. 变更流是什么

变更流允许程序订阅集合或数据库的变化。

例如：

1

这在什么场景下很有用：

场景 例子
实时通知 订单状态变化就发消息
缓存同步 数据改了就刷新缓存
搜索同步 数据改了就同步到搜索索引

条件 说明
需要副本集或分片集群 standalone 不支持正常使用场景

实战里最容易踩的坑

1. 把金额存成浮点

不推荐。

类型 问题
Double 可能有精度问题
Decimal128 更适合金额

所以金额类字段优先考虑：

1

NumberDecimal("88.00")

2. 时间存成字符串

很多新手喜欢这样：

1

{ "createdAt": "2026-04-23 10:00:00" }

能不用就别这么用。

推荐：

1

{ createdAt: ISODate("2026-04-23T10:00:00Z") }

原因：

好处 解释
范围查询方便 时间比较更自然
排序稳定 真正按时间排序
驱动更好处理 类型更明确

3. 把所有字段都塞进一个文档

短期看方便，长期很容易出问题。

尤其以下场景要警惕：

场景 风险
用户所有历史操作都放一个数组 无限增长
商品把所有评论都嵌进去 越来越重
一个租户所有资源都塞一个文档 文档很快爆炸

4. 看到 MongoDB 灵活，就完全不做 schema 治理

后果：

问题 例子
同一字段类型混乱 有时是数字，有时是字符串
字段命名漂移 userName、username、user_name 全都出现
下游聚合困难 统计口径变乱

5. 只会写 find()，不会看 explain()

这会导致：

问题 结果
线上慢查询不会排查 只能靠猜
索引是否生效不清楚 可能白建索引

6. 深分页一直用 skip

小数据没问题，大数据要小心。

因为页数越深，通常要跳过的数据越多。

更好的思路：

场景 更推荐
后台管理、小表 skip + limit 可以
App 时间流、订单流 基于排序键做范围分页

范围分页例子：

1
2
3

db.orders.find({
  createdAt: { $lt: ISODate("2026-04-15T10:00:00Z") }
}).sort({ createdAt: -1 }).limit(10)

7. 用事务解决所有问题

这是典型的“关系型思维惯性”。

更好的顺序应该是：

顺序 先做什么
1 先检查 schema 是否能更合理
2 再检查是否可通过单文档原子更新解决
3 真不行再上事务

常见报错与排查

1. duplicate key error

含义：唯一索引冲突，或者 _id 重复。

典型原因：

原因 例子
插入了重复 _id _id: "S001" 已存在
唯一索引字段重复 两个用户用了同一个邮箱

排查方向：

步骤 说明
先看报错里是哪一个索引冲突 会提示索引名
查现有数据是否已有同值 用 find() 验证
确认业务是否允许重复 不允许就改数据，不然就重新设计约束

2. 连接不上本地 MongoDB

常见原因：

原因 现象
MongoDB 服务没启动 mongosh 连不上
端口不是 27017 默认连接失败
安装完没把工具路径配置好 命令找不到

3. Atlas 连不上

常见原因：

原因 说明
数据库用户没创建对 用户名密码错误
IP 白名单没放开 Atlas 拒绝连接
连接串没替换密码 连接字符串仍是模板

4. 查询结果不对

先看这几件事：

排查项 常见问题
字段名拼写 userName 和 username 混了
类型 "18" 和 18 不是一回事
null 与不存在 匹配范围和你想的不一样
数组条件 没用 $elemMatch 导致匹配错

5. 查询很慢

先按这个顺序查：

顺序 检查点
1 查询条件是否合理
2 有没有索引
3 排序字段有没有纳入索引
4 explain() 是不是 COLLSCAN
5 文档是否过大
6 聚合是否早过滤

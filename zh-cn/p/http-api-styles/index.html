HTTP API 都有哪些设计方式？一文讲清 REST、RPC、GraphQL 与 SOAP

用订单系统的请求示例和六张示意图，讲清 HTTP API 的基本结构、REST、RPC、JSON-RPC、gRPC、GraphQL、SOAP，以及 SSE、WebSocket、Webhook 的区别与适用场景。

写前后端项目时，经常会遇到这些说法：“这个接口是 RESTful 的”“内部服务走 RPC”“前端用 GraphQL”“结果通过 SSE 流式返回”。它们都在描述程序之间的通信，但描述的并不是同一件事。

要看懂这些名词，可以先抓住三个问题：请求是围绕资源组织，还是围绕动作组织？数据用什么格式表示？结果是一次返回，还是持续传递？

本文用一个订单系统贯穿讲解：查订单、创建订单、取消订单，以及接收订单状态变化。文中的域名和业务字段都是教学示例，不对应真实服务；除特别说明外，HTTP 示例采用便于阅读的 HTTP/1.1 文本写法，并省略长度等与讲解无关的字段。

先把“格式”分清：设计方式、数据编码、通信方式

严格说，REST、RPC、GraphQL、SOAP 并不是几种平级的“HTTP 数据格式”。日常把它们叫作 API 类型方便交流，但理解原理时，需要拆开来看。

你想知道什么 对应概念 具体例子
接口围绕什么组织 设计思路 REST 围绕资源，RPC 围绕远程方法
客户端如何表达要取的数据 查询语言与执行模型 GraphQL 的字段选择、类型与执行规则
消息遵循什么规则 消息协议、框架 JSON-RPC、SOAP；gRPC 还提供生成代码等配套能力
消息如何传递 通信协议或交互方式 HTTP 请求响应、SSE、WebSocket、Webhook 回调
消息中的数据如何表示 数据格式与编码 JSON、XML、Protocol Buffers
双方如何约定参数和返回值 接口描述与契约 OpenAPI、.proto、GraphQL Schema、WSDL

这些维度可以组合。例如，一个 API 可以采用资源式设计 + HTTP + JSON + OpenAPI 文档；另一个可以采用 RPC 思路 + gRPC + HTTP/2 + Protocol Buffers。JSON-RPC 本身也不绑定 HTTP，可以通过其他通道传递。

其中，JSON 是一种文本数据交换格式，不负责规定 URL、调用方法或错误语义；OpenAPI 则用来描述 HTTP 接口，不能据此判断接口一定符合 REST。JSON 标准、OpenAPI 规范

REST：把接口组织成“对资源做操作”

REST 的全称是 Representational State Transfer，通常译为“表述性状态转移”。初学时，可以先理解为：用地址标识资源，通过资源的表示来读取或改变它的状态，并遵循统一的交互规则。

订单、用户、商品都可以是资源。客户端拿到的 JSON，是订单在这次响应中的一种表示，并不等于数据库表本身。

最常见的资源式 HTTP API

需求 常见写法 说明
查询订单列表 GET /orders?status=paid 在集合上筛选
查询订单详情 GET /orders/1001 读取一个订单
创建订单 POST /orders 向集合提交创建请求
整体替换订单表示 PUT /orders/1001 按接口约定提交完整的可写表示
修改部分字段 PATCH /orders/1001 使用约定的补丁格式
删除订单资源 DELETE /orders/1001 请求删除，不代表业务上允许删除

这里的重点是地址负责标识资源，方法表达操作语义。但 REST 并不规定 URL 必须用英文复数，也不要求响应必须是 JSON；这些是常见工程约定。

REST 不只是给 URL 换成名词

Fielding 提出的 REST 有一组架构约束，下面用日常开发中的说法解释：

约束 通俗理解
客户端与服务器分离 展示界面与服务端实现可以分别演进
无状态通信 每个请求带齐理解它所需的信息，不依赖上一次请求留下的会话上下文
可缓存性 响应应表明能否缓存、如何复用，不是所有响应都要缓存
统一接口 识别资源、通过表示操作资源，消息能被理解，并提供可推进业务的超媒体控制
分层系统 客户端可以通过网关等中间层访问服务
按需代码，可选 必要时向客户端提供可执行代码

“无状态”不等于“服务器不能用数据库”，也不等于“必须用 JWT”。订单数据当然可以保存在服务器；约束关注的是通信所依赖的会话状态。

统一接口里的超媒体控制，可以理解成：返回结果不仅给数据，还告诉客户端接下来可以做什么。例如，一个订单表示可以带上取消操作的链接。链接的含义、允许的方法和提交格式也要由双方理解的媒体类型或契约约定。

很多工程里的“REST API”，实际上主要实现了资源命名、HTTP 方法和状态码。称为“资源式 HTTP API”往往更准确。判断是否符合完整 REST，不能只检查路径里有没有动词。REST 原始论述，第 5 章

取消订单，究竟该怎么写？

取消订单通常不是删除订单。订单还要保留，以便展示历史、退款或审计。可以有几种合理设计：

POST /orders/1001/cancellations HTTP/1.1
Host: api.example.com
Content-Type: application/json

{
  "reason": "ordered_by_mistake"
}

这里把“取消申请”建模成子资源，便于给它单独的编号、状态和审核过程。

如果取消只是简单的状态变更，也可以提供明确约定的补丁：

PATCH /orders/1001 HTTP/1.1
Host: api.example.com
Content-Type: application/merge-patch+json

{
  "status": "cancelled"
}

服务端仍然要检查当前状态是否允许取消，不能把客户端提交的状态直接写入数据库。如果你采用 POST /orders/1001/cancel 这种动作接口，也应把它的业务含义讲清楚，不必为“URL 看起来纯不纯”牺牲可读性。PATCH 的含义是应用局部修改，具体如何修改由补丁格式决定。PATCH 标准、JSON Merge Patch 标准

安全、幂等、缓存，是三回事

“安全”在 HTTP 方法语义里指客户端不请求改变服务器状态，并不是说接口没有安全漏洞。查询仍然可能产生日志等附带效果。

“幂等”指同一个请求执行一次和多次，预期对服务器产生的效果相同。例如，重复请求删除同一个订单，第一次返回 204，第二次返回 404，仍然可以是幂等的，因为订单最终都处于不存在的状态。

方法 安全 按方法定义是否幂等 需要注意
GET 是 是 不应用于触发取消、转账等操作
POST 否 不保证 可以通过业务机制实现重复请求去重
PUT 否 是 表达创建或替换目标资源的状态
PATCH 否 不保证 “设为 2”与“增加 2”的重复执行效果不同
DELETE 否 是 幂等不要求每次响应完全相同

幂等性来自操作语义和服务端实现，不能靠把方法名改成 PUT 就获得。网络超时后也不能不加区分地重试所有请求。HTTP 安全与幂等语义

缓存则回答“能不能复用之前的响应”。例如，某个订单响应可以按权限设计为：

1
2

Cache-Control: private, max-age=30
ETag: "order-1001-v3"

客户端之后带上 If-None-Match: "order-1001-v3"，资源表示未变化时可以收到 304 Not Modified。private 表示只允许私有缓存存储，不能放进共享缓存；敏感数据是否应存储，还要由具体策略决定。使用 GET 并不意味着响应自动可以被任意 CDN 缓存。HTTP 缓存标准

RPC：把接口组织成“调用远处的方法”

RPC 是 Remote Procedure Call，也就是远程过程调用。它更接近这样的表达：

1
2
3

GetOrder(id="1001")
CreateOrder(product_id="P100", quantity=2)
CancelOrder(id="1001", reason="ordered_by_mistake")

REST 让你先想“资源是什么”，RPC 让你先想“需要执行什么动作”。在“计算运费”“生成报表”“审核申请”这类业务里，方法式表达往往很直观。

普通的 HTTP RPC

RPC 不一定需要专门的框架。下面就是一种常见的、由团队自行约定的 HTTP RPC：

POST /rpc/order.cancel HTTP/1.1
Host: api.example.com
Content-Type: application/json

{
  "order_id": "1001",
  "reason": "ordered_by_mistake"
}

也可以设计成 /OrderService/CancelOrder。RPC 这个概念本身没有规定 URL 的唯一写法，更没有规定一定走 TCP、一定用二进制或一定比 REST 快。

当所有请求都走一个入口时，网关和监控通常还需要读取方法名，才能区分“查询订单”和“取消订单”，为不同操作分别限流、授权和统计错误。

JSON-RPC：把方法调用的消息结构标准化

普通 HTTP RPC 的字段可能每家都不同。JSON-RPC 2.0 则规定了请求和响应的消息结构。例如：

  "params": {

    "reason": "ordered_by_mistake"

  "id": 7
}

  "jsonrpc": "2.0",
  "result": { "order_id": "1001", "status": "cancelled" },
  "id": 7
}

失败响应，例如参数不符合方法要求：

1
2
3
4
5

{
  "jsonrpc": "2.0",
  "error": { "code": -32602, "message": "Invalid params" },
  "id": 7
}

其中，id 用来把响应对应到请求；它不是业务去重键。成功用 result，失败用 error，两者不能同时出现。省略 id 的调用称为 notification，服务端不返回 JSON-RPC 响应；如果通过 HTTP 传递，仍然需要结束这次 HTTP 交互，只是不携带 JSON-RPC 响应对象。

JSON-RPC 还定义了批量调用。需要注意，批量不代表事务，也不保证按数组顺序执行或返回；要用 id 关联结果。HTTP 状态码如何映射也不是 JSON-RPC 核心规范统一规定的。JSON-RPC 2.0 规范

gRPC：围绕契约生成调用代码

gRPC 是 RPC 框架。典型用法是先写 .proto 文件，约定服务、方法和消息字段，再生成客户端与服务端代码。例如：

syntax = "proto3";
package shop;

service OrderService {
  rpc GetOrder (GetOrderRequest) returns (Order);
  rpc CancelOrder (CancelOrderRequest) returns (Order);
}

message GetOrderRequest {
  string order_id = 1;
}

message CancelOrderRequest {
  string order_id = 1;
  string reason = 2;
}

message Order {
  string id = 1;
  string status = 2;
}

这里 = 1、= 2 是字段编号，不是默认值。双方通过同一份定义理解字段，Protocol Buffers 默认用二进制编码消息。

原生 gRPC 的常见协议映射使用 HTTP/2，方法路径类似 /shop.OrderService/GetOrder，内容类型常见为 application/grpc。它支持四种调用：一次请求一次响应、服务端流、客户端流、双向流。gRPC 核心概念

因此，“RPC 和 HTTP 是二选一”不成立，gRPC 本身就是反例。但原生 gRPC 也不是往普通 URL 发一段 JSON 就能调用：消息有分帧规则，调用结果通常还要读取结尾元数据中的 grpc-status。收到 HTTP 200，不代表远程方法执行成功。gRPC 的 HTTP/2 协议映射

浏览器接入时通常要用 gRPC-Web 或适配网关，不能直接把浏览器支持 HTTP/2 等同于支持原生 gRPC 的所有能力。具体流式能力取决于所选客户端和部署方式。gRPC-Web 项目说明

它适合需要明确契约、跨语言协作和代码生成的服务通信；代价是要维护生成流程、兼容性和对应的调试工具。性能是否更好，要用真实消息大小、网络和调用链测试，不能只根据名字判断。

远程方法长得像本地方法，但会跨网络

设想你发送取消请求，服务端已经完成取消，但响应在网络中丢了。客户端看到的只是超时，不能据此断言“服务端没有执行”。

如果操作是扣款，直接重试可能产生重复扣款。业务可以约定一个幂等键，并由服务端持久化去重和结果；还要定义键的作用范围、有效期、并发处理方式，以及同一个键对应不同参数时怎么办。这个问题同样存在于 REST、GraphQL 和 SOAP 中。

GraphQL：由客户端描述“要哪些字段”

假设订单详情页需要订单编号、状态和收货人姓名。一个固定字段的 REST 接口可能返回大量暂时用不到的数据，也可能需要客户端再请求用户信息。

GraphQL 允许客户端按照服务端定义的类型和关系，选择这次需要的字段：

query OrderDetail($id: ID!) {
  order(id: $id) {
    id
    status
    customer {
      name
    }
  }
}

这里假设服务端的 Schema 已经定义了 order 和 customer 等字段。GraphQL 不是客户端随意执行的 SQL，客户端只能访问 Schema 暴露且权限允许的数据。

GraphQL 通常使用单个入口，但 /graphql 只是惯例。查询可以通过 POST 传递，服务端也可以支持 GET 查询；修改操作 mutation 不能通过 GET 执行。GraphQL 本身不绑定 HTTP，而 GraphQL over HTTP 对它在 HTTP 上的使用作进一步约定；截至本文写作时，后者仍标为草案。GraphQL over HTTP 官方说明

可以看到，GraphQL 的查询很强调数据形状，mutation 又常常采用动作式表达。它和 REST、RPC 的关系，不是简单地把 URL 换个写法。

一次 HTTP 请求，不等于后端只查一次

如果查询 20 个订单，每个订单再取一个客户，而服务端逐个查询客户，就可能执行 1 次订单查询加 20 次客户查询，这就是常说的 N+1 问题。减少浏览器请求次数，未必减少数据库访问次数。

工程上通常需要批量加载、合理分页、查询复杂度控制和逐字段授权。GraphQL 不会自动解决这些问题。GraphQL 性能说明

也不是“所有结果都返回 200”

GraphQL 响应可以同时含有 data 和 errors：例如订单基本信息成功返回，而某个可空的附属字段获取失败。客户端需要检查错误及受影响字段，不能把 HTTP 成功简单当成所有数据都完整。GraphQL 响应规则

无效请求、执行前验证失败、服务器故障和部分字段失败，处理方式不同；使用 application/json 还是 application/graphql-response+json 也会影响状态码约定。接入时应以服务端的媒体类型、实现和契约为准。GraphQL HTTP 错误说明

如果不同客户端对字段组合的需求差异大，GraphQL 值得考虑；如果只是几个稳定的查询和提交表单，资源式 HTTP API 或简单 RPC 往往更容易维护。这是根据需求作出的工程判断，并不是协议的优劣排名。

SOAP：把消息装进有规则的 XML 信封

SOAP 是一种消息协议。它常见于已有企业系统的对接，使用 XML 表示消息，并定义 Envelope、Header、Body、Fault 等结构。它可以承载 RPC 风格调用，也可以传递文档，不能简单理解为“用 XML 写的 REST”。SOAP 1.2 消息框架

例如，一次 SOAP 1.2 的查询请求可以长这样：

POST /OrderService HTTP/1.1
Host: api.example.com
Content-Type: application/soap+xml; charset=utf-8; action="urn:shop:GetOrder"

<soap:Envelope xmlns:soap="http://www.w3.org/2003/05/soap-envelope"
               xmlns:shop="urn:shop">
  <soap:Body>
    <shop:GetOrder>
      <shop:orderId>1001</shop:orderId>
    </shop:GetOrder>
  </soap:Body>
</soap:Envelope>

可以把它理解成：HTTP 负责这次请求响应，SOAP 规定消息信封，GetOrder 则是这个业务契约里的内容。上面使用的是 SOAP 1.2；不要把它的命名空间、媒体类型与 SOAP 1.1 的写法混用。SOAP 1.2 HTTP 绑定

SOAP 服务常配合 WSDL 描述服务契约，便于生成调用代码；这属于配套体系，不代表每个 SOAP 消息都必须附带 WSDL，也不代表使用 SOAP 就自动拥有可靠投递、事务或完善的安全策略。WSDL 2.0 入门

如果对接方已经提供 SOAP/WSDL，优先按对方契约接入。新项目是否选择它，主要取决于合作方要求、现有工具链和维护成本，不必因为消息看起来长就否定它，也不必因为规范多就认为它天然更安全。

持续更新与事件通知：SSE、WebSocket、Webhook

前面主要解决“如何表达一次调用”。接下来这三个概念，更多是在解决“消息什么时候发、往哪个方向发”。它们可以与前面的接口设计搭配使用。

方式 消息怎么走 典型用途 需要处理什么
轮询 客户端隔一段时间重新查询 更新频率不高的任务状态 查询间隔与额外请求量
SSE 客户端建立 HTTP 请求，服务端持续发送事件 任务进度、消息通知、逐步生成结果 断线恢复、代理缓冲、连接超时
WebSocket 建立连接后，双方都可以发送消息 聊天、协同编辑、实时交互 心跳、重连、消息语义与流量控制
Webhook 事件发生后，提供方请求接收方的回调地址 支付结果、仓库事件、系统集成 验签、重复投递、乱序、重试

SSE：一个响应里陆续收到多条事件

例如客户端订阅订单状态，服务端按 text/event-stream 格式返回：

 7
 8
 9

11

HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

id: 101
event: order.updated
data: {"order_id":"1001","status":"paid"}

id: 102
event: order.updated
data: {"order_id":"1001","status":"shipped"}

每条事件用空行结束。data: 内部可以放 JSON，但事件流本身不是一个完整的 JSON 文档。浏览器原生 EventSource 提供连接和重连机制，也可以携带最近的事件编号；服务端是否能补发历史事件，需要额外实现。SSE 标准

另一个常见细节是：原生 EventSource 使用 GET，并不提供任意设置请求头或请求体的接口。如果需要 POST 请求体或自定义认证头，可以根据服务端协议使用 fetch 读取响应流，并自行处理事件解析与重连。只要逐段返回，就一定是 SSE，这个判断不成立；按行分隔的 JSON、二进制流等也能流式传递。

WebSocket：建立双向消息通道

WebSocket 允许客户端和服务端在连接建立后分别发送消息，消息可以是文本或二进制。它定义了连接与消息帧，但不会替应用决定“取消订单消息应该有哪些字段”“收到消息后是否需要确认”。这些仍要自己约定。

经典 HTTP/1.1 场景会通过 Upgrade 握手建立 WebSocket；握手完成后，交换的是 WebSocket 消息帧，不再是每条消息一组普通 HTTP 请求响应。WebSocket 协议

因此可以在 WebSocket 上传 JSON-RPC，也可以设计自己的聊天消息。这里再次说明，通信通道和上层消息规则可以组合。

Webhook：由事件提供方主动调用你

例如，你把回调地址登记给支付平台。支付完成后，平台向你的服务发送一个新请求：

接收方要验证来源、去重，并处理平台重试或事件乱序。完成可靠接收或入队后，可以尽快按对方契约响应，再异步处理耗时业务；不能还没保存事件就直接表示成功，否则后续失败可能丢消息。支付平台的实际投递规则可以参考其官方文档。Stripe Webhook 文档

实际项目怎么选，还要约定哪些事？

先把主要几类设计放在一起比较。下面的场景建议是本文的工程取舍，具体项目仍要看客户端能力、团队经验和现有系统。

类型 主要围绕什么 常见消息表示 什么时候值得考虑 主要成本
资源式 HTTP API / 常说的 REST API 资源与 HTTP 语义 JSON，也可以用其他表示 用户、商品、订单等资源操作清楚，对接方较多 资源建模、状态变化和响应契约
普通 HTTP RPC 方法与参数 常见为 JSON 动作明确，希望简单直接 自己统一方法、错误和版本规则
JSON-RPC 标准化的方法调用消息 JSON 希望复用标准调用、通知和批量结构 HTTP 映射、业务去重和方法级治理
gRPC 服务方法与类型契约 默认 Protocol Buffers 需要跨语言代码生成、类型契约或流式调用 生成流程、网关和调试工具
GraphQL 类型关系与字段选择 HTTP 上通常使用 JSON 多客户端需要不同的数据组合 查询成本、字段权限和缓存策略
SOAP XML 消息与服务契约 XML 对接既有 SOAP 服务或有明确契约要求 配套规范、工具与兼容性

一套订单系统完全可以组合使用：对外提供资源式 HTTP API；内部某些服务通过 gRPC 通信；订单页用 SSE 接收状态更新；支付结果通过 Webhook 接入。每条边界选择适合它的方式，比强行全站统一更重要。

无论选择哪一种，下面的契约都要写清楚。

要约定的事情 具体要回答的问题
身份与权限 调用者是谁？是否能读取或取消这个订单？能否访问其中每个字段？
错误处理 哪些错误能重试？如何区分输入错误、权限不足和服务故障？
超时与重试 最长等多久？超时后是否能确认执行结果？是否需要幂等键？
分页与边界 一页最多多少条？游标如何使用？消息或请求体最大多大？
兼容性 新增、删除字段会不会破坏旧客户端？弃用流程是什么？
可观测性 如何按业务操作统计延迟、失败率，并关联请求日志？

对于普通 HTTP API，可以考虑使用 Problem Details 表示错误。例如，订单已经发货，不能取消：

HTTP/1.1 409 Conflict
Content-Type: application/problem+json

{
  "type": "https://api.example.com/problems/order-not-cancellable",
  "title": "订单无法取消",
  "status": 409,
  "detail": "订单已经发货，请使用退货流程。",
  "instance": "/requests/req-9f3a"
}

type 用于标识问题类型，detail 解释本次发生了什么，instance 标识本次问题的具体发生实例。不要把内部堆栈、数据库语句或密钥放进错误响应。这个格式是 HTTP API 的一种标准选择，不应机械替代 JSON-RPC、GraphQL、SOAP 自己规定的错误结构。Problem Details 标准

下次看到一个新 API，可以按顺序读它：先看方法、地址和消息头，再看调用围绕资源、方法还是字段选择，接着确认消息编码，最后看错误、超时和事件传递规则。这样即使名字没见过，也能很快找到它在解决什么问题。

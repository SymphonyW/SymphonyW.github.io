Helm 详解：从一堆 Kubernetes YAML 到可升级、可回滚的应用包

用图解讲清 Helm、Chart、values 与 Release 的关系，从零编写 Nginx Chart，完成预览、安装、多环境配置、升级、回滚与打包，并说明 Helm 3/4 差异和常见误区。

学过 Kubernetes 以后，你大概已经会写 Deployment 和 Service，也知道用 kubectl apply 把它们交给集群。但当一个应用变成十几个资源，还需要分别部署到开发、测试和生产环境时，“复制一份 YAML 再改几个字段”就开始让人头疼了。

Helm 解决的，就是如何把一组 Kubernetes 资源整理成可复用、可配置、可发布的应用包，并记录每一次安装和升级。

本文默认你知道 Pod、Deployment、Service 的基本作用。如果还不熟悉，可以先看 从 Docker 到 Kubernetes。这里围绕一个 Nginx 网站，把概念与命令连成一条能动手实践的路线。

版本与示例范围：本文使用 Helm 3、Helm 4 均支持的 apiVersion: v2 Chart。基础操作共用，失败恢复参数单独对照。示例使用 Linux 容器、已有的 Kubernetes 集群；命令按单行编写，可在常见 Shell 和 PowerShell 中执行。镜像标签只为教学固定，不表示生产版本建议。Helm 4 仍支持 v2 Chart，不能把 Helm 主版本与 Chart 格式版本混为一谈。Helm 4 官方说明

1. 为什么有了 kubectl，还需要 Helm？

假设你维护一个网站，最初只有两个文件：

1
2
3

website/
├── deployment.yaml
└── service.yaml

后来加上配置文件、入口路由、存储和权限，目录越来越长。紧接着，你又需要三套环境：

配置 开发环境 测试环境 生产环境
副本数 1 2 3
镜像版本 开发版本 候选版本 已验证版本
域名 dev.example.com staging.example.com example.com
资源额度 小 接近生产 按实际负载设置

直接复制目录当然能工作。但改一次健康检查，要同步修改三份；上线以后，还得另外记录“当时用了哪些 YAML、哪些参数，以及上一个可用版本是什么”。

Helm 把这些问题分成两部分：

  1. 描述怎么部署：把共同结构写成模板，把环境差异放进配置文件。
  2. 管理部署记录：为每次安装、升级保存配置、资源清单和状态，支持查看历史与回滚。

这也解释了它和其他工具的分工：

工具 主要负责什么 在网站例子中做什么
Docker / 镜像构建工具 把程序和运行依赖制成镜像 产出网站镜像
Kubernetes 调度资源，持续维护期望状态 保持需要的 Pod 运行
kubectl 与 Kubernetes API 交互 提交 YAML、查日志、看事件
Helm 打包配置、渲染模板、管理发布 用同一份 Chart 安装和升级网站

Helm 经常被比作 Kubernetes 的 apt 或 brew，这个类比适合帮助入门。不过它管理的核心是一组集群资源和发布记录，并不会直接替你编译代码或构建镜像。

如果你只有两个不怎么变化的 YAML，继续用 kubectl apply 很合理。当重复配置、多环境部署和版本管理成为日常工作，Helm 的价值才会明显起来。

2. 先分清四个词：Chart、values、Release、仓库

可以把部署网站想象成按菜谱做菜，但记住类比之后，还要落回具体对象：

名词 通俗理解 实际内容
Chart 一份可复用的部署方案 模板、默认配置、包信息和可选依赖
values 这次部署要填入的参数 镜像、副本数、端口等配置
Release 按这份方案安装出来的一套应用 有名字、namespace、历史修订和状态的安装实例
Repository / Registry 存放部署包的地方 传统 Chart 仓库，或支持 OCI 的制品仓库

同一个 Chart 可以安装出多个 Release。 比如把 web-demo Chart 安装为 web-dev 和 web-prod，它们可以使用不同参数，分别升级。Release 名在对应 namespace 中区分；查询时也要带对 namespace。

还要特别分清三个“版本”：

字段 例子 表示什么
Chart 的 version 0.1.0 部署包自己的版本
Chart 的 appVersion "1.28.0" 描述应用版本的元数据
Release 的 revision 1、2、3 某次安装实例的历史修订编号

例如：你只调整了资源额度，可以发布 0.1.1 的 Chart，应用版本不必变化；再把它升级到已有 Release，这个 Release 就会产生新的 revision。

修改 appVersion 不会自动更新镜像。 本文模板从 .Values.image.tag 读取镜像标签，因此只有修改这个输入，镜像字段才会变。其他 Chart 如果显式使用 .Chart.AppVersion，行为又会不同。Chart 格式说明

3. 敲下 helm install 后，发生了什么？

主线可以这样理解：

1
2
3
4
5
6
7

Chart 模板 + 合并后的 values + Release 等上下文
                       ↓
                普通 Kubernetes YAML
                       ↓
               Kubernetes API Server
                       ↓
        Deployment 等控制器持续维护实际资源

例如模板里写：

1

replicas: {{ .Values.replicaCount }}

配置里写：

1

replicaCount: 2

渲染出来的资源就是：

1

replicas: 2

Kubernetes 最终接收的是渲染后的资源，不负责理解 {{ ... }}。Helm 还会处理发布记录、资源更新及可选的 hooks；它并非只是对文件做字符串替换。

Helm 3、4 的常规 CLI 使用不需要在集群额外安装 Helm 服务端。老文章里的 Tiller 属于 Helm 2 的架构，不要照着部署。安装完成后，即使你退出终端，维持副本、重建 Pod 的工作仍由 Kubernetes 承担。

默认情况下，Release 信息保存在它所属 namespace 的 Kubernetes Secret 中，包括 Chart 和配置等内容。helm history 能看到历史，并不是因为你本地保留了一个终端窗口；同时，这些记录可能含敏感配置，需要合理控制访问权限。Release 存储说明

Helm 也不是持续同步 Git 的控制器。你手动改了线上资源，Helm 不会自己定时发现并修复；需要下一次操作或额外的 GitOps 控制器参与。资源更新细节也有版本差异：Helm 4 新安装的 Release 默认使用服务端应用，已有 Release 的升级通常沿用之前的应用方式。Helm 4 更新机制

4. 动手：从零部署一个 Nginx 网站

这部分只包含一个 Deployment 和一个 Service。先把主流程跑通，再增加入口路由、存储和其他能力。

可以下载 完整示例工程，解压后进入 helm-web-demo 目录；也可以按下面的目录与代码自行创建。后续命令都在包含 web-demo/ 和 values-dev.yaml 的目录执行。

现在只需要看懂几种模板写法：

写法 作用 本文中的效果
.Values.xxx 读取合并后的配置 决定副本数、镜像和服务端口
.Release.Name 读取安装实例的名字 Release 叫 demo，资源就叫 demo-web
.Release.Namespace 读取目标 namespace 将资源放到 helm-lab
toYaml 把对象转回 YAML 输出整段 resources 配置
nindent 12 换行并缩进 12 个空格 把 resources 内容放在正确层级
{{- 去掉左侧紧邻的空白 避免插入模板时出现多余空行

instance 标签很关键：同一个 namespace 安装两套网站时，Service 要选中属于自己 Release 的 Pod。只用相同的应用名，可能把两套 Pod 混在一起。模板上下文和管道语法可查 内置对象 与 函数和管道。

先检查，再安装，再访问

先在本地检查结构和渲染结果，这两步不需要集群：

1
2

helm lint ./web-demo
helm template demo ./web-demo -n helm-lab

第二条输出中应该看到一个 Service、一个 Deployment，资源名都是 demo-web，Deployment 的 replicas 是 1。正常渲染后，资源中不会再残留 {{ ... }}。

示例验证范围：附带工程已用 Helm 3.19.0、4.0.0 检查 Chart 结构和本地渲染。实际安装、镜像拉取、页面访问、升级与回滚，需要在你自己的练习集群继续验证。

helm template 只生成 YAML，不会创建 Release。 想把渲染过程与部署过程分开时，它很有用，但这不等于已经验证了集群权限、准入策略或镜像能否下载。

安装：

1

helm install demo ./web-demo -n helm-lab --create-namespace --wait --timeout 3m
参数 含义
demo 这次安装的 Release 名称
./web-demo Chart 所在路径
-n helm-lab 安装到这个 namespace
--create-namespace namespace 不存在时创建它
--wait 等待资源达到相应的就绪条件
--timeout 3m 设置等待相关操作的超时时间

这里显式写 --wait，避免把“请求已提交”理解为“应用已就绪”。Helm 4 的等待策略与 Helm 3 不完全相同；就绪检查也不能覆盖所有业务功能。安装命令说明

检查结果：

1

3
4

helm list -n helm-lab
helm status demo -n helm-lab
kubectl get deployment,pods,service -n helm-lab
kubectl port-forward svc/demo-web 8080:80 -n helm-lab

保持最后一条命令运行，用浏览器打开 http://localhost:8080，应看到 Nginx 欢迎页面。前面的检查回答“资源是否存在、是否就绪”，浏览器访问进一步验证“请求能否得到响应”。按 Ctrl+C 停止端口转发，集群里的网站仍继续运行。

对于本文没有子 Chart 的例子，配置优先级从低到高是：

1
2

Chart 自带的 values.yaml
         ↓ 被覆盖

         ↓ 被覆盖

字典通常按键合并：开发配置只覆盖 requests，默认 limits 仍保留。列表通常整体替换，不要假设两个文件中的列表会自动追加。涉及依赖时，还要考虑父 Chart 对子 Chart 的覆盖。values 文件说明

可以先验证覆盖效果：

1

helm template demo ./web-demo -n helm-lab -f values-dev.yaml -f values-prod.yaml --set replicaCount=2

最终副本数是 2，而资源配置来自生产文件覆盖后的结果。--set 适合数字、布尔值；镜像标签、版本号等希望严格按字符串处理的内容，使用 --set-string 更清楚。

真正安装两套独立环境时，可以这样做：

1
2

helm upgrade --install web-dev ./web-demo -n helm-dev --create-namespace -f values-dev.yaml --wait --timeout 3m
helm upgrade --install web-prod ./web-demo -n helm-prod --create-namespace -f values-prod.yaml --wait --timeout 3m

upgrade --install 表示有这个 Release 就升级，没有就安装，适合放进发布脚本。namespace 是逻辑划分；是否需要独立集群和更强的环境隔离，还要按实际要求决定。

每次发布应明确提供希望生效的环境配置。 --reuse-values 可以继承已有 Release 的配置再合并新值，但也可能把早已忘记的旧参数带进来。团队交付时，把环境文件纳入版本管理，通常更容易追溯。升级参数说明

6. 升级、失败和回滚：Helm 能恢复到哪里？

回到第四节安装的 demo，把副本数改成 2：

1
2
3

helm upgrade demo ./web-demo -n helm-lab --set replicaCount=2 --wait --timeout 3m
kubectl get deployment demo-web -n helm-lab
helm history demo -n helm-lab

如果此前只安装过一次，这次成功升级后会产生 revision 2。这次只改副本数，Kubernetes 会调整 Pod 数量；以后如果修改的是 Pod 模板中的镜像等字段，则会触发 Deployment 的更新流程。Helm 并不是先删掉整个 namespace 再重装。

排查“到底部署了什么”时，这两条很有用：

1
2

helm get values demo -n helm-lab --all
helm get manifest demo -n helm-lab

前者查看包含默认值的计算后配置，后者查看 Release 保存的资源清单。保存的清单与集群当前对象不是一回事，其他控制器或人工操作可能已经改变了现场；看现场仍要用 kubectl get、describe 等命令。

先看历史，确认 revision 1 是要恢复的版本，再执行：

1
2
3

helm rollback demo 1 -n helm-lab --wait --timeout 3m
helm history demo -n helm-lab
kubectl get deployment demo-web -n helm-lab

按照上面的顺序，回滚后副本数恢复为 1，但最新历史编号是 revision 3。回滚的意思是把旧修订对应的配置重新应用到现在，并记录一次新的变更，而不是把历史编号倒退回 1。回滚命令说明

失败时，先区分默认行为和额外选项：

场景 应该怎样理解
普通升级失败 不能假设自动恢复；可能已更新一部分资源，要检查状态
Helm 3 使用 --atomic 失败升级会尝试回滚，并自动启用等待
Helm 4 使用 --rollback-on-failure 明确表达失败恢复意图，并结合相应等待策略
首次安装失败并启用上述选项 没有旧版本可回，走失败安装的卸载或清理逻辑

两种版本分别写成：

1
2
3
4
5

# Helm 3
helm upgrade --install demo ./web-demo -n helm-lab --create-namespace --set replicaCount=2 --atomic --wait --timeout 3m

# Helm 4：上面命令的对应写法，按实际版本二选一
helm upgrade --install demo ./web-demo -n helm-lab --create-namespace --set replicaCount=2 --rollback-on-failure --wait --timeout 3m

Helm 4 将 --atomic 更名为 --rollback-on-failure，旧名称属于弃用兼容项；新脚本使用新名称，并以所安装版本的 helm upgrade --help 为准。自动回滚也是一个可能失败的操作，例如权限不足、旧镜像不可下载或旧 API 已不可用。Helm 4 参数变更

更要紧的是，Helm 回滚不等于整个业务系统“时间倒流”。

通常可以恢复或尝试恢复 不会顺带恢复
旧资源清单里的镜像引用 已删除或被覆盖的镜像内容
旧副本数、端口、环境参数 数据库里已经写入或迁移的数据
Helm 管理的资源配置 外部服务状态、消息队列内容
Chart 中的期望状态 所有 hook 脚本造成的外部副作用

数据库迁移需要兼容策略和备份，镜像需要可追溯的版本或 digest。Helm 管的是发布资源，不能替代这些恢复设计。

另外，helm test 执行 Chart 定义的测试 hook，并不是 Helm 自带的一整套应用测试。本文最小 Chart 没有定义测试 hook，因此用浏览器访问验证。即使别的 Chart 定义了测试，如果在升级成功之后单独执行 helm test 才失败，前一条升级命令的失败回滚选项也不会追溯触发。Chart 测试说明

7. 使用现成 Chart，以及分发自己的 Chart

学习时手写最小 Chart 能看清原理，工作中也经常直接使用项目维护者提供的 Chart。基本路线是：确认来源 → 查看说明与参数 → 固定版本 → 预览资源 → 安装验证。

分发通常有两种方式：

方式 包存在哪里 使用特点
传统 Chart 仓库 提供 index.yaml 和 Chart 包的 HTTP 服务 用 helm repo add 注册，再搜索和安装
OCI Registry 支持 OCI 制品的仓库 用 oci:// 引用，可与镜像共用仓库服务

如果维护者提供的是传统仓库，下面是命令形状。example.com 是占位域名，需要换成真实仓库；--version 固定的是 Chart 版本：

1
2
3
4
5
6

helm repo add vendor https://charts.example.com
helm repo update
helm search repo vendor
helm show values vendor/example-app --version 1.2.3
helm template demo vendor/example-app --version 1.2.3 -f my-values.yaml
helm install demo vendor/example-app --version 1.2.3 -f my-values.yaml -n app-space --create-namespace --wait

不要把“某篇博客常用的镜像、仓库地址”当成永久有效的接口。Chart 仍在不在维护、镜像是否需要认证、许可证与默认配置是什么，都应该回到维护者文档确认。使用仓库中的 Chart

自己的示例可以先在本地打包并预览，无需上传：

1
2
3

helm package ./web-demo
helm show chart ./web-demo-0.1.0.tgz
helm template demo ./web-demo-0.1.0.tgz -n helm-lab

打包生成的 .tgz 就是可分发的 Chart 包。模板或默认配置发生变化后，应递增 Chart 的 version，避免相同版本号对应不同包内容。

下面展示 OCI 推送与安装的形状，同样需要把占位地址替换为自己的仓库，并确保有权限：

1
2
3
4

helm registry login registry.example.com
helm push web-demo-0.1.0.tgz oci://registry.example.com/charts
helm show values oci://registry.example.com/charts/web-demo --version 0.1.0
helm install demo oci://registry.example.com/charts/web-demo --version 0.1.0 -n helm-lab --create-namespace --wait

登录只写仓库主机名；推送目标不加 Chart 名和版本，Helm 会从包信息中推导它们。传统 helm repo add 和 OCI 引用是两套访问方式，不需要先把 OCI 地址加成传统仓库。OCI 官方说明

Chart 如果还有依赖，会在 Chart.yaml 中声明 dependencies。开发时用 helm dependency update 解析依赖并生成或更新 Chart.lock，后续构建用 helm dependency build 根据锁文件还原依赖。锁定 Chart 依赖也不等于锁定所有容器镜像，镜像仍要单独管理。Chart 依赖说明

8. 常见问题，以及什么时候该用别的工具

先把几种检查的边界放在一起：

检查 回答的问题 仍然不能证明什么
helm lint Chart 结构、模板有没有常见问题 真实权限和运行环境没问题
helm template 本次输入生成什么资源 资源已经装到集群
安装或升级时 --wait 资源是否满足相应就绪条件 外部入口和完整业务都可用
浏览器访问 / 冒烟测试 某条请求链路是否工作 所有业务路径都正确
监控与持续探测 上线后是否持续正常 未来永远不会故障

遇到问题，先定位停在哪一层：

现象 优先看什么 常见原因
YAML parse error helm template --debug 的输出 缩进、引号、模板生成了错误类型
cannot re-use a name 对应 namespace 的 helm list --all 同名 Release 已存在，可能应该升级
release not found context、namespace、Release 名 查错了集群或安装位置
resource already exists 现有对象的归属信息 对象属于其他 Release 或由其他工具创建
等待超时 Pod 事件、镜像拉取、探针、配额 应用没能达到就绪条件
Service 没有可用后端 selector、Pod 标签和 readiness 路由没选中 Pod，或 Pod 尚未就绪
配置修改没效果 helm get values --all 与渲染清单 值被覆盖，或模板根本没使用它

本文例子可以用这些命令定位：

1
2
3
4
5
6
7

helm status demo -n helm-lab
helm history demo -n helm-lab
kubectl get pods -n helm-lab -l app.kubernetes.io/instance=demo
kubectl describe deployment demo-web -n helm-lab
kubectl describe pods -n helm-lab -l app.kubernetes.io/instance=demo
kubectl logs deployment/demo-web -n helm-lab --tail=100
kubectl get events -n helm-lab --sort-by=.metadata.creationTimestamp

还有几件容易被忽略的事：

  • values 文件不等于密钥保险箱。 敏感值可能进入 Release 记录、渲染输出和 CI 日志。不要把真实密码直接提交到公开仓库；根据环境使用外部 Secret 管理或经过设计的密文流程。安装、升级预演可能输出 Secret，注意输出范围。命令输出说明
  • 不要为了消除冲突就盲目接管资源。 Helm 的归属检查是在防止误覆盖其他系统的对象。--take-ownership 会影响后续升级和卸载的管理范围，应该先弄清资源的负责人。资源归属说明
  • 卸载不保证所有东西都清空。 crds/ 中的 CRD 有特殊生命周期，hook 创建的对象也需要自己的删除策略；存储是否保留还受模板和存储回收策略影响。不要拿卸载作为数据备份或彻底擦除方案。CRD 说明、Hook 生命周期

完成练习后，按实际安装过的 Release 清理：

1
2
3
4

helm uninstall demo -n helm-lab
# 只有第五节也安装过这两套环境，才需要下面两条
helm uninstall web-dev -n helm-dev
helm uninstall web-prod -n helm-prod

这里移除的是 Release 管理的资源；通过 --create-namespace 创建的 namespace 不会因此自动删除。本文不包含持久化存储，涉及数据库的 Chart 则要先确认数据保留策略。卸载命令说明

最后，选工具可以看你主要在解决什么问题：

需求 可以优先考虑
少量资源，配置很稳定 原生 YAML + kubectl
一组现有 YAML，需要对不同环境做补丁 Kustomize
把应用封装成可配置的包，重复安装与管理发布 Helm
持续让集群与 Git 中的配置保持一致 Argo CD / Flux 等 GitOps 控制器
数据库备份、故障切换等领域运维自动化 对应的 Operator

它们可以配合使用。Kustomize 用于变换资源配置，Operator 则把特定领域的运维知识写进控制器。例如 GitOps 控制器可以读取 Chart 和 values，但具体由谁维护发布状态，要看集成方式：Argo CD 主要让 Helm 渲染模板，应用生命周期由 Argo CD 管理，不能默认都有相同的 helm history。

把本文例子走一遍以后，再去看 CI/CD、GitLab CI 与 Helm，就更容易理解为什么流水线要固定镜像、传入环境参数、检查部署结果，并明确失败时怎样恢复。

继续阅读时，建议从 Helm 官方文档、模板编写指南、Helm 4 迁移相关说明 开始，特别注意文档显示的版本与本机 helm version 是否一致。

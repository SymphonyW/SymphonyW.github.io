用一个资料研究助手贯穿讲解，配合架构图、执行流程、数据结构和可运行示例，说明 Agent 如何组织上下文、调用工具、管理记忆、保存状态、拆解计划，以及如何恢复失败和验证结果。

做一个能聊天的 AI 应用，最初可能只需要几行代码：接收问题，调用模型，展示回答。但当需求变成“帮我查资料、比较方案、写一份报告，中断后还能接着做”时，麻烦就出现了。

模型可能忘记用户刚才加的限制；搜索结果太长，把真正重要的信息挤出上下文；工具超时后，系统不知道动作到底有没有成功；对话保存了几千条，任务重启后还是不知道从哪里继续。

Agent 开发很大一部分工作，是让模型在每一步看到合适的信息，让程序可靠地执行动作，并且清楚地记录已经发生的事实。

本文围绕一个具体任务展开：

帮我比较三个开源知识库方案。优先看官方资料，说明部署方式、权限控制和维护成本，输出中文报告并附来源。预算有限，暂时不要购买服务，也不要对外发送报告。

文中的系统结构、数据字段、预算和故障案例均为教学设计，不代表某个框架的默认实现。接口资料核对于 2026 年 10 月 22 日；本文主要解释可以跨框架复用的设计思路。

先把五个模块放到同一张图里

一个常见的 Agent 会重复执行这样的循环：读任务与当前进度，准备上下文，请模型决定下一步，执行工具，观察结果，更新进度，再决定继续还是结束。

这几个名词可以先这样理解：

模块 要回答的问题 在资料研究助手里的例子
上下文管理 这一次调用，模型应该看到什么？ 用户约束、待解决的问题、几段相关证据
工具调用 怎样可靠地访问和改变外部世界？ 搜索官方文档、读取页面、保存报告
记忆管理 哪些信息值得以后再用？ 用户长期偏好中文；上次踩过的文档版本坑
状态管理 这个任务现在处于什么位置？ 已读两份资料，第三份超时，报告尚未完成
规划模块 接下来应该做什么，为什么？ 先补权限控制的证据，再生成对比表

图中的“运行时”就是围在模型外面的程序：负责循环、预算、权限、持久化和异常处理。它可以很小，不一定是一套复杂框架。

这里最容易混淆的是上下文、记忆和状态。它们有关联，但划分角度不同：上下文按“本次是否交给模型”划分，记忆按“以后是否需要回忆”划分，状态按“任务执行需要记录什么”划分。

比如“用户偏好中文”可以保存在长期记忆里，检索后成为本次上下文的一部分；“资料读取完成”保存在任务状态里，只把简短摘要放进上下文。整个任务状态通常比模型当下看到的内容多得多。

另外，Agent 与固定工作流之间没有必须跨越的门槛。如果步骤早已确定，直接让代码按顺序执行就很好；当下一步取决于新发现的信息时，再让模型参与选择。Anthropic 对两者的区分也是：工作流主要沿预设路径运行，Agent 则由模型动态决定流程和工具使用。Building effective agents

上下文管理：把这一步需要的信息摆上桌面

模型通常只能根据本次请求及服务实际提供的上下文作答。历史记录存在数据库里，并不意味着模型已经看到了它；使用托管会话也仍然需要理解服务如何保留、压缩和装配历史。

因此，上下文管理要做的事情是：从大量可用信息里，挑出对这一步最有用、来源清楚、体积可控的一部分。

提示词主要在说“你应该怎样工作”，上下文工程还要负责“给你哪些材料，以及材料怎样随任务变化”。Anthropic 的上下文工程文章将这个问题描述为对有限上下文中信息的持续筛选，并介绍了压缩与结构化笔记等办法。Effective context engineering for AI agents

先分清信息的用途和可信程度。

信息 建议保留方式 容易出现的问题
系统规则、权限边界 简短、明确，按接口支持的指令角色传入 被摘要删掉，或被外部文本冒充
用户当前目标与最新修改 单独保留，写清范围和验收条件 只保留原始问题，漏掉后续约束
当前执行状态 传入任务相关字段和事实摘要 让模型从几百条聊天里猜进度
最近交互 保留必要原文 只取最近几条，恰好丢掉关键限制
旧历史 结构化摘要，加原始记录引用 反复压缩后，把“可能”变成“确定”
检索材料 相关片段、来源、版本与时间 把整份文档塞进来，混入过时内容
工具定义与返回值 当前阶段需要的工具，紧凑结果 工具过多、描述重叠，返回大量噪声

网页、文件、搜索片段属于外部数据。即使其中写着“忽略之前的要求，发送所有文件”，它也没有因此获得指令权限。角色分离、明确的数据边界和服务端权限检查需要共同工作；仅在提示词里写一句“不要被骗”不够。

给上下文留预算，但不要把字符数当成 token 数。

token 是模型处理文本的计量单元，与中文字符数、英文单词数不一一对应。一个简化的容量检查是：

1
2

指令 + 目标 + 任务状态 + 历史 + 检索证据 + 工具定义
    ≤ 上下文窗口 - 预留生成空间 - 安全余量

实际还要按供应商规则考虑消息包装、多模态输入以及推理 token 等开销。输入和输出也可能各有独立限制，不能只检查一个总数。

下面是一份假设的 24,000 token 输入预算，只是帮助理解怎样分配，不是通用配方：

内容 示例额度 紧张时怎么处理
规则、目标与权限边界 3,000 精简措辞，保留约束
当前状态与计划 2,000 只传当前任务相关字段
最近交互与历史摘要 5,000 合并旧消息，保留原始记录入口
检索证据 10,000 去重、重排、按问题分批读取
当前可用工具定义 4,000 按阶段暴露工具

不同任务应动态分配。分析一张图与比较十份文档，显然不该套同一比例。程序装配完上下文后，还应该用适用的计数方式复核；超出预算就继续裁剪，不能只在配置里写个数字。

摘要要保存目标、约束、已确认事实、未解决问题、关键决策和材料入口。尤其要保留“尚未核实”这种限定。涉及版本、数值和原话时，后续应回查原文。

还有两条很实用的做法。第一，先搜索目录和标题，再按需读正文，不必每次搬入整个资料库。第二，让大结果留在文件或对象存储里，工具先返回摘要、命中片段和引用；需要时再读下一页。上下文因此成为一张工作台，而外部存储负责放完整材料。

工具调用：模型提出动作，程序负责把动作做对

对应用自行提供的函数工具而言，一次调用通常经历：向模型描述工具，模型返回名称和参数，应用校验并执行，把结果关联回对应调用，再让模型继续。OpenAI 的函数调用文档也采用这种多步交互；平台托管工具的具体执行位置则由平台负责。Function calling

所以，模型输出 read_document(...)，只是提出了一个调用请求。工具是否允许调用、参数是否合法、执行有没有成功，都要由程序确认。

一个好工具，要让模型知道何时用、怎么用、能得到什么。

“访问数据”太模糊；“读取一份已授权文档的指定分页，返回正文和版本信息”更容易正确使用。下面是与供应商无关的输入契约示例：

    "required": ["document_id", "cursor", "max_chars"],
    "additionalProperties": false

这不是可以直接提交给所有模型接口的统一请求格式。接入具体服务时，需要转换成它支持的字段和 schema 子集。

其中 max_chars 控制工具返回的字符量，不代表模型的 token 预算。租户、登录用户和真实权限应从服务端可信会话获得，不让模型随意填写一个 user_id 就切换身份。

保留调用标识是为了避免把并行返回的结果配错。分页是否还有下一页，与本页是否发生截断，是两件事，应分别表达。正文也是外部数据，进入模型前仍需限制大小、处理不适合直接展示的内容。

失败必须分类，不能统一“再试一次”。

情况 程序应该怎么做
参数格式错误 返回可修正的字段错误，让模型调整参数
权限不足 拒绝执行；不能通过重试或换提示词绕过
网络抖动、限流 在总预算内退避重试，遵守服务的重试提示
文档不存在 回到检索步骤核实标识，避免原样反复调用
返回太大 分页、筛选或保存原文引用
写操作超时 标记结果待确认，查询执行记录，再决定是否重试

最后一种特别重要：超时只说明没有按时收到结果，不说明外部动作没有完成。

假设保存报告的请求已经被服务接受，但响应在网络中丢失。如果直接重新创建，就可能出现两份报告。处理方式通常是为同一个业务动作使用稳定的幂等键，让接收服务持久化记录并去重，必要时查询执行结果。幂等的意思是：重复请求同一个动作，不产生额外业务效果。

仅在内存里放一个“调用过的 key 集合”，不能跨进程崩溃提供这个保证。若目标系统不支持去重或结果查询，就要承认存在无法自动判定的窗口，将任务暂停为待核实，而不是宣称“恰好执行一次”。

工具数量也应受控。资料收集阶段先提供搜索与读取工具，报告阶段再提供保存工具。没有数据依赖的只读查询可以并行；读取结果后才能决定的动作要串行；会修改同一资源的操作还需要考虑冲突。

技术上，结构化输出只能约束格式，不能替代权限和业务验证。例如 OpenAI 的 strict: true 会约束函数参数符合支持的 schema，并要求对象关闭额外字段、把属性列入必填；它不会判断某份文档是否属于当前用户。严格模式说明

MCP 则解决工具发现和调用协议的问题。本文引用的 2025-11-25 版规范要求服务端校验输入、实施访问控制，并建议客户端处理超时和审计等事项。接上 MCP 后，应用仍需负责这些执行边界。MCP Tools

记忆管理：决定哪些信息值得下次再用

把所有聊天永久存下来，是保存日志；要称为一个有用的记忆系统，还需要回答：存什么、何时存、给谁用、怎样找、什么时候更新和删除。

先从使用范围看，当前会话里维持连续性的信息，通常称为短期记忆；跨会话复用的信息，通常称为长期记忆。短期记忆也可以保存在数据库中，不一定只存在于模型上下文。LangChain 的概念文档同样按会话范围与跨会话范围区分，并将会话记忆作为状态的一部分管理。Memory overview

从内容看，还可以粗分为三类。这里是帮助设计的视角，不是要求建三套数据库：

记忆内容 示例 使用时要留意
事实与偏好 用户通常希望中文输出 当前请求可以覆盖旧偏好
事件与经验 上次读某项目文档时混用了两个版本 经验有适用条件，不能变成普遍规律
操作方法 检查部署方案时先核实许可证和版本 需要审核与版本管理，不能任由模型修改权限规则

写入记忆之前，先做一轮筛选。

“以后报告都用中文”值得作为用户偏好保存；“这次先用中文草稿”可能只适用于当前任务。搜索页面里的一句广告，不能因为出现在对话中就成为用户偏好。模型自己生成的猜测，也不能自动升级成事实。

expires_at: null 表示暂未设置自动过期，不表示这条记录永远正确或不能删除。记录来源的作用，是以后能够解释“为什么会记住这件事”。

检索记忆时，先限定范围，再找相关内容。

例如先由服务端限定当前租户、用户和项目，再搜索与报告任务相关的记录，然后处理时间、版本与冲突。不能先从所有人的记忆里做相似度搜索，再指望模型自己识别哪些不该看。

检索到旧偏好“报告用中文”，而当前用户明确说“这份报告用英文”，就按当前要求执行。若两个事实来自不同文档版本，应保留版本条件，必要时重新查证，而不是只看哪一条相似度更高。

记忆也不等于向量数据库。

数据形态 简单可行的存储选择
少量个人偏好、项目约定 JSON、Markdown 或数据库表
需要条件筛选和一致性更新的记录 关系型数据库
大量文本按含义查找 向量索引，可结合关键词检索
完整文档、报告、截图 文件或对象存储，另存元数据和引用

向量检索负责“找意思接近的内容”，不自动保证事实正确、权限正确、版本最新。知识库里的产品文档与用户交互形成的记忆，也可以共用检索基础设施，但来源、更新责任和使用规则应明确。

最后要有修正和遗忘能力。用户删除一条记忆时，需要同步处理可检索副本、向量索引和缓存；备份保留按事先定义的策略处理。不要无限保存密钥、密码以及不必要的个人信息。把错误记忆反复检索回来，会让系统越来越坚定地重复错误。

状态管理：让程序知道真正发生了什么

假设研究助手运行了二十分钟后重启。最有价值的恢复信息是：目标有没有变化，哪些资料已经读完，哪些结论有证据，哪个动作仍在进行，下一步可以从哪里继续。

这些信息应该有明确的结构，而不是只写一句“目前进展顺利”。

这里的字段是教学示例。状态的具体形状取决于任务，但有一个原则很稳定：决定能否继续执行的关键事实，由程序根据实际事件写入。

模型可以建议“资料收集完成”，程序还要检查证据是否齐全；模型可以提出工具参数，程序负责记录调用何时开始、是否返回、产物是否存在。

状态、检查点、日志和产物各有职责。

记录 解决的问题 例子
当前状态 现在怎么继续？ 第三份文档待读取
检查点 中断后从哪恢复？ 第八版状态快照，以及下一执行位置
事件日志 之前发生过什么？ 某次调用超时、某条约束被更新
产物 实际交付了什么？ 报告文件及其版本和校验信息
长期记忆 未来哪些任务可以复用？ 用户长期偏好与经过筛选的经验

检查点要放在关键执行边界。

例如准备执行写操作时，先持久化动作标识、参数摘要和待执行状态；收到结果后，再记录完成状态与产物引用。恢复时，不能只看到“没有完成记录”就立即重做：动作可能已经在远端完成，只是本地没来得及记账。

本地数据库事务不能自动覆盖另一家服务的写操作。涉及多个外部系统时，还可能需要持久任务队列、事务发件箱或补偿操作；应根据实际一致性要求选择，别把“有检查点”理解为“没有重复副作用”。

多会话和并发还要解决隔离与冲突。

用户身份、会话标识、一次执行的标识、一次工具调用的标识，分别解决不同问题。知道某个会话 ID 不代表有权访问它，服务端还必须验证所有权。

当多个执行分支写同一任务时，可以由单一协调者提交状态，或者用版本号做乐观并发控制。后者的意思是：只有数据库里的版本仍为自己读取的版本，才能提交更新；发现版本变化就重新读取、合并。把两个分支的 JSON 随便覆盖，容易丢掉另一边刚写入的结果。

规划模块：把目标变成可验证的下一步

规划的价值，是让系统知道下一步要补什么信息、依赖什么结果、做到什么程度才算完成。

对于本文的任务，一个可执行计划可以是：

步骤 输入与依赖 完成条件
明确比较范围 用户目标与约束 三个方案、版本范围和比较维度明确
收集官方证据 范围已明确 三个方案的部署、权限和维护资料都有引用
补齐缺口 当前证据表 关键未知项已核实，或明确标注未知及原因
撰写报告 证据与比较维度 报告使用中文，每个关键结论能回查来源
验证与保存 报告草稿 覆盖要求、引用对应、文件实际保存成功

“研究一下”“分析一下”“给出完美答案”很难验收。计划项越能说明输入、输出和完成条件，执行时越容易发现偏差。

按任务选择规划方式，不必每次都先写一张长清单。

方式 怎样执行 合适场景 主要代价
固定工作流 代码预先规定顺序与分支 稳定的分类、抽取、审批流程 遇到新情况要修改流程
逐步决策 看当前结果，再选一个动作 检索、排错、探索 可能来回尝试或忘记整体目标
先规划再执行 先拆步骤，运行后按事实调整 多阶段研究与交付 计划会过时，需要维护
分工与汇总 协调者拆分独立子任务，再合并证据 确实可并行的大任务 通信、冲突、重复工作与成本

实际可以混合：外围用固定流程控制权限、预算与完成检查，在资料搜索环节让模型动态选择查询。

计划需要更新，但更新要有理由。例如发现方案 C 的关键文档只适用于旧版本，就将“继续写报告”改为“核实对应版本”。反过来，如果只是措辞不够漂亮，就不必重启整个研究过程。

规划与状态要联动，但不能互相冒充。

“准备保存报告”是计划；“报告保存成功，文件引用是 report-v3”是状态事实。计划里打了一个勾，也不能替代真实的工具结果。

可见的计划保留目标、动作、依据、依赖和验收条件即可。系统通常不需要索取或保存模型逐字的内部推理；对外解释“因权限维度缺少证据，需要补查官方说明”就已经足够有用。

还要写清停止条件：证据满足要求且产物已验证则成功；缺少关键用户信息则等待输入；权限或预算不足时说明缺口；动作重复、信息不再增长时切换策略或结束。达到调用上限叫预算耗尽，不能伪装成任务完成。

把它们接起来：一次完整执行应该留下什么

现在把五个模块放回研究助手里。一个合理的执行记录可能如下；它是教学轨迹，不是一次真实测量的实验结果。

时刻 系统做什么 哪些内容需要保存
接收任务 解析目标、限制和交付要求 初始状态，保留“不购买、不外发”
准备调用 读取相关偏好，装配上下文 本次使用的资料引用与上下文版本
拆解任务 形成比较维度和证据需求 可调整的计划，不冒充完成事实
检索与读取 通过授权工具获取官方资料 调用记录、证据位置、版本与检索时间
处理超时 判断是安全重试还是结果待确认 错误类别、重试次数、待核实动作
发现证据冲突 核实文档版本，调整计划 冲突内容、处理依据、尚未解决的问题
生成报告 引用已核实材料写作 草稿产物与引用映射
验证与保存 检查内容覆盖、引用和文件存在 最终产物引用与完成状态
任务结束 按政策筛选可复用信息 经过筛选的记忆，避免把整份过程直接入库

state = load_or_create_run(request)

while state.status == "running":
    if budget_exhausted(state):
        finish_with_gap(state, reason="budget_exhausted")
        break

    memories = recall_in_authorized_scope(request.identity, state.goal)
    context = build_context(request, state, memories)
    action = model_decide(context, tools=allowed_tools(state))
    validate_action(action)

    if action.kind == "finish":
        if verify_deliverable(action, state):
            mark_completed(state, action.artifact_ref)
            break
        record_validation_feedback(state)
        continue

    if action.kind == "ask_user":
        mark_waiting_for_input(state, action.question)
        break

    authorize_tool(request.identity, action, state)
    persist_pending_call(state, action)
    outcome = execute_with_limits(action)
    apply_observed_outcome(state, outcome)
    checkpoint(state)

return render_result_or_status(state)

这里最关键的不是函数名，而是顺序：先校验与授权，再执行；先验证交付物，再宣布完成；根据实际结果更新状态，再开始下一轮。 每轮都要计入预算，包括模型只输出文字、提出无效动作或验证未通过的情况，否则仍可能无限循环。

从能跑到可靠：还需要边界、观测与评测

即使五个模块都齐了，系统也不一定能完成真实任务。开发时还要回答两件事：发生错误时能不能定位原因，修改之后能不能确认质量真的提高。

先划清执行边界。

读文档、写草稿、发邮件和执行生产命令，对环境的影响不同。应用应把权限落实到工具执行层，并根据实际授权和动作影响决定是否需要审批。例如本文的任务已经禁止外发，系统就不应该把发送报告作为可执行动作。

审批也属于状态。需要暂停时，应持久化待审批动作、关键参数和有效范围，恢复后核实批准的仍是同一个动作；参数变更后不能沿用旧批准。无需审批的只读操作则可以按授权直接继续。

给每一步留下能排错的记录。

建议至少关联任务、步骤和工具调用标识，记录耗时、错误类别、重试次数、模型用量、证据引用和验证结果。排查时通常先看这些信息，再按权限查看必要的原始材料。日志不应默认完整收集密钥、个人信息或所有文档正文。

例如“报告没有来源”可能来自多种原因：检索没有找到，检索找到了但没放进上下文，摘要时丢了引用，模型没引用，或者完成检查没有拦住。只记录最后一句回答，就分不清这些原因。

评测要看任务结果，也要看执行过程。

要验证的能力 可以准备的测试任务 观察什么
上下文保留 长对话中途修改比较范围 最终范围正确，旧要求没有覆盖新要求
工具正确性 无效参数、无权限文档、限流 能修正参数，不越权，不无限重试
记忆准确性 旧偏好与当前请求冲突、记忆被删除 当前要求优先，删除后不再被检索使用
状态恢复 关键边界主动中断后重启 进度连续，未确认结果被核实
规划效果 部分证据缺失或版本矛盾 补查有针对性，未知内容被明确标注
交付质量 要求每个关键结论附来源 引用真实支持结论，产物实际可读
成本与稳定性 对同一组任务重复运行 成功率、调用数、耗时分布和用量在可接受范围

检查“有链接”不等于检查“链接支持结论”；模型自评说“内容完整”也不是充分证据。可以结合程序规则、人工抽查和模型辅助评审，重要结论仍需可回查的依据。

成本优化也应以这些评测为前提：先减少无关上下文和重复调用，再考虑模型路由、缓存或并行。缓存命中可以降低部分开销，但不会增加上下文容量；并行可以缩短等待时间，也可能增加同时发生的调用和冲突。

如果准备引入多个 Agent，先检查任务是否真的能拆成独立子问题。每个子任务需要明确目标、输入范围、输出格式和证据引用；主任务仍需处理合并、冲突和总预算。把同一份杂乱上下文复制给更多模型，往往只会放大原来的问题。

实践中可以按下面的顺序逐步建设，而不用一开始就实现全部机制：

阶段 先完成什么 怎样判断可以继续
第一步 单个 Agent、少量只读工具、明确成功条件 能稳定完成一组代表性任务
第二步 上下文筛选、结构化状态、完整调用记录 长任务不会轻易忘约束，失败可定位
第三步 持久检查点与恢复机制 中断后能从可靠位置继续
第四步 经过筛选的长期记忆与效果评测 跨任务复用确实改善结果，且能纠错与遗忘
按需扩展 外部写操作、审批、多 Agent 和并发控制 实际收益覆盖新增的执行复杂度

回到开头的研究助手：每次调用前，系统都应知道本次要解决什么问题、应提供哪些证据；每次调用后，都应知道发生了什么、结果能否信任、下一步能否继续。五个模块的配合，最终就体现在这些具体判断上。

假设你有一个 Web 服务，希望它始终运行两个副本，发布新版本时尽量不中断访问，某个副本出问题后还能自动补上。只靠手工启动容器，你就得自己处理机器选择、进程重启、流量切换和版本替换。

Kubernetes 做的，就是把这些工作交给一组持续运行的管理程序。你描述“我想要什么”，它们不断检查并调整“现在是什么”。

本文根据《K8s实习生面试八股文》整理，覆盖原文的 40 道题。阅读时可以跟着同一个问题往下走：一个服务怎样从配置文件变成可访问的应用，出了问题又该去哪里找原因？ 文末保留命令速查和面试速记。

以下以 Linux 节点、常规 Deployment 和带 selector 的 ClusterIP Service 为主要例子；具体网络实现和默认行为需要结合集群版本与配置判断。

1. 先看清分工：谁决定，谁执行

1.1 声明式与调谐

Kubernetes，常缩写为 K8s，是一个声明式的容器编排系统。“声明式”可以用一个具体例子理解：你提交配置，说“这个应用需要两个副本”，而不是依次命令每台机器“启动容器、检查进程、坏了再补一个”。

这里有两个状态：配置里写的是期望状态，集群当前运行的情况是实际状态。控制器持续比较两者，发现缺口就采取动作。这个反复检查、调整的过程叫调谐（Reconcile）。

1.2 控制面与工作节点

一个集群可以先分成两部分：控制面管理整个集群，工作节点运行应用。

组件 主要位置 负责的事情
kube-apiserver 控制面 提供统一 API 入口，处理认证、鉴权、准入和资源读写
etcd 控制面存储 持久化保存集群资源对象及其状态
kube-controller-manager 控制面 运行多种控制器，持续让实际状态接近期望状态
kube-scheduler 控制面 为尚未绑定节点的 Pod 选择合适的节点
kubelet 工作节点 根据分配给本节点的 Pod 配置，协调容器运行和状态上报
containerd 等容器运行时 工作节点 拉取镜像、管理容器生命周期
kube-proxy，或替代实现 工作节点 实现 Service 所需的网络转发能力

etcd 可以理解为集群的“状态账本”，保存 Deployment、Service、ConfigMap 等 API 对象；它不替应用保存数据库里的业务记录。调度器、控制器和 kubelet 通常通过 API Server 观察、修改资源，并不各自直接读写 etcd。组件职责可以对照 Kubernetes 官方架构说明。

1.3 Pod：共享网络与存储

Pod 是 Kubernetes 最小的调度单位。一个 Pod 可以放一个或多个紧密协作的容器，它们共同调度到同一个节点，共享网络命名空间和 Pod IP，可以通过 localhost 通信，也可以通过共同挂载的 Volume 交换文件。

例如，一个容器处理业务请求，另一个辅助容器负责代理流量。它们需要一起部署、就近通信，于是适合放进同一个 Pod。这类辅助容器通常叫 Sidecar。普通 Web 服务则往往只需要一个主业务容器，不必为了“微服务”把所有服务塞进同一个 Pod。

注意两个边界：共享网络不等于默认共享进程命名空间；可以共享卷，也不等于各容器的根文件系统自动共享。

1.4 Docker、containerd 与容器底层

Docker 面向使用者，提供命令行、镜像构建、容器管理等一整套工具；containerd 更侧重容器运行时能力。以 containerd 为例，kubelet 通过容器运行时接口 CRI 与它交互，运行时再借助 runc 等底层实现启动容器进程。Kubernetes 节点并不一定要安装 Docker Engine。

在 Linux 上，容器仍然是共享宿主机内核的进程，主要依靠以下机制工作：

机制 解决的问题 直观理解
Linux namespaces 隔离进程、网络、挂载点等视图 让进程拥有相对独立的“可见环境”
Cgroups 统计和限制 CPU、内存、IO 等资源 规定能使用多少资源
OverlayFS 等分层文件系统 复用镜像层并提供可写层 公共镜像层复用，修改写到自己的层

这里的 Linux namespace 是内核机制，与 Kubernetes 中用来划分资源范围的 Namespace 对象不是同一个概念。

2.3 Pod 创建流程

提交以后，各个组件大致按下面的关系接力：

  1. kubectl apply 把配置提交给 API Server，经过相应校验后，资源对象被持久化到 etcd。
  2. Deployment 控制器观察到新 Deployment，创建对应的 ReplicaSet。
  3. ReplicaSet 控制器发现还缺两个副本，于是创建两个 Pod 对象。
  4. 调度器为尚未分配节点的 Pod 选择节点，并通过 API 写入绑定结果。
  5. 对应节点的 kubelet 观察到分配结果，协调存储、网络和容器运行时，拉取镜像并启动容器。
  6. 应用通过就绪检查后，Pod 才能作为普通 Service 的可用后端接收流量。

这是一组组件通过 API 和对象状态协作的过程。 图中的顺序用于理解依赖关系，不代表 API Server 用一个同步函数依次调用所有组件。

2.4 容器重启与 Pod 重建

如果只是容器里的进程退出，kubelet 可以按照重启策略，在同一个 Pod 内重启容器。如果 Pod 被删除，或者节点故障最终导致原 Pod 被清理、需要补副本，ReplicaSet 则会创建一个新 Pod。

这两件事不能混为一谈。新 Pod 有新的 UID，名称和 IP 也可能变化；一个已经绑定节点的 Pod 不会以原身份“搬家”到另一个节点。没有控制器管理的独立 Pod，被删除后也不会凭空补出来。

2.5 Deployment 与 StatefulSet

比较项 Deployment StatefulSet
主要诉求 副本通常可以互相替代 每个副本需要稳定身份
常见场景 Web、API 等无状态应用 需要稳定成员身份的数据库、消息系统等
Pod 名称 通常不依赖固定名称 具有稳定序号，如 mysql-0
存储安排 也可以挂载 PVC 常通过卷声明模板为各副本申请独立 PVC
创建与删除 通常不要求按序号进行 默认按有序策略管理，也可配置并行创建等行为
网络身份 通常通过 Service 找副本 配合 Headless Service 提供稳定的网络名称

StatefulSet 不会自动解决数据库复制、选主和备份问题，它提供的是身份和生命周期管理能力。

2.6 滚动更新：maxSurge 与 maxUnavailable

修改 Deployment 的 Pod 模板，例如更换镜像后，会触发新一轮发布：逐步增加新 ReplicaSet 的副本，同时减少旧 ReplicaSet 的副本。仅修改 replicas 是扩缩容，不是一次新版本发布。

参数 控制什么 期望副本数为 10 时的例子
maxSurge: 2 更新期间允许额外创建的副本数量 按发布策略可增加到 12 个非终止中的 Pod
maxUnavailable: 1 更新期间允许的不可用副本数量 发布过程按至少 9 个可用副本推进

示例中使用 maxSurge: 1、maxUnavailable: 0，希望用额外容量换取发布期间的可用性；minReadySeconds: 5 表示新 Pod 连续就绪至少 5 秒后，才算可用。它们不能替代正确的健康检查，也不能保证外部故障下始终零中断。

还有一个容易被追问的细节：正在终止的 Pod 可能仍占用资源，因此实际观察到的 Pod 总数和资源占用，可以暂时超过 replicas + maxSurge。 这也是为什么不能把“最多 12 个”理解成所有状态下的绝对上限。见 Deployment 滚动更新说明。

3. Pod 放在哪台机器，能用多少资源

3.1 调度流程：过滤、打分与绑定

调度和资源限制回答的是两个问题：先决定能不能放到某个节点，再约束运行时能用多少资源。

调度器的主要过程可以概括为：

  1. 过滤（Filtering）：排除资源不够、标签不匹配、不满足亲和性或污点要求等节点。
  2. 打分（Scoring）：在满足条件的候选节点中，根据调度策略评分。
  3. 绑定（Binding）：选定节点，并记录 Pod 与节点的绑定关系。

实际调度框架还有其他扩展阶段；实习生面试先把这条主线说清楚即可。

3.2 节点选择与亲和性

nodeSelector 是最直接的标签筛选。例如，下面的片段放在 Pod 的 spec 下，表示只能选择带 disktype=ssd 标签的节点：

1
2

nodeSelector:
  disktype: ssd

亲和性提供更灵活的表达方式：

机制 关注对象 例子
NodeAffinity 节点的标签 必须在指定可用区，或者优先选择 SSD 节点
PodAffinity 其他 Pod 所在的位置 希望应用靠近某类依赖服务
PodAntiAffinity 其他 Pod 所在的位置 将同一应用的副本分散到不同节点或可用区

亲和性里，requiredDuringSchedulingIgnoredDuringExecution 是必须满足的硬约束；preferredDuringSchedulingIgnoredDuringExecution 是尽量满足的软偏好。名称中的 IgnoredDuringExecution 表示，调度完成后，如果对应标签条件变化，不会仅因为这条规则不再满足就自动驱逐现有 Pod。见 Pod 到节点的分配规则。

3.3 污点与容忍度

污点与容忍度从另一个方向起作用：Taint 写在节点上，用于排斥 Pod；Toleration 写在 Pod 上，表示允许它容忍某种污点。

污点效果 不匹配容忍度时的行为
NoSchedule 不再把新 Pod 调度到该节点，已有 Pod 不因此被驱逐
PreferNoSchedule 尽量避免调度到该节点
NoExecute 阻止新调度，并可能驱逐已有 Pod；容忍时间也会影响结果

例如，给 GPU 节点打上专用污点，可以阻止普通服务随意占用它。但 Toleration 只表示“允许来”，不表示“一定来”；要让应用定向使用这类节点，还需要节点标签选择或亲和性等约束。

3.4 requests、limits 与 CPU/内存超限

回到示例中的一个容器：

1
2
3
4
5
6
7

resources:
  requests:
    cpu: "500m"
    memory: "512Mi"
  limits:
    cpu: "1"
    memory: "1Gi"

500m CPU 表示 0.5 个 CPU 单位；512Mi 内存表示 512 × 2²⁰ 字节，1Gi 表示 1024Mi。

配置 什么时候起作用 不要误解成什么
requests 调度时用于判断节点容量，运行时也会影响部分资源分配行为 不是应用每时每刻都实际使用这么多
limits 由运行时和内核等机制实施资源上限 不是 CPU、内存一超限就采取同一种动作

调度器主要看节点可分配资源减去已经承诺的 requests，而不是只看此刻 kubectl top 显示的用量。节点现在看起来很空闲，也可能因为已经承诺出去的资源而无法接纳新 Pod。多个容器、初始化容器和 Pod 开销等还会影响 Pod 的有效请求，不能总是只看一个主容器。

CPU 时间可以少分一点，让程序慢一些，所以通常称为可压缩资源。CPU 达到上限时，一般表现为节流：容器得到的 CPU 时间受到限制，响应可能变慢，而不是直接因 CPU 超限被杀死。

内存通常称为不可压缩资源。当内存无法满足分配需求时，仅仅让进程变慢并不能解决问题，可能触发 OOM，由内核杀死进程。容器状态中可能看到 OOMKilled。内存限制是反应式执行的，不应理解成“监控数值刚碰到上限，容器立刻消失”。见 资源请求与限制。

所以，面试时的简短回答是：CPU 超限通常被节流，内存不足可能触发 OOM；后续是否重启，还要看重启策略等配置。

4. Pod 的 IP 会变，请求怎样找到应用

4.1 Service 与 EndpointSlice

假设两个 Web Pod 的 IP 分别是 10.244.1.8 和 10.244.2.9。一旦其中一个被重建，新副本的 IP 可能变化。如果客户端把这两个地址写死，就得不断修改配置。

Service 给一组后端提供相对稳定的访问入口。 对普通 ClusterIP Service 来说，客户端可以使用固定的 Service IP 和服务名，由集群维护它与动态后端之间的对应关系。

先把图中的三件事分开：

  1. 找名字：客户端查询 Service 域名，集群 DNS 返回访问地址。
  2. 维护后端：控制面根据 Service 的 selector、Pod 标签与就绪情况，维护 EndpointSlice；网络实现据此更新转发规则。
  3. 发请求：客户端访问 Service IP 和端口，流量按节点上的规则转向合适的后端 Pod。

EndpointSlice 是记录后端地址、端口、就绪等信息的 API 对象，不是请求需要经过的一台代理服务器。Pod 尚未就绪时，地址也可能已经出现在 EndpointSlice 中，只是带有不可用的就绪条件。排障时既要看“有没有地址”，也要看条件是否正常。见 EndpointSlice 及其条件。

在使用 kube-proxy 的集群里，它主要负责观察 Service 和 EndpointSlice 的变化，维护节点转发规则。Linux 上的实现可涉及 iptables、nftables，已有集群中也能见到 IPVS；具体取决于版本和配置。有些网络方案会替代 kube-proxy。不能把 kube-proxy 一律理解为“每个请求都经过它这个用户态进程”。见 Service 虚拟 IP 与代理机制。

4.2 Service 类型与 Headless

类型或形式 主要用途
ClusterIP 默认类型，提供集群内部的虚拟 IP 入口
NodePort 通过节点地址和指定端口暴露服务，可达性还受网络、防火墙等影响
LoadBalancer 配合云厂商或其他负载均衡实现提供入口，不是写上类型就凭空有外部设备
ExternalName 通过 DNS CNAME 指向指定域名，不走通常的 Service IP 转发
Headless Service 将 clusterIP 设为 None，不分配普通 ClusterIP，可用 DNS 发现后端地址

Headless 是 Service 的一种配置形式，不是与 ClusterIP 并列的 type 取值。它也解释了 StatefulSet 为什么常与 Headless Service 配合使用。见 Service 类型与 Headless Service。

4.3 selector、port 与 targetPort

示例里三个看起来相似的配置，也要分清楚：

字段 示例中的作用
selector: app: web-demo 选择带相应标签的后端 Pod
port: 80 客户端访问 Service 时使用的端口
targetPort: http 转发到 Pod 中名为 http 的端口，此处对应 80

containerPort 是端口声明，本身不会替程序打开监听端口。应用仍要实际监听正确的地址和端口；通常应监听容器内的可达接口，而不是只监听 127.0.0.1。

4.4 CoreDNS 与服务名解析

在常见配置下，集群通过 CoreDNS 提供 DNS 服务。Pod 中的解析器根据 /etc/resolv.conf，把查询发送到集群 DNS 地址；查询最终到达 CoreDNS。CoreDNS 对集群服务名生成相应结果，对外部域名通常再转发到上游解析器。部分集群还会增加节点本地 DNS 缓存。

假设服务位于 default 命名空间，集群域是 cluster.local，Linux Pod 中常见的访问名称有：

1
2
3

web-demo
web-demo.default
web-demo.default.svc.cluster.local

同命名空间通常可以直接使用短名称，背后依赖解析器的搜索域。cluster.local 可以自定义，不能假定每个集群都一样。普通 ClusterIP Service 的 DNS 结果通常是 Service IP；Headless Service 的结果则可以是后端地址。见 Pod 与 Service 的 DNS。

5. 能运行以后，还要处理健康、数据和配置

5.1 Startup、Readiness 与 Liveness

Running 不等于 Ready。 前者是 Pod 生命周期的阶段，后者表示它是否满足就绪条件。一个 Pod 可以已经运行，但因为应用还在预热、依赖不可用等原因，尚未准备好接收请求。

探针 要回答的问题 失败达到配置阈值后的主要效果
Startup 应用是否完成启动？ 终止容器，按重启策略处理；成功前不执行另两类探针
Readiness 应用现在是否能接请求？ 标记为未就绪，普通 Service 通常不再将其作为可用后端，不直接因此重启
Liveness 应用是否陷入需要重启才能恢复的状态？ 终止容器，按重启策略处理

比如，一个应用需要较长时间加载数据，可以用 Startup 给它留出启动窗口；运行期间暂时无法处理请求，可以让 Readiness 失败；进程死锁且无法自行恢复，才适合由 Liveness 触发重启。Startup 成功后，Readiness 和 Liveness 各自判断，不要求先通过 Readiness 才能做 Liveness。

示例中 Nginx 的三个探针都访问 /，便于理解配置。真实业务通常应根据各探针的目的设计检查条件，避免把一次短暂的外部依赖故障扩大成全体容器反复重启。相关语义见 三类探针配置。

“未就绪不接流量”说的是普通 Service 的常见行为。直接访问 Pod IP 不受 Readiness 自动阻断；显式设置 publishNotReadyAddresses 等配置时，也需要另外判断。

5.2 emptyDir、PV、PVC 与 StorageClass

对象或机制 表示什么 生命周期上的重点
emptyDir Pod 内可共享的临时目录 容器重启通常保留，Pod 从节点移除后数据被删除
PVC 应用对存储容量、访问模式等的申请 Pod 引用它来使用持久化存储
PV 集群中的持久化卷资源 与满足条件的 PVC 绑定
StorageClass 描述存储类别及动态供应方式 有相应供应器时，可按 PVC 动态创建存储和 PV

通常先由 PVC 申请存储，再绑定已有 PV，或触发 StorageClass 对应的动态供应器创建合适的卷，最后 Pod 挂载 PVC。

emptyDir 适合临时文件、缓存或同 Pod 容器间的数据交换；它的生命周期跟着 Pod，不会因为同一个 Pod 中的容器崩溃重启就自动清空。持久卷能否保留数据，则还要结合回收策略、工作负载设置和底层存储判断。emptyDir 的边界见 卷类型说明。

5.3 ConfigMap 与 Secret

ConfigMap 用来存普通配置，例如服务地址、日志级别；Secret 用来承载密码、Token、证书等敏感配置。

需要记住：Secret 的 data 字段使用 Base64 编码，Base64 可以直接解码，并不等于加密。 数据保护还依赖 API 权限、静态加密配置以及实际的密钥管理方式，不能只因为对象叫 Secret 就认定内容已经安全加密。见 Secret 官方说明。

6. 出问题时，先判断卡在哪一步

6.1 排障入口：get、describe 与 logs

故障题不要从“是不是网络坏了”开始猜。先获得事实，再决定往哪层走：

1
2
3
4

# 以下示例使用 default 命名空间；<pod>、<node> 等需要换成实际名称
kubectl get pods -n default -o wide
kubectl describe pod <pod> -n default
kubectl logs <pod> -n default

get 看现状，describe 看资源配置、状态和 Events，logs 看程序输出。对于容器尚未启动的故障，应用日志可能根本不存在，Events 往往更有帮助。

还要区分：Pending、Running 是 Pod 的阶段；CrashLoopBackOff、ImagePullBackOff 是 kubectl 常展示的容器状态原因，不是同一层级的 Pod phase。见 Pod 生命周期。

6.2 Pending：调度与启动准备

Pending 包含等待调度和容器准备过程，不只等于“调度器没找到节点”。在 get -o wide 和 describe 中检查节点分配、PodScheduled 条件和 Events：

看到的线索 优先检查什么
FailedScheduling、Insufficient memory/cpu requests 与节点可分配资源，以及其他 Pod 的已申请资源
节点标签或亲和性不匹配 nodeSelector、required 规则与实际标签
未被容忍的污点 节点 Taint 与 Pod Toleration
PVC 无法绑定 PVC 状态、StorageClass、卷容量和拓扑条件
已有节点，但容器仍未就绪 镜像拉取、卷挂载、Pod 网络及初始化容器

调度提示 Insufficient memory，说明按请求计算无法满足放置条件；它不是在说这个尚未启动的容器已经 OOM 了。合理调整请求、释放已占用容量或扩容节点，需要根据实际资源需求选择。

1
2
3
4

kubectl get nodes
kubectl describe node <node>
kubectl get pvc -n default
kubectl describe pvc <pvc> -n default

6.3 ImagePullBackOff：镜像拉取失败

它表示镜像拉取失败后正在退避重试。可以依次看：镜像名或 tag 是否存在、仓库地址是否可达、节点访问仓库的 DNS 和网络、私有仓库认证，以及 imagePullSecrets 的名称和命名空间是否正确。

架构问题也要看具体错误：仓库没有适配该节点架构的镜像清单，可能导致拉取失败；如果镜像已经拉下来，运行时才报 exec format error，则属于启动阶段，不能一概叫 ImagePullBackOff。

6.4 CrashLoopBackOff：反复退出与重启

这表示容器反复退出、重启，并处在重试退避中。原因可以是应用报错、缺配置、启动命令不对、探针失败，也可能是内存问题；使用 Always 重启策略的容器即使正常退出，也可能不断被重启。

1
2
3

kubectl logs <pod> -n default -c <container>
kubectl logs <pod> -n default -c <container> --previous
kubectl describe pod <pod> -n default

--previous 用来查看同一 Pod 中该容器上一个实例的日志。多容器 Pod 用 -c 指定目标，避免看错容器。结合 Last State、Reason、退出码和探针事件，才能把“反复重启”缩小到具体原因。

6.5 OOMKilled：内存限制与节点压力

现象 怎样判断
容器状态出现 OOMKilled 对照内存 limit、用量峰值、内核记录，调查是否超出容器内存预算
节点内存不足导致系统级 OOM 结合节点状态与内核日志判断，不能只看一个容器的 limit
Pod 显示 Evicted，节点有内存压力 检查 kubelet 的节点压力驱逐事件，与容器 OOM 区分
只看到退出码 137 常见含义是进程被 SIGKILL，不能单凭它认定是 OOM

kubectl top 提供当前采样，不一定能抓到导致 OOM 的短时峰值，最好结合历史监控。处理时再判断是资源预算不合理、批处理峰值过高，还是程序存在内存泄漏。节点压力驱逐与内核 OOM 是不同机制，官方的 节点压力驱逐说明 也区分了两者。

6.6 Running 但 Service 不通 

1
2
3
4
5

kubectl get pods -n default -l app=web-demo -o wide
kubectl describe pod <pod> -n default
kubectl get svc web-demo -n default -o yaml
kubectl get endpointslices -n default -l kubernetes.io/service-name=web-demo -o yaml
kubectl describe svc web-demo -n default
检查顺序 要确认的事实
应用 进程实际监听什么地址和端口，访问应用本身是否正常
Pod 就绪 Ready 是否为真，Readiness 有没有失败
Service 选择 selector 是否匹配 Pod 标签，是否处于同一命名空间
EndpointSlice 是否记录了预期地址、端口，是否存在可用后端
端口映射 Service 的 port、targetPort 与应用实际监听是否一致
网络 NetworkPolicy、网络插件 CNI、节点路由和 Service 转发实现是否正常

没有预期地址时，先看 selector、标签等；有地址但不可用时，先看就绪条件。只有可用地址、端口都正常，才继续深入转发与网络。若能访问 Pod IP 却不能访问 Service IP，重点往 Service 端口、转发规则等方向收敛，而不是继续重复重启应用。

在一个确实包含 cat、nslookup 等工具的 Pod 中执行；精简业务镜像没有这些工具时，使用集群允许的调试镜像或调试容器。

kubectl exec <debug-pod> -n default -- cat /etc/resolv.conf

这些名称与标签是常见约定，实际部署不同就替换。检查顺序是：Pod 的 nameserver 和搜索域 → DNS Service 与可用后端 → CoreDNS 状态和日志 → 到 DNS 的 UDP、TCP 53 端口网络 → 上游解析器。

如果 Service IP 可访问、对应名字却解析失败，就先调查 DNS；如果连集群内服务名也失败，优先调查集群 DNS 链路；如果内部名称正常、只有外部域名失败，再检查上游配置和外部访问。

7.2 面试前三分钟速记

复习时可以先合上正文，试着回答下面这些问题：

问题 一句话抓住重点
Kubernetes 在做什么？ 持续让实际状态接近声明的期望状态
谁保存集群状态？ etcd；其他核心组件通常通过 API Server 读写对象
谁创建、调度、启动 Pod？ 控制器创建对象，调度器选节点，kubelet 协调运行时启动
Pod 为什么存在？ 为紧密协作的容器提供统一调度、共享网络和可共享卷
Pod 出问题后如何恢复？ 区分同一 Pod 内重启容器与控制器补建新 Pod
Deployment 和 StatefulSet 怎么区分？ 可互换的副本，与需要稳定身份的副本
调度主线是什么？ 过滤 → 打分 → 绑定
requests 与 limits 怎么区分？ 请求用于容量与分配，上限约束运行时资源使用
CPU、内存超限有什么区别？ CPU 通常节流，内存不足可能 OOM；137 不是独立证据
亲和性与污点有什么区别？ 前者表达放置条件，后者由节点排斥 Pod；容忍不保证被选中
Service 为什么有用？ 用稳定入口连接会重建、会换 IP 的后端
EndpointSlice 干什么？ 记录后端地址和条件，供网络实现维护规则
CoreDNS 干什么？ 提供集群服务发现，并按配置解析或转发外部域名查询
三种探针怎么区分？ Startup 看启动，Readiness 控制就绪，Liveness 判断是否需重启
emptyDir 与 PVC 怎么区分？ 前者跟随 Pod 生命周期，后者申请持久化存储
Secret 是否等于已加密？ 不等于，Base64 是编码，保护措施需要另外配置
Pending 先查什么？ 节点分配、PodScheduled 条件和 Events
CrashLoopBackOff 先查什么？ 上次退出原因、logs --previous、配置和探针事件
Service 不通先查什么？ 应用监听、Ready、selector、可用 EndpointSlice 和端口
故障题怎么组织回答？ 先确认现象和证据，再沿创建、调度、启动、就绪、访问链路定位

回答面试题时，可以用“一句结论 → 关键过程 → 一个验证方法”的顺序。例如被问到“Pod 已经 Running，为什么还访问不了”，先说 Running 不代表 Ready，再解释就绪条件如何影响普通 Service 的可用后端，最后给出 describe pod 和查询 EndpointSlice 的命令。这样既能说清机制，也能说明自己会怎样验证。

K8s 自动化部署全流程：从一次 Git Push 到发布验证与回滚

接着 Docker、Kubernetes 与容器云部署的学习路线，用一个完整 Go 服务串起 GitHub Actions、GHCR、K8s 发布权限、滚动更新、冒烟验证与失败回滚，并说明如何进一步演进到 GitOps。

前面的《从 Docker 到 Kubernetes》讲清了 Pod、Deployment 和 Service，《K8s 容器云平台服务部署流程》把打包镜像、上传仓库和在平台上创建应用串了起来；《CI/CD 完整指南》则介绍了流水线的基本概念。

接下来很自然会遇到一个问题：应用已经能够手动部署了，怎样做到提交代码以后，自动测试、打包、更新服务，而且出问题能及时发现和恢复？

这篇文章用一个很小的 Go 服务，走完一条完整链路。先理解每一步的输入和输出，再看可以放进项目的配置。示例中的订单服务只是演示 HTTP 服务，没有接入真实订单或数据库。

一、先把“自动化部署”拆成可验证的步骤

手动部署时，很多信息存在人的脑子里：“这个镜像应该是新的”“页面能打开应该就没问题”。自动化以后，这些判断必须变成明确的检查。

阶段 输入 → 输出 通过条件 失败后怎么办
代码集成 PR → 通过检查的提交 单元测试、静态检查、镜像能构建 阻止合并
构建制品 main 的提交 → 容器镜像 构建和推送成功，得到 digest 不进入部署
发布准备 镜像 digest + YAML → 发布计划 集群可达、身份有效、权限足够 保留线上版本
更新服务 发布计划 → 新的 Pod Deployment 完成滚动更新 收集现场，尝试恢复
发布验收 服务接口 → 真实响应 健康检查、业务冒烟、版本都正确 恢复旧 Pod 模板
持续观察 日志和指标 → 发布结论 错误率、延迟、关键业务指标可接受 停止扩大发布，按策略回滚

本文主线采用 GitHub Actions → GHCR → Kubernetes：PR 只做检查，合并到 main 后生成镜像，再部署到专用的 demo-prod 命名空间。保留人工批准时属于持续交付；移除批准且检查通过就上线，才是持续部署。

先说明实验边界。 你需要一个已有 K8s 集群、GitHub 仓库，以及可以管理该命名空间的管理员身份。命令使用 Linux/Bash；Windows 可以在 WSL 或 Git Bash 中执行。示例节点是 linux/amd64。集群搭建沿用前文，本篇重点是把已经能部署的服务接入流水线。

最容易遗漏的准备项并不是 YAML，而是网络：

连接 必须具备的条件
Runner → GitHub / GHCR / 工具下载源 能拉代码、下载工具、推送镜像
Runner → K8s API Server 能访问 kubeconfig 中的地址，证书可信
K8s 节点 → GHCR 节点能拉镜像，私有镜像还要有拉取凭据
外部用户 → 网关 → Service → Pod 入口控制器、DNS、TLS 和后端配置正确

kubectl 登录成功，不代表节点可以拉镜像；Runner 登录了镜像仓库，也不会自动替节点登录。GitHub 托管 Runner 也不能直接访问你电脑上的 127.0.0.1 或公司的内网 API。内网集群应使用可信网络中的专用 Runner，或平台提供的受控网络连接；不要为了跑通实验直接公开管理接口。

package main

import (
	"context"
	"errors"
	"fmt"
	"log"
	"net/http"
	"os"
	"os/signal"
	"sync/atomic"
	"syscall"
	"time"
)

var version = "dev"

func routes(ready *atomic.Bool) http.Handler {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /healthz", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "ok")
	})
	mux.HandleFunc("GET /readyz", func(w http.ResponseWriter, r *http.Request) {
		if !ready.Load() {
			http.Error(w, "not ready", http.StatusServiceUnavailable)
			return
		}
		fmt.Fprintln(w, "ready")
	})
	mux.HandleFunc("GET /version", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, version)
	})
	mux.HandleFunc("GET /{$}", func(w http.ResponseWriter, r *http.Request) {
		fmt.Fprintln(w, "order-api is running")
	})
	return mux
}

func main() {
	var ready atomic.Bool
	ready.Store(true)
	server := &http.Server{
		Addr: ":8080", Handler: routes(&ready),
		ReadHeaderTimeout: 5 * time.Second,
	}
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
	defer stop()
	go func() {
		if err := server.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
			log.Fatal(err)
		}
	}()
	<-ctx.Done()
	ready.Store(false)
	shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()
	if err := server.Shutdown(shutdownCtx); err != nil {
		log.Print(err)
		os.Exit(1)
	}
}

Addr: ":8080" 让服务监听容器网络接口。收到终止信号后先取消就绪，再等待正在处理的请求结束。它是优雅退出的基础；真实系统还要考虑入口连接排空、长连接和后台任务，不能仅凭几行配置承诺零停机。

package main

import (
	"net/http"
	"net/http/httptest"
	"strings"
	"sync/atomic"
	"testing"
)

func TestReleaseContract(t *testing.T) {
	var ready atomic.Bool
	handler := routes(&ready)
	for _, tc := range []struct {
		path   string
		ready  bool
		status int
		body   string
	}{
		{"/healthz", false, 200, "ok"},
		{"/readyz", false, 503, "not ready"},
		{"/readyz", true, 200, "ready"},
		{"/version", true, 200, version},
		{"/", true, 200, "order-api is running"},
	} {
		ready.Store(tc.ready)
		recorder := httptest.NewRecorder()
		handler.ServeHTTP(recorder, httptest.NewRequest(http.MethodGet, tc.path, nil))
		if recorder.Code != tc.status || strings.TrimSpace(recorder.Body.String()) != tc.body {
			t.Errorf("%s ready=%v: status=%d body=%q", tc.path, tc.ready, recorder.Code, recorder.Body.String())
		}
	}
}

  name: order-api
  namespace: demo-prod
spec:
  replicas: 2
  revisionHistoryLimit: 5
  minReadySeconds: 5
  progressDeadlineSeconds: 180
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  selector:
    matchLabels:
      app: order-api
  template:
    metadata:
      labels:
        app: order-api
    spec:
      automountServiceAccountToken: false
      imagePullSecrets:
        - name: ghcr-read
      nodeSelector:
        kubernetes.io/arch: amd64
      terminationGracePeriodSeconds: 30
      securityContext:
        runAsNonRoot: true
        runAsUser: 65532
        seccompProfile:
          type: RuntimeDefault
      containers:
        - name: order-api
          # 模板占位值；发布前会在本地替换成真实 digest。
          image: ghcr.io/your-owner/order-api:replace-before-apply
          ports:
            - name: http
              containerPort: 8080
          envFrom:
            - configMapRef:
                name: order-api-config-v1
          resources:
            requests:
              cpu: 100m
              memory: 64Mi
            limits:
              cpu: 500m
              memory: 128Mi
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
          startupProbe:
            httpGet:
              path: /healthz
              port: http
            periodSeconds: 2
            failureThreshold: 30
          readinessProbe:
            httpGet:
              path: /readyz
              port: http
            periodSeconds: 3
          livenessProbe:
            httpGet:
              path: /healthz
              port: http
            periodSeconds: 10

APP_ENV 用来展示配置注入，当前服务没有据此切换业务逻辑。配置更改时，创建 order-api-config-v2 并修改 Deployment 引用；旧版本暂时保留。这样恢复旧 Pod 模板时，才能同时恢复它引用的那份配置。Secret 也需要版本或外部密钥版本策略，不能把密码写进 ConfigMap。

配置 在发布中的实际作用
startupProbe 启动探针通过之前，不执行 readiness 和 liveness 检查
readinessProbe 未就绪的 Pod 不作为 Service 的正常就绪后端
livenessProbe 连续失败达到阈值后触发容器重启
minReadySeconds: 5 新副本需要持续就绪一段时间，才算可用
maxUnavailable: 0 滚动更新计划中不主动减少可用副本数
maxSurge: 1 可额外创建一个更新用副本，需要预留资源
progressDeadlineSeconds: 180 无发布进展达到期限后报告失败状态

探针的准确语义见 Kubernetes 官方探针文档。发布失败不会因为配置了超时就自动恢复旧版本，后面会由流水线处理。

图中展示的是理想更新顺序。节点故障、容量不足、入口传播延迟和应用本身都可能影响可用性；maxUnavailable: 0 不是“任何情况下都零停机”的保证。终止中的 Pod 也可能让短时间内实际占用的资源超过图中的三份配额。

域名入口由平台准备。 这套最小示例先通过 ClusterIP + port-forward 验证应用。要对外提供服务，再让平台配置 Gateway/Ingress、DNS 和 TLS。Ingress 对象必须配合真正运行的入口控制器，ClusterIP 也不能直接当公网地址使用。

四、先打通身份和权限，再让流水线发布

发布时至少有三套不同凭据：

凭据 谁使用 能做什么 本例如何提供
GITHUB_TOKEN 构建 Job 向 GHCR 发布镜像 GitHub 在 Job 中提供，授予 packages: write
ghcr-read K8s 节点 拉取私有镜像 管理员创建的 docker-registry Secret
KUBE_CONFIG 部署 Job 更新 demo-prod 的应用 受限发布账号的 kubeconfig

GHCR 新发布的包默认是私有的；发布账号有写权限，也不代表节点有读权限。可以将纯演示镜像设为 public，或按下面的私有仓库路径配置拉取 Secret，具体权限参见 GitHub Container registry 文档。

这条初始化命令适合受控实验终端，token 会短暂出现在本机进程参数中；共享主机上应通过平台密钥管理或受控 docker config 导入，别把它写进脚本、shell 历史或日志。已存在同名 Secret 时，按平台流程轮换，不要直接重复创建。

gh secret set KUBE_CONFIG --env production < .deploy-local/ci.kubeconfig

另外添加环境 Variable KUBECTL_VERSION，填写与 API Server 版本兼容的明确补丁版本，例如 v1.35.0 只是格式示例。kubectl 应处于服务端相邻一个次版本范围内，安装和校验方式见 官方 Linux 安装说明。

一小时 token 只用于跑通实验，保存成 Secret 不会让它自动续期。 到期或批准等待过久都会导致 Unauthorized，需要重新生成并更新。长期运行的生产流水线，应使用平台支持的 OIDC/工作负载身份换取短期凭据，或平台托管的轮换机制。GitHub 的 OIDC 令牌也不能直接通用于任意 K8s 集群，需要对应的信任配置或认证交换。TokenRequest 的行为可查 ServiceAccount 官方说明。

name: order-api-release

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-24.04
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - uses: actions/setup-go@v7
        with:
          go-version: '1.26.9'
          cache: false
      - run: go vet ./...
      - run: go test -race -v ./...
      - name: Check Dockerfile on PR
        if: github.event_name == 'pull_request'
        run: docker build --build-arg VERSION=pr-check -t order-api:pr .

  build:
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    needs: test
    runs-on: ubuntu-24.04
    permissions:
      contents: read
      packages: write
    outputs:
      image: ${{ steps.name.outputs.image }}
      digest: ${{ steps.push.outputs.digest }}
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - id: name
        shell: bash
        run: echo "image=ghcr.io/${GITHUB_REPOSITORY,,}" >> "$GITHUB_OUTPUT"
      - uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/setup-buildx-action@v4
      - id: push
        uses: docker/build-push-action@v7
        with:
          context: .
          push: true
          platforms: linux/amd64
          tags: ${{ steps.name.outputs.image }}:sha-${{ github.sha }}
          build-args: VERSION=${{ github.sha }}
          labels: org.opencontainers.image.source=https://github.com/${{ github.repository }}

  deploy:
    needs: build
    runs-on: ubuntu-24.04
    environment: production
    concurrency:
      group: order-api-production
      cancel-in-progress: false
    env:
      KUBECTL_VERSION: ${{ vars.KUBECTL_VERSION }}
      IMAGE_REF: ${{ needs.build.outputs.image }}@${{ needs.build.outputs.digest }}
    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false
      - name: Install compatible kubectl
        shell: bash
        run: |
          set -euo pipefail
          test -n "$KUBECTL_VERSION"
          url="https://dl.k8s.io/release/${KUBECTL_VERSION}/bin/linux/amd64/kubectl"
          curl -fsSL "$url" -o "$RUNNER_TEMP/kubectl"
          curl -fsSL "$url.sha256" -o "$RUNNER_TEMP/kubectl.sha256"
          expected=$(cat "$RUNNER_TEMP/kubectl.sha256")
          printf '%s  %s\n' "$expected" "$RUNNER_TEMP/kubectl" | sha256sum --check
          chmod +x "$RUNNER_TEMP/kubectl"
          echo "$RUNNER_TEMP" >> "$GITHUB_PATH"          
      - name: Configure cluster access
        env:
          KUBE_CONFIG: ${{ secrets.KUBE_CONFIG }}
        shell: bash
        run: |
          set -euo pipefail
          test -n "$KUBE_CONFIG"
          export KUBECONFIG="$RUNNER_TEMP/order-api.kubeconfig"
          umask 077
          printf '%s' "$KUBE_CONFIG" > "$KUBECONFIG"
          echo "KUBECONFIG=$KUBECONFIG" >> "$GITHUB_ENV"
          kubectl auth can-i patch deployments -n demo-prod | grep -qx yes          
      - name: Reject stale release
        env:
          GH_TOKEN: ${{ github.token }}
        shell: bash
        run: |
          set -euo pipefail
          latest=$(gh api "repos/$GITHUB_REPOSITORY/git/ref/heads/main" --jq '.object.sha')
          test "$latest" = "$GITHUB_SHA"          
      - name: Save previous Pod template
        shell: bash
        run: |
          set -euo pipefail
          kubectl -n demo-prod get deployment order-api --ignore-not-found -o json \
            | jq -c '.spec.template // empty' > "$RUNNER_TEMP/previous-template.json"          
      - name: Apply release and wait
        id: release
        shell: bash
        run: |
          set -euo pipefail
          kubectl apply -f k8s/runtime.yaml
          kubectl set image --local -f k8s/deployment.yaml \
            "order-api=$IMAGE_REF" -o yaml > "$RUNNER_TEMP/rendered-deployment.yaml"
          kubectl apply -f "$RUNNER_TEMP/rendered-deployment.yaml"
          kubectl -n demo-prod rollout status deployment/order-api --timeout=240s          
      - name: Verify response and source version
        id: verify
        shell: bash
        run: |
          set -euo pipefail
          kubectl -n demo-prod port-forward service/order-api 18080:80 \
            > "$RUNNER_TEMP/port-forward.log" 2>&1 &
          forward_pid=$!
          trap 'kill "$forward_pid" 2>/dev/null || true' EXIT
          actual=$(curl -fsS --retry 12 --retry-connrefused --retry-delay 1 \
            --max-time 5 http://127.0.0.1:18080/version)
          test "$actual" = "$GITHUB_SHA"
          curl -fsS --max-time 5 http://127.0.0.1:18080/readyz
          test "$(curl -fsS --max-time 5 http://127.0.0.1:18080/)" = "order-api is running"
          printf 'Verified commit: `%s`\n\nImage: `%s`\n' \
            "$GITHUB_SHA" "$IMAGE_REF" >> "$GITHUB_STEP_SUMMARY"          
      - name: Collect failure evidence
        if: ${{ failure() && (steps.release.outcome == 'failure' || steps.verify.outcome == 'failure') }}
        shell: bash
        run: |
          kubectl -n demo-prod get deployment,replicaset,pods -l app=order-api -o wide || true
          kubectl -n demo-prod describe deployment order-api || true
          kubectl -n demo-prod get events --sort-by=.lastTimestamp || true
          kubectl -n demo-prod logs -l app=order-api --all-containers --prefix --tail=100 || true          
      - name: Restore previous Pod template
        if: ${{ failure() && (steps.release.outcome == 'failure' || steps.verify.outcome == 'failure') }}
        shell: bash
        run: |
          set -euo pipefail
          if [ ! -s "$RUNNER_TEMP/previous-template.json" ]; then
            echo 'First deployment: no previous template. Manual investigation required.'
            exit 1
          fi
          patch=$(jq -c '[{op:"replace",path:"/spec/template",value:.}]' "$RUNNER_TEMP/previous-template.json")
          kubectl -n demo-prod patch deployment order-api --type=json -p "$patch"
          kubectl -n demo-prod rollout status deployment/order-api --timeout=240s          
      - name: Remove temporary kubeconfig
        if: always()
        shell: bash
        run: rm -f -- "$RUNNER_TEMP/order-api.kubeconfig"

Actions 的用法和镜像发布权限参考 GitHub 镜像发布教程及 Docker build-push-action。这里为阅读方便使用主版本 tag；生产应将 Action 固定到审核过的完整 commit SHA，再用依赖更新工具维护，@v7 并不是不可变版本。自托管 Runner 还需满足对应 Action 的运行时要求。

这段配置有几个容易看漏的设计：

设计 为什么这样写
PR 只跑 test；main push 才跑 build/deploy 未合并代码不能获取生产发布凭据
needs: test、needs: build 前一阶段失败，后续阶段不会继续
镜像名将仓库全名转为小写 GHCR 镜像路径使用小写，例如 ghcr.io/symphonyw/order-api
tag 记录 SHA，部署使用 image@sha256:... tag 便于查找；digest 精确标识这次发布制品
context: . 明确使用 checkout 后的目录作为 Docker 构建上下文
部署阶段不重新 build 用测试后构建出的同一份制品，避免环境之间产生不同镜像
从本地模板替换镜像后再 apply 集群不会先拉取占位镜像；Git 中的副本、探针等配置也一起生效
发布前读取 main 的最新 SHA 尽量阻止等待时间较长的旧任务覆盖新提交
仅部署 Job 使用固定并发组 同一环境避免两条流水线同时修改工作负载
回滚步骤显式使用 failure() 前面发布失败后，仍可以执行诊断和恢复

cancel-in-progress: false 保留正在执行的部署，但 GitHub 的并发组不是严格 FIFO 发布队列，默认待执行任务可能被更新的任务替换，执行顺序也没有保证。SHA 检查是额外的过期任务检查；检查之后到 apply 之间仍可能有新提交，因此它也不是跨系统事务锁。这里适合“部署最新 main”的模式，要求每个版本严格按序上线时，需要专用发布队列或发布控制器。语义见 GitHub 并发控制说明。

为什么同时检查 rollout 和接口？ kubectl apply 成功只说明 API 接受了资源；rollout status 成功说明控制器完成更新；接口返回正确的 SHA 才证明你访问到了预期版本。冒烟再补一个核心业务请求，可以发现“进程活着，但业务已经坏了”的问题。

本例通过 port-forward service/... 访问选中的一个 Pod，验证了应用响应，但没有覆盖真实 Service 转发、所有副本、DNS、网关和 TLS。如果平台已配置域名，发布验收还应增加 curl -fsS --max-time 10 https://你的域名/version，并执行适合业务的读写验证。不要把一次 HTTP 200 当成整条用户链路已经通过。

六、跑一次正常发布，再演练一次失败恢复

首次操作按下面顺序做，尤其注意私有镜像的授权和短期 token 到期时间：

顺序 操作 应看到的结果
1 初始化 namespace、RBAC、拉取 Secret；配置 production 环境 发布账号权限检查为 yes
2 提交应用文件，创建 PR test 通过，Dockerfile 可以构建
3 将 test 设为 main 的必需检查，再合并 PR build 生成 sha-<commit> tag 和 digest
4 首次发布时检查 GHCR 包访问设置 ghcr-read 使用的账号确实有目标包读权限；需要时暂停批准并修正
5 批准 production（如果配置了批准） deploy 使用同一份 digest 更新 Deployment
6 检查 Workflow Summary 和集群 版本 SHA 匹配，Deployment 有 2 个可用副本

如果 GHCR 中已经存在同名包，还要确认当前仓库获准通过 Actions 写入该包。分支保护、环境批准等功能的可用性取决于仓库类型与组织策略，应以实际仓库设置为准。

kubectl -n demo-prod get pods -l app=order-api

再做一次只影响实验环境的失败演练。 成功发布过一版后，在专用实验仓库中把 readiness 路径改为 /not-ready，通过 PR 检查后合并。应用会对这个路径返回 404，新 Pod 无法就绪，更新最终失败；流水线先打印现场，再恢复发布前保存的 Pod 模板。观察旧版本恢复后，立刻通过新的修复提交把 Git 中的路径改回 /readyz。

恢复时使用“发布前快照”，而不是简单地执行一次无条件 rollout undo，可以避免把“上一条历史记录”误当成“发布前实际在运行的模板”。但这个策略仍有边界：

情况 本例的行为 还需要做什么
测试或镜像构建失败 不改集群 修复代码重新提交
发布前认证、权限或过期任务检查失败 不进入 apply 修正凭据、网络或使用最新提交
新 Pod 不就绪，且已有旧模板 恢复旧模板并等待 rollout 再验证业务与外部访问
首次部署失败 明确失败，没有旧模板可恢复 管理员排错，必要时清理失败资源
恢复也超时 Job 继续失败 人工介入，检查容量、节点、镜像、配置
Job 被取消、Runner 丢失、API 完全不可达 恢复步骤可能无法运行 由外部监控告警和运维流程接管
Service 被错误修改、Secret 原地覆盖或数据库已变更 Pod 模板恢复不等于完整恢复 独立配置版本、兼容迁移或专门恢复流程

恢复成功后，本次工作流仍然是失败状态。 自动回滚表示尝试恢复服务，不表示这次发布通过了。回滚的 rollout 成功也只代表副本重新满足条件，还需要业务检查和指标观察。Deployment 的历史回滚只处理 Pod 模板，具体语义见 Kubernetes Deployment 文档。

遇到故障，可以先按发生位置缩小范围：

表现 优先检查 常用命令或证据
GHCR 推送 403 packages: write、包与仓库关联、组织策略 build Job 日志、包访问设置
Unauthorized / Forbidden token 有效期、当前 context、RoleBinding kubectl auth can-i ...、API 错误
API 连接超时 Runner 网络、API 地址、防火墙、CA kubectl 连接错误，勿输出完整 kubeconfig
ImagePullBackOff digest 是否存在、拉取 Secret、节点出网 kubectl describe pod <pod> -n demo-prod
Pod 一直 Pending CPU/内存、amd64 节点选择、配额 describe 中的调度事件
CrashLoopBackOff 启动参数、配置、运行权限、OOM kubectl logs <pod> -p -n demo-prod
Pod Running 但不 Ready 探针路径、监听地址、依赖状态 describe 与应用日志
内部验证成功，域名访问失败 入口控制器、Service、DNS、TLS 网关日志与外部端到端请求

数据库迁移要单独设计。 常用做法是 expand–migrate–contract：先加向后兼容的字段或表，让新旧应用都能运行；迁移数据并完成观察后，再清理旧结构。迁移 Job 需要自身的幂等、并发和失败处理，不能让每个应用 Pod 启动时都抢着执行不可逆 DDL。回滚应用也不会自动撤销已经发送的消息、调用过的外部接口或修改过的数据。

七、从一条可用流水线，走向长期可维护的发布系统

主线跑通以后，下一步不是立即加入所有工具，而是补齐真实业务需要的验证和治理。

维度 本文的起点 生产中逐步补齐
环境 一个隔离实验命名空间 dev、staging、prod 隔离，生产账号独立
制品 SHA tag + digest 保留历史 digest、漏洞扫描、SBOM、签名验证
凭据 实验用短期 kubeconfig 按 Job 获取短期身份、轮换与审计
验证 readiness + 版本 + 一个业务请求 集成测试、真实入口 E2E、分环境验收
观察 失败日志、手动检查 错误率、P95/P99 延迟、重启数、业务指标及告警
发布策略 两副本滚动更新 根据风险采用金丝雀或蓝绿发布
发布记录 Git SHA、digest、Actions 运行记录 关联环境、配置版本、操作者、审批及恢复结果

多环境推广应复用同一个 digest：构建一次，在 staging 验证后把这份制品推广到 prod，环境差异通过配置注入。不要在每个环境重新构建一份“看起来版本号相同”的镜像。

滚动更新也不是金丝雀：普通 Deployment 逐步替换副本，并不会自动按错误率判断是否继续发布。要做到“先放少量流量，观察指标，再逐渐扩大”，还需要流量控制和渐进式发布控制器；是否采用应取决于业务风险。

再往后，可以把部署端改成 GitOps。 本文是 Push 模式：Runner 带发布身份调用集群 API。GitOps 把期望状态留在部署仓库，由集群侧的 Argo CD 或 Flux 拉取并协调。

对比项 本文的 Push CD GitOps
谁向集群发起变更 CI 的部署 Job 集群侧或受控网络内的协调器
期望版本在哪里 源码模板 + CI 输出的 digest，需要关联记录 Git 中提交了具体 digest 的环境清单
集群发布凭据 由部署 Job 使用 由协调器持有，CI 不必直接连接 API
人工临时修改 默认不持续检测和纠正 可检测漂移，是否纠正取决于配置
版本恢复 恢复模板快照，再修复 Git 将部署仓库中的期望版本改回旧 digest

采用 Argo CD 自动同步时，要先把 Git 中的期望状态改正确；启用 self-heal 后，只在集群手动改镜像可能会被协调器改回。资源删除也需要明确配置 prune，并不是开启同步就会自动做所有清理。相关边界见 Argo CD 自动同步说明。

这条链路的完成标志，是每次发布都能回答：部署来自哪个提交，用的是哪个制品和配置，验证覆盖了什么，出错后恢复到了哪里。 等这些答案都有记录，再去增加多环境、灰度或 GitOps，才有可靠的基础。
